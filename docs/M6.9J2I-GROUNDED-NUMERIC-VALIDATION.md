## Audit before production changes

The old validator removed SKU-like codes and allowed MA28 identifiers, then extracted
`-?\d+(?:[.,]\d+)?`. It recursively collected only finite numeric values from the
observation's referenced facts, not numbers embedded in strings or arbitrary query
text. It accepted exact numeric equality and rounding to 1 or 2 decimal places.
There was no integer-rounding tolerance, package-number recognition, percentage
conversion, arithmetic authorization or structural numeric whitelist. Written
cardinals/ordinals are not digit claims and do not authorize extra numeric values.

Before production edits, 20 focal tests ran: 17 PASS, 3 FAIL. The failures were
legitimate cited product identities containing `900 ml` or `750 g`, including full
and shortened names. Decimals with comma/dot, rounded decimals, recommendedQty
18/24/12 and explicit horizonDays already passed.

`horizonDays: 7`, when materialized in cited forecast facts, was already supported.
It is not automatically authorized just because the question says “esta semana”.
A separate fixture with horizonDays 13 verifies the logic is not hardcoded to 7;
an arbitrary 9999 in the query remains unsupported. No context builder change.

The approved policy still rejects `5.03 → 5`; earlier J.2D regression explicitly
requires that rejection. It accepts `5.03 → 5.0`, `7.16 → 7.2`, `34.75 → 34.8`.
No new numeric tolerance was introduced.

## Fix and number origins

`groundedNumbers.js` separates finite FACT_NUMBER sources from ENTITY_LABEL_NUMBER
occurrences. All sources remain scoped to observations[].evidenceRefs.

Product presentation recognition is restricted to objects with a SKU and name,
productName or displayName. A generated package number must match the exact amount
and unit (ml, kg, mg, g, l) from that name. The preceding name must retain at least
two distinct words in canonical order, allowing controlled shortened names and
accent/case normalization. Decimal comma/dot representations are equivalent.
There are no package unit conversions or a general numeric whitelist.

Only the recognized name/presentation occurrence is excluded from metric-number
checking. The number cannot authorize an unrelated purchase quantity, a second
occurrence, another product, a different unit or a recommendation using that amount.
Package facts in uncited evidence cannot authorize the generated number.

FACT_NUMBER matching retains exact equality and 1–2 decimal rounding. Explicit
horizonDays in cited facts uses this same path. J.2I did not introduce query-number
permissions. J.2J classifies only a leading `1.`/`2.`/`3.` or `1)`/`2)`/`3)` at the
start of a line (optionally after a Markdown bullet) as STRUCTURAL_NUMBER. It removes
only that marker before numeric extraction; digits later on the same line remain
claims. Other arbitrary query digits and SKU digits do not enter the supported fact
set. No calculations, percentages, probabilities or recommended quantities are
derived by the validator.

numbers. Public response, history projection, logs and expandable activity pass
only numeric finite values with absolute magnitude <=1e9, maximum three entries.
Other validation reasons do not expose this field. Oversized/invalid values are
omitted without changing rejection. Label: “Valores rechazados”.

schemaReason/schemaField, validationField, finishReason and content presence remain.
Grounding failure still rejects synthesis and preserves the safe factual fallback.
