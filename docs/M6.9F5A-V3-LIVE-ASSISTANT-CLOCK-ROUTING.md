# M6.9F.5A — Assistant operational clock and LIVE routing

## Scope

This phase separates the V3 historical/model cutoff from the operational
calendar and connects the existing assistant READ skills to the F.4E LIVE
serving contract. It does not run the V3 bootstrap, write operational data,
deploy, or change approved analytics formulas.

## Operational clock

`backend/src/utils/operationalClock.js` is the server-owned date provider. It
uses `America/Lima` and supports injected clocks for deterministic tests. The
V3 service captures one instant and its Lima calendar date per authenticated
request. Browser timezone, locale, and UTC calendar date are not consulted.

`2026-10-12` remains the immutable historical/model and Market Basket cutoff;
it is no longer treated as today's date. Relative periods use the captured
operational date: today, yesterday, the already supported rolling 7/30-day
windows, this week, and this month. Historical explicit dates through the
cutoff use the frozen bundle. Periods that end after the cutoff retain the
full requested period and use LIVE mode, allowing the ML runtime to combine
the canonical history with the authorized operational delta.

## Snapshot and domain routing

For authenticated V3 requests whose `asOfDate` is after the cutoff, the
backend builds a fresh snapshot using the authenticated business id, the
captured operational instant, and the request's as-of date. Snapshot errors
are surfaced as a functional unavailability; the adapter never retries the
same request against stale historical data. Every LIVE response is checked
against the exact snapshot `dataVersion` and `snapshotHash` used by that ML
request. A bounded multi-intent reuses the same immutable snapshot only within
that assistant request; a subsequent READ gets a new snapshot. No analytical
result cache is added, so a later READ builds against the new Mongo revision
after a successful WRITE.

The existing six completed domains route LIVE: Business, Inventory, Forecast,
Customer, Supplier, and Business Health. Forecast remains limited to 1/7/14
days and uses the approved MA28 implementation. Market Basket remains a
historical request at the frozen cutoff, and the user-facing view identifies
that freshness explicitly, including within the LIVE Business Health view.
Historical requests do not build snapshots.

The request payload uses explicit Pydantic context fields rather than copying
internal binding properties. ML schemas accept both snapshot contract v1 and
the F.4B–F.4E v2 receipt/cancellation envelope; v1 remains unchanged.

## Continuations, empty periods, and safety

Product context, bounded multi-intent plans, and READ continuations remain in
the existing V3 conversation state. The focused multi-intent cases cover
Business + Inventory and same-product Inventory + Forecast. An empty day stays
the requested day and can yield zero/no records; it is never replaced by the
last day with activity or the historical cutoff. Current-day sales remain
partial-day operational evidence, while forecast semantics remain total
expected demand as defined by F.4E.

The F.5A changes do not alter the existing action gate: WRITE still prepares a
preview and needs explicit confirmation. Selecting an entity is not a
confirmation. Existing preview, confirm/cancel, and selection-safety tests
remain part of the focused regression set.

## Validation

Focused tests cover Lima clock boundaries, today/yesterday/last-seven-day
resolution, explicit historical date routing, a period crossing the cutoff,
LIVE snapshot v2 submission, frozen Market Basket, snapshot failure with no
historical fallback, `dataVersion` refresh between READs, and v1/v2 ML snapshot
schema compatibility. F.5A runs only these tests plus affected V3 temporal,
context, routing, and WRITE-safety subsets; it does not run the mass P3 audit.

## F.5B blockers / operational activation

- Do not treat this wiring as proof that the real V3 tenant has an audited
  revision-zero bootstrap. Snapshot construction remains fail-closed until
  the separate authorized bootstrap gate is `VERIFIED`.
- Validate one controlled post-cutoff transaction, read-after-write revision
  change, and real zero-sales date only in the separately approved F.5B phase.
- No cloud deployment, browser validation, Atlas access, or real operational
  writes were performed in F.5A.
