# A.3.7.6.4 — API de historial de actualizaciones ML

Esta fase expone en V3 las ejecuciones ya persistidas por `ForecastMlUpdateExecution`. Es una superficie de lectura: no reclama trabajo, recalcula impacto, ejecuta servicios ML, entrena, promueve ni dispara GitHub Actions.

## Rutas

Montadas bajo `/api/intelligence/forecast/ml-update` y protegidas por la autenticación y autorización de negocio existentes:

- `GET /history`: lista compacta, más nueva primero.
- `GET /history/:executionId`: detalle de una ejecución.
- `GET /history/:executionId/products`: productos afectados, paginados por SKU.
- `GET /status`: conserva su función existente de estado actual; no se sustituye por el historial.

Las tres rutas de historial responden `{ success: true, data }`. Los errores exponen únicamente códigos controlados. Una ejecución inexistente y una ejecución fuera del scope producen el mismo `ML_HISTORY_EXECUTION_NOT_FOUND`.

## Scope y filtros

El negocio proviene de `req.user.businessId`; el escenario es el V3 configurado por el servidor, igual que en la API actual de solicitud manual. El cliente no puede elegir negocio ni escenario mediante query. Cada lectura por ejecución aplica simultáneamente `executionId`, `businessId` y `scenarioId`.

La lista acepta exclusivamente `limit`, `cursor`, `triggerSource`, `status`, `from`, `to` y `promotedOnly`. `limit` por defecto es 20 y el máximo 50. Fechas aceptan día ISO o timestamp ISO canónico; `from` no puede ser posterior a `to`. Filtros o claves adicionales se rechazan con error 400 sanitizado.

`promotedOnly=true` requiere evidencia de promoción atribuible a esa ejecución: resultado y decisión `PROMOTED`, y `activeChangeSource=EXECUTION`.

## Cursor y orden

La lista ordena por `{ requestedAt: -1, executionId: -1 }`. El cursor base64url contiene versión, tipo de endpoint, scope, filtros activos y la tupla de continuación. Se valida su forma, fecha, identificador, scope y filtros; así los timestamps iguales continúan por `executionId` sin saltos ni duplicados. El cursor no es una credencial ni autoriza acceso: cada página vuelve a derivar el scope de la sesión.

El endpoint de productos pagina por `sku` ascendente con límite por defecto 25 y máximo 50. Su cursor se vincula al scope y a la ejecución.

## DTO y compatibilidad histórica

La lista proyecta solo campos de resumen y nunca carga los arrays de detalle por SKU. El detalle y productos se serializan mediante allowlists explícitas. No se exponen `_id`, `__v`, claves de idempotencia, tokens, snapshots, hashes, features, datasets, artifacts, errores Mongo ni mensajes de dependencias.

Los campos históricos ausentes permanecen `null`, `UNKNOWN` o `NOT_CAPTURED`, según el campo. No se asigna el `requiredOrigins` actual a una ejecución antigua que no lo almacenó; tampoco se reconstruyen impactos desde snapshots en un GET. Los estados persistidos (`NO_PENDING_WORK`, `NOT_ELIGIBLE`, `EVALUATED_NO_PROMOTION`, `PROMOTED`, `PARTIAL`, `FAILED`, `INTERRUPTED`, entre otros) se conservan y no se reducen a una etiqueta genérica.

Los nombres/SKU y métricas expuestos en productos proceden del impacto durable guardado. Los valores ausentes se mantienen como `null` o `NOT_CAPTURED`.

## Lecturas e índice

La lista usa una proyección compacta y el índice existente `forecast_ml_execution_history` sobre negocio, escenario, `requestedAt` descendente y `executionId` descendente. El detalle filtra por scope e ID público. El endpoint de productos selecciona únicamente los arrays durables de impacto requeridos y pagina en memoria con un límite acotado por el contrato de persistencia (hasta 200 productos por ejecución). Ninguna ruta llama servicios de scoring o runtime.
