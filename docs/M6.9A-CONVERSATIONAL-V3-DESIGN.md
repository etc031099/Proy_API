## 2. Decisión arquitectónica y ownership

Conservar tres agentes y una sola entrada conversacional. Flujo propuesto:

```text
/assistant → POST /api/agent/messages → auth/contexto confiable
 → resolver capabilities/calendario del tenant
 → Coordinator: plan READ acotado, entidades, periodos, continuaciones
 → Operations / Analyst → registry/executor → backend intelligence adapter
 → FastAPI autenticado → motores Python aprobados / artefacto basket
 → DTO validado → evidence + respuesta determinística → UI/historial
```

Decisión C, híbrida: Node mantiene controles, consultas operacionales actuales y resolución de identidades; Python mantiene el cálculo M6.5–M6.8. No portar media móvil, RFM, ABC/XYZ, métricas de supplier ni FP-Growth a JavaScript. No introducir un agente por dominio, framework de agentes ni una ruta paralela `/assistant-v3`.

Coordinator identifica familias y crea como máximo cuatro tareas READ tipadas. Operations responde catálogo, stock vivo, transacciones, reglas/eventos/entregas y stock/recomendaciones de inventario V3. Analyst responde forecast, business/customer/supplier/basket/health e interpretación de inventory intelligence. Una recomendación READ puede ser propiedad de Operations sin conceder a Analyst permiso WRITE. `get_inventory_intelligence` será compartida; las demás seis nuevas skills serán de Analyst.

Para consultas existentes (`get_sales_summary`, `get_product_sales_summary`, `get_top_selling_products`, `get_demand_forecast`, costos y presupuesto), reutilizar el intent y seleccionar adapter por capabilities verificadas. V1/V2 mantienen sus executors/semántica; en V3 el adapter devuelve el mismo contrato antiguo cuando sea compatible o usa la nueva skill explícita si exige otra métrica. No reemplazar respuestas de mínimos/stock vivo por métricas analíticas de riesgo. No enrutar una consulta V3 hacia el joblib V1.

La gramática por familia produce `{family, mode, entities, period, filters, horizonDays, metric}`. Un mapa central family→skill/owner reemplaza la proliferación de excepciones dispersas. El router sigue siendo determinístico; no crear intent por frase ni un router LLM general. Las variantes lingüísticas normalizan texto conservando SKU, tamaños y números.

## 4. Periodos y forecast

Reutilizar el parser endurecido parametrizando calendario/fecha, sin cambiar la convención global. Traducir fechas locales V3 a límites UTC correctos para consultas Node (inicio inclusivo, siguiente día exclusivo); Python recibe fechas locales inclusivas. No usar UTC 00:00 como medianoche Lima.

| Expresión V3 | Resolución al corte |
| --- | --- |
| hoy / ayer / anteayer | 2026-10-12 / 2026-10-11 / 2026-10-10 |
| últimos 7 / 30 / 90 días | corte + 6 / 29 / 89 días anteriores |
| esta semana | lunes→corte; distinto de últimos 7 días |
| semana pasada | lunes→domingo anterior; al comparar semana en curso, mismos días transcurridos |
| este mes | 2026-10-01→2026-10-12; no incluir días futuros |
| mes pasado | 2026-09-01→2026-09-30 |
| histórico / ranking genérico de más vendidos | historia completada disponible hasta el corte; no current_month heredado |
| desde / entre fechas completas | validar orden, calendario, cobertura y corte; rango incompleto pide aclaración |

Resumen general business/health sin periodo: últimos 30 días, anunciado. Supplier general sin periodo: historia observada al corte, anunciado. Customer segmento: RFM fijo 90d; gasto solicitado puede tener otro periodo, rotulado por separado. Inventory sin periodo: snapshot al corte. Basket: periodo del artefacto aprobado, no una ventana inventada.

Comparación sin rango explícito: misma duración inmediatamente anterior; mes en curso contra mismo tramo del mes anterior siguiendo M6.8. Comparación semanal usa mismos días de la semana anterior; si faltan días de historia, comparisonAvailable=false y variación=null. Si el usuario pide dos rangos explícitos desiguales, declarar duraciones y no fingir equivalencia. Periodos sin ventas producen cero, no fallback a otra fecha. No reutilizar selectedPeriod en una nueva pregunta general salvo referencia temporal explícita.

Forecast `MOVING_AVERAGE_28` mantiene fórmula y estrategia versionadas de `v3_baseline_bundle.predict()`, horizontes aprobados 1/7/14 días. Las unidades estiman ventas efectivas observadas, no demanda latente sin restricciones. Confidence y predictionInterval siguen null. Explicación: «Se usa una media móvil de 28 días, seleccionada por su generalización en los horizontes operativos principales del benchmark V3». No afirmar que ganó cualquier métrica/horizonte, ni presentar probabilidad o precisión individual.

«Próximos 7 días» en V3 significa 2026-10-13→2026-10-19 respecto al corte del escenario, no al reloj real. Mostrarlo una vez. «Mañana» = horizonte 1 desde referenceDate. «Esta semana» no equivale automáticamente a 7d: si exige intervalo distinto de 1/7/14, aclarar el horizonte soportado. No dividir 7d entre siete ni inventar curva diaria. Fecha histórica arbitraria solo se atiende si el adapter soporta ese origen y hay 28 días completos previos; señalar que es replay. «Predicción de ayer» sin producto/contexto pide producto y confirma el origen solicitado; con contexto mantiene SKU y usa origen ayer si está soportado. ## 5. Catálogo exacto: siete nuevas skills READ

Todas usan schema cerrado, enums de modo/métrica, límites y allowlists del registry existente. BusinessId, scenario, fechas base, dataset y versiones no son argumentos del usuario/LLM; vienen de contexto confiable. Referencias aceptadas por el executor ya están resueltas y verificadas en el tenant. Filtros product/customer/supplier se intersectan explícitamente, nunca se ignora un filtro no soportado.

Contrato común de salida interna: `{status, data, metadata}`. status = OK/PARTIAL/UNAVAILABLE; metadata incluye corte, timezone, periodo/comparación, sourceMode, versions, datasetSha256, returnedCount, totalMatches, truncated, pagination, reasonCodes y warnings aplicables. Ausencia de dato = null + razón, no cero. Dinero en centavos enteros + moneda (display dos decimales); ratios numéricos sin redondear internamente. Cada DTO proyecta únicamente los campos requeridos por el mode; rankings se calculan globalmente antes de paginar, empates por clave estable.

### 5.1 `get_business_analytics` — Analyst

- Familias: resumen de ventas/negocio, comparación, tickets, margen bruto, rankings producto/categoría/subcategoría.
- Inputs: `mode=summary|compare|rank`, `period={startDate,endDate}`, `comparisonPeriod?`, `entityType=product|category|subcategory`, `metric=units|revenue|gross_margin|gross_margin_pct|tickets`, `productIds?` (máximo 5), `categoryCode?`, `subcategoryCode?`, `limit<=20`, `offset<=10000`. entityType/metric obligatorios en rank; comparación requiere periodos resueltos o política equivalente.
- Entidades: ninguna para resumen; filtro opcional validado; categorías/subcategorías canónicas. Periodo explícito resuelto, HISTORY para ranking genérico, LAST_30_DAYS para resumen sin periodo.
- Output: summary KPI revenueCents/units/tickets/averageTicketCents/cogsCents/grossMarginCents/grossMarginPct por moneda; compare añade previousKpis, deltas, comparisonAvailable; rank añade entidades/valor/cantidad de tickets y totales globales. Margen bruto no es utilidad neta.
- Errores: INVALID_PERIOD, ENTITY_NOT_FOUND, UNSUPPORTED_METRIC, INSUFFICIENT_HISTORY, DATASET_MISMATCH, SERVICE_UNAVAILABLE. Cero ventas es OK; denominador cero implica ratio null.
- Contexto: guarda periodo solo para follow-up de business; ranking tipado en selectedRanking. Una nueva venta general no hereda cliente/producto.
- Ejemplos: «¿Vendí más que la semana pasada?», «¿Qué categoría deja más margen?», «qué vendí más».

No endpoint público que acepte businessId, rutas de fichero, URI Atlas, URL de artifacts, filtros Mongo o Python del cliente. Reutilizar límite 2 MiB, rechazar schema/path/type incorrectos, usar comparación constante del secreto. No conectar FastAPI a Atlas ni introducir credenciales Mongo en Python.

Si falta capacidad de empaquetar el dataset o se exceden memoria/build/tiempo en Render, stop gate de B: reportar tamaño medido y requisito pendiente antes de habilitar V3. No duplicar fórmulas en backend ni servir resultados V1 como sustituto. La inteligencia de tenants reales/mutable requerirá otra fuente/actualización versionada posterior; no afirmar soporte live en esta entrega.

## 7. Resolución, presentaciones y selección clicable

Unificar política 0/1/N sobre ranking/normalización existentes, con adapters por tipo. PRODUCT usa nombre+SKU+brand+presentation/size/unit y mantiene números completos/padding estructurado. No borrar ml/L/gr/pack al normalizar. CATEGORY/SUBCATEGORY usan códigos/labels canónicos relacionados; CUSTOMER/SUPPLIER usan Contact tenant-scoped, stable keys/codes y aliases verificados. Extender proyección de resolver para códigos V3; no crear cinco fuzzy engines separados.

0 coincidencias: mensaje humano y refinar; 1 HIGH_CONFIDENCE: auto-resolve; 1 débil: pedir referencia mejor; N: clickable, cinco por página con total estable/orden/candidatos visibles. No elegir presentación arbitraria de «Inca Kola» o «Coca-Cola». «Inca Kola 500 ml» y «1.5 L» conservan stock, precio, costo y demanda independientes. No consolidar marcas como SKU ni crear identidades nuevas por alias.

La UI actual ya soporta customer/supplier/product. Reutilizar `suggestions`, `suggestionsEntityType`, `suggestionsExpiresAt`, `suggestionsPagination`; ampliar únicamente enums/labels para categoría/subcategoría en D si una ambigüedad real lo exige. El click envía selección del contexto visible, no businessId ni confirmación. Fallback número/ordinal/nombre completo/SKU/código; «el segundo» = segundo visible, incluso en página 2. Una lista de un resultado acepta nombre visible repetido de forma idempotente. F5 restaura snapshot vigente y página; expirado deshabilita sin ejecutar nada.

Identidades internas pueden existir en memoria/auth, nunca en texto público. Labels y messages públicos usan nombre+SKU/código comercial. Un click/nombre se revalida contra el binding y el candidato visible; no confiar en un identificador arbitrario enviado por UI.

## 8. Memoria, multiturn y multi-intent

Campos conceptuales adicionales del snapshot existente: `selectedCustomer`, `selectedCategory`, `selectedSubcategory`, `selectedRanking`; selectedProduct/selectedSupplier/selectedPeriod se mapean al estado actual donde ya existen. No segunda memoria ni respuestas completas. Cada entidad compacta incluye type/id interno/key/label/origin/createdAt; ranking incluye tipo, orden visible, periodo, corte, versión, métricas presentes, página y expiración. Mantener TTL existentes (30 min general, 20 min continuación supplier) y cola por tenant+user+conversation; restauración valida TTL, ownership, schema, versiones y referencias.

Prioridad: nueva intención explícita → entidades explícitas → continuación READ activa → referencia pronominal tipada → aclaración. Un PendingAction antiguo no captura una selección READ nueva. Corrección «no el segundo, el primero» selecciona primero; negación sola «no el segundo» no elige. Parámetros producto/proveedor/cliente/periodo/horizonte se guardan por intención; solo referencias inequívocas heredan. «¿Cuánto vendí?» general no hereda customer/product; «¿y cuánto gastó?» sí usa selectedCustomer. «¿Y su proveedor?» tras cliente ambiguo aclara, no recicla proveedor anterior.

Selección de ranking establece entidad por tipo, no acción. Follow-up que puede calcularse exactamente desde métricas guardadas usa 0 skills/0 LLM y provenance contextual; si falta el campo, invoca una skill específica. Un ranking de mayor demanda no selecciona su primer producto automáticamente. No cruzar listas de clientes/proveedores/productos ni mezclar temporalidad del ranking con stock vivo sin rotular.

| Secuencia | Resultado y llamadas esperadas |
| --- | --- |
| «¿Qué productos están por agotarse?» → «El primero» → «¿Cuánto debería pedir?» → «¿Qué proveedor lo vende?» | inventory READ crea ranking; selección fija producto; recomendación desde snapshot o inventory detail; supplier_products/compare_supplier_costs con ese SKU; 0 LLM |
| «¿Quiénes son mis mejores clientes?» → «El segundo» → «¿Qué suele comprar?» → «¿Cuánto gastó este mes?» | customer rank por gasto 90d anunciado; customer seleccionado; preferencias/gasto exactos con periodo nuevo; no Consumer Final individual; 0 LLM |
| «¿Qué proveedor se demora más?» → «El primero» → «¿Qué productos me vende?» → «¿Alguno está crítico?» | supplier rank por retrasos observados con muestra; supplier_products; inventory sobre SKU de ese proveedor, nunca todo el catálogo como respuesta al pronombre; 0 LLM |
| «¿Cuánto vendí esta semana y qué debería reponer?» | Coordinator crea business task con periodo semanal e inventory task al corte; delega Operations/Analyst; evidencia separada; 2 skills normalmente, 0 LLM |

Decomposición solo para combinaciones de familias soportadas, con parámetros por task y plan validado contra límite de cuatro skills. Si superar límites, preguntar qué priorizar; no aumentar presupuestos. Reutilizar evidencia en el mismo turno; la lista creada ese turno tiene prioridad sobre listas antiguas. Un componente fallido admite respuesta PARTIAL claramente marcada para los otros; no éxito ficticio global.

## 9. Recomendación → acción

«¿Cuánto debo pedir?» siempre READ. «Haz el pedido» expresa intención WRITE, no confirma. Reutilizar referencia analítica solamente como propuesta: resolver SKU/cantidad/proveedor de modo inequívoco, validar entero/pack/disponibilidad/oferta vigente y ejecutar flujo existente de preview+PendingAction. Si hay varias recomendaciones/proveedores, preguntar selección. No convertir decimales forecast en cantidades de compra sin recomendación entera validada.

El usuario confirma el preview por el mecanismo actual; selección de candidato, ranking, «sí» fuera de condiciones seguras o un análisis favorable no equivalen a consentimiento. Repetición no duplica; cancelación/expiración/corrección conservan garantías P2D/P0. Nuevas skills no llaman a create_purchase/sale, applyStockChange, alert evaluator, outbox o dispatcher. No ampliar permisos de Analyst.

## 10. Respuesta pública, lenguaje y LLM

Mantener envelope público actual y trace `participants/actions/evidence/usage`; cada llamada muestra agente, skill, estado/duración y evidencia. No emitir acción «ejecutada» por recomendación. InternalCause, body del servicio, payloads, claves privadas, prompts y razonamiento privado no llegan al cliente. Extensiones públicas necesarias serán aditivas y probadas; no serializar DTO interno entero.

Evidence por dominio: label humano, skillId, periodo/asOf y recordCount; el registry interno conserva versions/hashes y correlation. ContextProvenance diferencia skill nueva de snapshot de lista; no mostrar «consulta ML/DB» si no ocurrió. Costos y moneda separados; precisión UI dos decimales, unidad/unidades y singular/plural. Una mención del corte por bloque coherente, no repetirlo en cada línea.

| Dominio | Formato inicial compacto |
| --- | --- |
| Inventory | hasta 5 filas: producto/presentación · stock al corte · cobertura · riesgo · reponer/shouldReorder · motivo observable |
| Business | ventas y periodo · variación si comparable · margen bruto · ticket promedio · top categoría; no utilidad neta |
| Forecast | producto · estimación unidades/horizonte y fechas · media móvil 28d · advertencia de escenario |
| Customer | nombre · segmento traducido · última compra/recencia · frecuencia/gasto de ventana indicada · preferencias |
| Supplier | nombre/código · compras/gasto · lead time y muestra · puntualidad/retrasos · dependencia aparte |
| Basket | «En el escenario analizado, X e Y aparecen juntos…»; tickets/support; confidence como frecuencia condicional observada, lift para explicación avanzada |
| Business Health | seis dominios en frases breves, hasta 3 prioridades + oportunidad; sin 83/100; dominios no disponibles identificados |

AT_RISK→«cliente en riesgo según actividad observada»; INACTIVE→«sin compras completadas en últimos 90 días»; TOP_HIGH_VALUE→«cliente de alto valor observado». Mostrar razón real (recencia/tendencia) y no probabilidad de abandono. Supplier: «X% de órdenes recibidas fueron tardías con N observaciones», no «es malo» ni causalidad demostrada. Basket no garantiza futuras compras/ventas ni demuestra efecto promocional. Business Health conserva reasonCodes/umbrales observacionales M6.8 y healthScore=null.

Datos básicos, rankings, selección, explicación de reasonCodes, limitaciones, temporales y follow-ups respaldados: 0 LLM/0 tokens. LLM opcional solo para interpretación/redacción residual explícita, con un DTO acotado de hechos ya obtenidos y como máximo una generación lógica de síntesis para estas nuevas rutas. Coordinator determinístico 0 LLM en familias soportadas. No enviar base, historial completo, teléfonos/emails ni perfiles latentes. Aplicar validador grounded actual a cifras/SKU/evidenceRefs y claims. Un failover de provider existente se registra como intento físico, no ocultarlo como cero tokens.

Si síntesis falla, fallback determinístico con los hechos concretos obtenidos. Si no se entiende la intención, aclaración con opciones, sin inventar datos. Fallo del LLM no convierte una consulta determinística soportada en 503. «¿Por qué ocurre esto?» sin evidencia causal explica límites y ofrece comparación factual, 0 LLM/0 skills cuando contexto basta.

## 11. Fallos y seguridad

| Situación | Resultado funcional / diagnóstico |
| --- | --- |
| producto/cliente/proveedor ausente o ambiguo | 0/1/N con selección/refinar; no ejecutar query general sustituta |
| periodo inválido/incompleto o fuera de cobertura | aclaración y rango disponible; no corregir silenciosamente |
| historial insuficiente | readiness/razón por entidad, estimaciones null; listar válidos si batch parcial |
| basket ausente o corte distinto | explicar ausencia de asociaciones validadas; no minería ni LLM generativo para rellenar |
| servicio remoto unavailable / timeout | mensaje seguro; partial si hay otros hechos; categoría sanitizada y correlación, no cifras inventadas |
| schema/version/hash/binding inesperado | fail closed; diagnóstico específico interno; no utilizar otro tenant/versión |
| requisito no modelado (churn/confidence/pérdida/fill-rate) | limitación determinística; no transformar métricas en probabilidades/causas |
| dominio no habilitado para V1/V2 | conservar habilidad existente o informar capacidad no disponible, sin reenrutar a V3 |

Diseño HTTP: validación 400, auth interna 401/403, entidad 404, conflicto de linaje 409, horizonte/contexto semántico 422, servicio 503; detalles sanitizados y no raw excepción. Casos funcionales parciales se representan con status explícito; controller Node conserva códigos públicos seguros y no filtra códigos nuevos sin mapa.

Timeout: mantener 5 s local y 25 s para las siete skills con servicio remoto, HTTP 20 s, cancelación ligada a signal de ejecución y AbortController. Ningún retry nuevo. M6.9B medirá carga y latencia: si un motor excede límites, optimizar loader/proyección/reuso antes de pedir ampliar timeout. No copiar solo Promise.race dejando requests huérfanas. Log allowlist: requestId/conversationId/agentRunId/skillCallId, skillId/domain/status/cause/duration/timeout y versiones no sensibles; nunca valores de clientes/payload/secret.

Forecast source of truth: módulo Python aprobado. No fallback de media móvil reimplementado en Node durante esta integración; si Python no responde, dato no disponible o snapshot validado al mismo corte con etiqueta explícita, únicamente si esa política ya está habilitada. No usar cache vieja como forecast actual.

## 12. Caching y eficiencia

Decisión para B: reutilizar fuente validada e índices del proceso; cargar artifact Market Basket aprobado una vez y verificar hash/version/corte. No ejecutar FP-Growth ni benchmark durante serving. Esto es lifecycle de fuente inmutable, no nueva caché compartida de conversaciones.

Caché de resultados inventory/health: diferir implementación hasta medir latencia; diseño admite clave `(businessId,scenarioId,datasetSha256,asOfDate,timezone,domainVersion,mode,period,comparisonPeriod,horizon,filters,sort,pagination)`. Nunca clave global scenario-only, nunca mensajes/customer context. Invalidar por cambio de dataset/version/capabilities; separar live de fixed. Si se agrega luego, TTL y capacidad bounded, cada respuesta declara source/corte; no omitir filtros ni autorizar desde cache.

Pregunta ventas 7 días invoca solo business; supplier lead time usa supplier con agregados mínimos y dependencia opcional; customer gasto no ejecuta inventory/basket. Cuando un motor actual calcula más de lo necesario, adapter selectivo reutiliza helpers/fórmulas y tests equivalentes, no usa fachada M6.8 completa. Health integral es la única consulta que compone los seis dominios. Proyecciones públicas máximo 20; UI inicial cinco. No repetir resolución/forecast del mismo SKU en el mismo request.

## 16. Riesgos resueltos en diseño y gates pendientes

1. Fuente ignorada por Git: bundle reproducible debe estar físicamente disponible y validado en el servicio; gate B, no supuesto de despliegue.
2. Serving está especializado V1: separar runtime V3 y disponibilidad por capability, conservar V1/V2; no reemplazar el modelo productivo existente.
3. Historia congelada vs live: tags/cortes explícitos; stock/oferta actuales permanecen operacionales; toda compra revalida. No prometer refresco analítico automático.
4. Gasto por rango arbitrario y supplier selectivo requieren adapter de agregaciones existentes; cobertura/equivalencia obligatorias en B.
5. Cliente/categoría/contexto multi-entidad requieren extensión compacta, no están completos hoy; gate D.
6. Calendario V3 Lima/fecha fija vs UTC anterior requiere pruebas de límites; no tocar timezone global.
7. Auth service secret autentica backend, no usuario final: binding server-side de dataset/tenant y validación Node son ambos necesarios.
8. Bundle de tamaño/memoria aún sin medidas serving; no afirmar que cold start cumple 20 s hasta B/E.
9. Basket es artifact congelado y algunos dominios dependen de fuente/corte: preservar null/PARTIAL, sin resultados futuros filtrados hacia atrás.
