## V3 estimate and capacity interpretation

The already validated local V3 scenario occupies an estimated **29.6 MiB** physical footprint (compressed data plus proportionally attributed indexes; approximate). Its logical BSON plus index estimate is about **105 MiB**. With current Atlas usage (~13.74 MiB `storageSize + indexSize`), adding the local physical estimate projects roughly **43.3 MiB** before an operational reserve. A planning reserve of 50% of V3's estimated footprint would put the rough target near **58 MiB**. These are planning estimates only: compression, index allocation, replication, backups, and billing metrics can differ on Atlas.

**Verdict: D — capacity cannot be determined from available metrics.** The observed database is small and V3 is plausibly modest, but the Atlas tier/quota and available headroom are unknown. Do not claim that it fits with a safe margin until those are checked in Atlas metrics/settings.

## Cleanup candidates

There are **no justified Atlas cleanup candidates** from this audit. The previously observed `ML-DEMO-M5-CA3` exists in the local Docker database, not in the Atlas tenant distribution. V1 and V2 are active completed scenarios. Their regenerability, backups, and ownership have not been approved for deletion. No deletion is proposed or authorized.

## Next safe action

Read the Atlas project/cluster tier and storage usage/headroom from the Atlas UI or an authorized read-only Atlas administration view. Compare the provider's actual quota and billing metric with current usage plus at least the ~29.6 MiB V3 local estimate and a reserve. If that gate passes, provision an isolated V3 business using the approved account flow, then import V3 alongside V1/V2 and run canonical-to-Atlas parity. If the gate does not pass, stop and request an explicit cleanup decision; do not remove V1/V2 or shared/auth/integration data as an automatic response.
