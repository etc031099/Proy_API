# A.3.7.4 — Solicitud manual durable de evaluación Ridge

## Arquitectura

Sesión autenticada → POST → transacción Mongo de los estados existentes 7d/14d
→ commit → workflow_dispatch server-to-server (mode=run, main)
→ CLI --check/--run → coordinator → runEligible → worker/evaluación
→ CANDIDATE → promoción/rechazo con la política vigente.

No existe otro entrenador, ningún entrenamiento dentro de Express ni un proceso
en background dependiente de Render Free. El schedule de seis horas recupera
solicitudes aunque falle el dispatch o se duerma el backend. GitHub puede demorar
un run: "ahora" significa solicitar evaluación, no completarla sincrónicamente.

## API

- POST `/api/intelligence/forecast/ml-update/request`, body `{}`, sin query.
- GET `/api/intelligence/forecast/ml-update/status`, sin body ni query.

Ambos usan authenticate y checkBusinessAccess. Scope desde req.user.businessId;
solo se admite el tenant V3 aprobado y su scenario configurado. Otros tenants:
403; sin sesión: 401. No se aceptan campos arbitrarios, horizonDays, tenant,
scenario, force ni policy desde cliente (400). Cache-Control: no-store.

POST nuevo: HTTP 202:

```json
{
  "success": true,
  "data": {
    "requestStatus": "REQUEST_ACCEPTED",
    "trigger": "MANUAL",
    "pending": true,
    "horizons": [7, 14],
    "dispatchStatus": "DISPATCHED",
    "messageCode": "ML_UPDATE_REQUESTED"
  }
}
```

Si falta configuración o falla GitHub: misma aceptación con dispatchStatus DEFERRED;
el trabajo YA está comprometido y no se pierde. DISPATCHED confirma recepción
por GitHub, no inicio/finalización del job. RESERVED representa una reserva durable
de dispatch cuyo resultado aún no se confirmó. Si el proceso muere entre commit y
dispatch, se recupera por schedule o por reintento del POST después de un minuto.

POST duplicado: HTTP 200 ALREADY_PENDING, sin otro trabajo ni otro dispatch
exitoso. Mientras corre una lease vigente: HTTP 200 RUNNING, sin alterar lease,
sin encolar otra ejecución detrás. El pending de la respuesta es global del flujo;
el GET detalla el estado real por horizonte.

## Durabilidad, idempotencia y límites

Se reutiliza ForecastMlUpdateState: manualPending, clave interna de solicitud,
lastManualRequestAt, lastManualDispatchAt, manualDispatchStatus,
lastManualEvaluatedAt, lastManualResult, lastTriggerSource y clave capturada por
el claim. No nueva colección ni eventType comercial falso, no incremento artificial
de dataVersion ni de eventCount. Se mantiene el índice único business/scenario/horizon.

La transacción snapshot/majority coalescea clics simultáneos entre réplicas.
Un dispatch RESERVED se reserva antes de salir a red, evitando el doble clic
durante la llamada HTTP. Un dispatch fallido/no configurado puede reintentarse
como máximo una vez por minuto, con la misma solicitud durable. DISPATCHED no se
reenvía por clics repetidos mientras siga pendiente. No hay retry automático HTTP.

Rate limit HTTP: POST 10/minuto y GET 60/minuto por usuario/negocio. Además,
entre solicitudes nuevas evaluadas existe un límite durable de un minuto por
negocio (429); no depende de la memoria de una réplica. El timeout GitHub es 4s.
La API no espera que termine Actions. No se registra el body/error de GitHub.
Cada dispatch aceptado puede consumir un run y minutos de Actions incluso si
no entrena. Se conserva la cuota del plan/repositorio; no se promete costo cero.
Coalescing y límites reducen clics redundantes, pero no reemplazan esa cuota.

Una instalación sin estados previos inicializa sus watermarks a partir de la
metadata ACTIVE existente y la revisión operacional, sin inventar correcciones
históricas. No escribe Registry/Artifact ni crea un ACTIVE.

## Elegibilidad y consumo

Manual NO omite debounce (15min), cooldown (24h), madurez, comprobaciones de
integridad, 107 origins, fencing ni promoción. Puede evitar esperar seis horas
únicamente al despertar el mismo workflow. No afecta 1d ni introduce MA28.

manualPending refleja una evaluación solicitada, no necesariamente labels nuevos.
describePending conserva la elegibilidad operacional original. Solo RUN puede
consumir una solicitud manual; CHECK y STATUS siguen siendo read-only.

Si no hay trabajo operacional elegible, RUN registra NO_PENDING_WORK,
DEBOUNCE_NOT_ELAPSED, NOT_MATURE, COOLDOWN_ACTIVE o PREVIOUS_FAILURE_NOT_RETRYABLE
y cierra la solicitud manual, sin borrar el pending operacional. No promete
reevaluación inmediata al terminar un debounce: el schedule normal lo recogerá.
Si otra lease está activa, no consume la solicitud.

Cuando sí entrena, el claim captura la clave manual y el ACK/FAIL fenced registra
su resultado. No consume una solicitud posterior. Los reintentos del mismo ACK
mantienen la idempotencia previa. ACTIVE sigue sirviendo durante el proceso.

## GET status para futura UI

Cabecera: dataVersion (string) y closedThrough (Lima). Por 7d/14d:

- activeModelVersion, trainedDataVersion (no desaparecen por pending).
- pending, currentlyRunning, trigger AUTO/MANUAL.
- lastRequestAt (manual), lastAttemptAt, lastEvaluatedAt.
- lastResult: LAST_RESULT_NO_PENDING, LAST_RESULT_INSUFFICIENT_HISTORY,
  LAST_RESULT_REJECTED, LAST_RESULT_PROMOTED, LAST_RESULT_FAILED o NOT_ELIGIBLE_YET.
- lastEvaluationReason específico (enum seguro), eligibility actual, nextEligibleAt.
- requestStatus y dispatchStatus.
- requiredOrigins=107; availableOrigins=null: esta API NO ejecuta Python para
  calcular readiness. No confundir null con cero. El resumen del worker conserva
  los conteos exactos calculados en su preflight.

No Mongo IDs, claves internas de solicitud, hashes, bytes de artifacts, tokens o
mensajes de dependencias. Fallo interno: 503 ML_UPDATE_UNAVAILABLE sanitizado.
