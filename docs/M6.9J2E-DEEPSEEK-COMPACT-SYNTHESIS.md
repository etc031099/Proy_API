## Changes and final strategy

The provider JSON schema remains observations/evidenceRefs/interpretation/
advisoryRecommendation plus limitations. No new response schema, parser fallback,
validator relaxation or architecture is introduced.

The system prompt explicitly asks for:

- at most three recommendations, preferably one grouped observation;
- one or two sentences per product: decision, reason and relevant caveat;
- approximately 100–180 visible tokens, at most approximately 200;
- JSON overhead inside the same 300-token budget;
- no introduction, repeated skill blocks or unrequested methodology;
- no invented facts/actions; supplier metrics remain supplier-wide observations.

Hard cap stays **300** in both request and adapter configuration. No confirmed
historical `length` means no authorized evidence-based increase to 400/450 yet.
`reasoning_effort=none`, cost/usage accounting, domain gate, READ routing, WRITE
safety, provider retries and all analytical formulas remain unchanged.

Accepted synthesis is the sole main answer (as established in J2D). Failed
replenishment synthesis now starts with the explicit failure message, followed by
up to three compact candidate lines: name, stock, incoming, risk and suggested
quantity. Missing numeric facts are “no disponible”, never zero. Full inventory,
forecast and supplier blocks are not repeated in this failure response. Existing
activity/evidence remains available.

For inventory_priorities only, the context projection now:

1. Retains at most three candidate inventory rows, stock/incoming/cover/risk/
   recommendation, configured minimum and ROP when supplied.
2. Retains only forecast rows matching those candidate SKUs and their seven-day
   expected units/method/status.
3. Filters Supplier rows using explicit productsSupplied[].sku or LIVE
