# M6.9F.6A.1 — API autenticada de Inteligencia del Negocio V3

## Alcance

Adaptador de lectura para el dashboard. No cambia fórmulas ni persiste datos. El navegador usa únicamente estas rutas del backend; no conoce la URL ni el secreto interno del servicio ML. La búsqueda de productos reutiliza `GET /api/products?search=...&page=...&limit=...`, ya autenticado y limitado al negocio.

## Seguridad y tiempo

Todas las rutas están montadas bajo `/api/intelligence` y pasan por `authenticate` y `checkBusinessAccess`. El negocio se toma de `req.user.businessId`; los parámetros del request no pueden escoger tenant. El servicio V3 valida que ese negocio tenga el escenario `minimarket-pasco-v3` y su lineage aprobado.

La fecha predeterminada procede del reloj operacional del backend en `America/Lima`. `?asOf=YYYY-MM-DD` es opcional y debe estar entre `2025-10-13` y la fecha operacional actual. Fechas hasta `2026-10-12` usan `HISTORICAL`; fechas posteriores requieren snapshot `LIVE`. Un snapshot requerido pero no válido produce error; no hay fallback silencioso al cutoff histórico. Varias lecturas de un endpoint agregado comparten el mismo `requestId` y snapshot del turno.

## Endpoints

### `GET /api/intelligence/summary`

Devuelve `asOf`, `timezone`, `mode`, freshness si la fuente la ofrece, `salesToday`, `unitsToday`, `ticketsToday`, `averageTicket`, `grossMargin` y resumen de inventario. Ventas con cero real se devuelven como cero. `grossMargin` lleva `value`, `currency`, `percent` y `availability` (`AVAILABLE`, `PARTIAL` o `UNAVAILABLE`); valores desconocidos son `null`, no cero.

Compras pendientes se exponen solo si todas las filas de proveedor incluyen `pendingOrderCount`; de lo contrario el campo es `null`.

### `GET /api/intelligence/inventory?limit=20`

Devuelve resumen de productos/riesgos/reposición y filas compactas (`sku`, `productName`, `presentation`, `stock`, `coverageDays`, `risk`, `riskReasonCodes`, `recommendedQty`, `reorderNow`) del ranking devuelto por el motor, hasta 20. Conserva el orden del motor; los nombres/presentaciones se resuelven en una consulta de catálogo acotada al tenant. El adaptador no calcula puntuación ni reordena productos.

### `GET /api/intelligence/products/:sku/forecast?horizonDays=1|7|14`

Devuelve producto/presentación, `status`, fecha operacional, método `MOVING_AVERAGE_28`, observaciones cerradas y los totales aprobados `horizons.1d/7d/14d`. También devuelve `observedSeries` de 28 fechas cuando haya historia; cada punto distingue `CLOSED`, `ZERO`, `MISSING` y `PARTIAL`.

El forecast V3 aprobado proporciona totales acumulados por horizonte, no una curva de valores diarios. Por eso `forecastPeriod` es un rango con total agregado; no se divide ese total entre días ni se inventa una línea diaria. La solicitud de horizonte 28 devuelve `UNSUPPORTED_HORIZON`.

La serie observada solo se adjunta cuando el backend solicita `includeObservedSeries`; las respuestas ML existentes mantienen su payload predeterminado. No se incorpora el día operacional parcial al historial observado de MA28.

### `GET /api/intelligence/products/:sku/inventory`

Devuelve disponibilidad/freshness (`status`, `availability`, `mode`, `updatedAt`, `dataThrough`) junto con `stock`, `demand`, `coverage`, `inventoryPolicy`, `recommendation`, `risk` y clasificación ABC/XYZ según los campos que entregue el motor. `reorderNow` deriva directamente de `shouldReorder`. El adaptador no etiqueta una recomendación como preventiva porque el contrato analítico no distingue esa semántica.

## Contratos y errores

Las respuestas son `{ success: true, data: ... }`; errores usan `{ success: false, code, message }` con texto seguro. Códigos principales: `LIVE_SNAPSHOT_REQUIRED`, `LIVE_SNAPSHOT_INVALID`, `TENANT_MISMATCH`, `ANALYTICS_UNAVAILABLE`, `PRODUCT_NOT_FOUND`, `INSUFFICIENT_HISTORY`, `UNSUPPORTED_HORIZON`, `INVALID_PERIOD`, `SCENARIO_NOT_SUPPORTED`, `ARTIFACT_UNAVAILABLE` e `INVALID_REQUEST`.

`INSUFFICIENT_HISTORY` para forecast es un estado de datos (200), con horizontes nulos, sin serie pronosticada. Las observaciones disponibles se devuelven si el motor pudo producir la fila. No se exponen hashes, dataVersion, secretos, stack traces ni detalles Mongo.

## Pruebas y regresión

- `backend/test/v3BusinessIntelligenceDashboard.test.js`: cero ventas, margen no disponible/parcial, tenant de contexto, request compartido, 1/7/14, rechazo de 28d, inventario, error sanitizado y autenticación.
- `ml/tests/test_m6_9f4e1_live_http.py`: serie LIVE certificada, día cero, cold-start y horizonte no aprobado.
- `ml/tests/test_m6_9f4e1_live_http.py`: parity histórica con serie habilitada.
- Los endpoints V3 existentes conservan el payload por defecto; `includeObservedSeries` es opcional y se activa solo para la consulta de dashboard.

## Contrato para F.6A.2

1. Cargar tarjetas desde `/summary`; los `null` representan no disponible.
2. Usar el endpoint autenticado `/products` para el selector de SKU/nombre/presentación.
3. Cargar `/inventory` para tabla y distribución de riesgo del motor.
4. Para el SKU seleccionado cargar forecast e inventario; permitir solo horizontes 1, 7 y 14.
5. Presentar la serie observada con su estado; representar la previsión como total del rango seleccionado, no como valores diarios derivados.
6. Mostrar errores funcionales sin detalle interno y nunca reutilizar datos históricos como si fueran LIVE.

Frontend/dashboard visual, tests de UI y F.6B quedan fuera de esta fase.
