# A.3.7.9.4 — Restore local verificable y fencing

Estado: GO para aceptación LOCAL; NO-GO para restore Atlas.
`cloudRestoreEnabled=false`. El servicio administrativo exige localhost y una
base `ml_checkpoint_<32 hex>_test`. No existe endpoint, CLI ni permiso cloud de
restore. No se ejecutó entrenamiento ni dispatch reales.

## Flujo implementado

1. Checkpoint READY y scope exacto de V3.
2. Verificación completa de manifiesto, chunks, SHA256, frames y conteos.
3. Reconstrucción de cada documento y comprobación de round-trip BSON exacto,
   antes de borrar datos. BSON no reproducible por el driver se rechaza.
4. CAS sobre control: TEST_ACTIVE -> RESTORING; `$inc` de resetEpoch BSON int64,
   restoreId, owner nonce y lease acotado. Nunca se copia epoch del checkpoint.
5. Archivo de evidencia de rama en la misma transacción que el CAS.
6. Una transacción por colección: escribir control con owner/epoch, borrar
   únicamente scope y reinsertar documentos BSON sin hooks comerciales.
   Inserciones por lotes de hasta 100 documentos/objetivo 4 MiB; un documento
   BSON grande conserva su integridad y el driver aplica su límite de mensaje.
7. Lectura snapshot final: mismos hashes crudos, bytes, conteos y revisión para
   las 23 colecciones. Los índices fuente no se recrean ni eliminan.
8. Invalidación de identidad de caché y CAS final a TEST_ACTIVE.

La restauración completa NO es una sola transacción de 96 MiB. Un fallo entre
colecciones deja una mezcla transitoria protegida por FAILED/RESTORING. No se
reabre automáticamente. La reanudación explícita con el mismo restoreId vuelve
a aplicar todas las colecciones, conserva epoch y archivo y verifica de nuevo.
Un owner vivo no puede sustituirse antes de expirar su lease; el nonce impide
que un owner anterior continúe después de un takeover. No hay retry infinito.

Repetir el restoreId ya completado verifica igualdad y devuelve idempotent=true
sin incrementar epoch ni crear otro archivo. Si los datos cambiaron, falla
cerrado; otra rama requiere un restoreId nuevo. Errores externos se reducen a
códigos allowlisted sin mensajes Mongo/URI/payloads.

El scope operativo es tenant completo, incluyendo scenarioId=null; ML/histórico
se limita al escenario autorizado. Otro tenant permanece intacto.

## Fencing y writers

`mlTestFence` conserva el token de ciclo con AsyncLocalStorage. El token contiene
presencia del control, testCycleId y resetEpoch; un contexto nuevo no puede
sustituir un token explícito antiguo. Las queries Mongoose diferidas se esperan
dentro del contexto para no perderlo.

Un plugin en los 23 modelos de la allowlist protege save, insertMany, bulkWrite,
updates, replacements y deletes. Para una mutación V3 en TEST_ACTIVE exige:
token capturado + transacción. Escribe un nonce sobre el control en ESA misma
sesión/transacción con condición de epoch/ciclo/estado. Esto produce conflicto
real con el CAS de restore y evita write skew. Un snapshot antiguo de la
transacción no autoriza un commit posterior al reset. Ante conflicto se consulta
la versión actual para distinguir STALE_TEST_EPOCH de contención del mismo epoch.

NO_TEST o control ausente conserva las operaciones normales. No se crean
controles/índices desde el guard. En test, un camino sin token/transacción falla
cerrado; no se vuelve inseguro para permitir la demo.

| Camino | Integración |
|---|---|
| Venta/compra | Ciclo en writeTransaction, plugin en Product/Transaction/Movement y journal |
| Cancelación/ajustes/crédito | Contexto HTTP autenticado + plugin en los modelos que mutan |
| Recepción diferida | Ciclo en receiveV3Purchase, guard dentro de su transacción existente |
| Solicitud ML | Ciclo desde request; transacción original y bookkeeping protegido |
| Coordinator/claims | Ciclo y transacción local de mutaciones en test; claim transporta testEpoch |
| Worker/job/artifact/promotion | Ciclo de worker y plugin dentro de transacciones existentes |
| ACK/FAIL | Token del claim y guard transaccional; epoch antiguo no puede persistir |
| Historial/impacto durable | Ciclo desde inicio de mutación; repositorio transaccional en test |
| Alertas/outbox/delivery | Modelos protegidos; entrega y claims externos suprimidos en modo test |

El runner CLOUD rechaza cualquier control test activo antes de preparar historial
o ejecutar worker. También bloquea un Action antiguo que recién comienza. En
esta fase es una prohibición completa, no una habilitación de entrenamiento en
cloud con epoch. Las pruebas tardías ejercen writers reales de modelos y una
transacción real antigua; la promoción v2 es un estado simulado, sin fit/policy.

## Cachés y reloj

La identidad de los contextos backend incorpora testCycleId/resetEpoch y una
generación local. Al cambiar se limpian bindings, entidades, turnos y snapshots.
RESTORING/FAILED bloquea nuevas lecturas BI de datos intermedios. La lookup es
por índice businessId, sin tocar datos ni crear colecciones.

ML LIVE ya usa la identidad completa del snapshot incluyendo snapshotHash,
dataVersion, asOfDate y observationsClosedThrough. Ridge no introduce una caché
de artefactos solo por versión. Restaurar bytes idénticos reutiliza, como mucho,
un contexto semánticamente idéntico; nuevo cierre/reloj cambia la identidad.
No se cambian fórmulas, features ni contrato Python.

No hay frontend administrativo de restore en esta fase. Un nuevo request lee
la identidad actual; no se afirma haber cancelado respuestas HTTP ya en vuelo
ni actualizado automáticamente pestañas de otros procesos. Es un gate de 9.5.

No se restaura el reloj. Solo revisión/estado/documentos persistidos vuelven al
checkpoint. Watermarks y madurez se derivan de la hora actual al consultarse.

## Side effects y evidencia

Con control distinto de NO_TEST se suprimen Telegram, webhook Node-RED,
dispatcher outbox, channel delivery y dispatch GitHub antes de enviar. La
supresión es conservadora para el proceso/servicio entero mientras V3 está en
test. No se supone que revoca un mensaje que Node-RED ya recibió antes del test.

`mltestbrancharchives` está fuera del snapshot y tiene índice único aditivo
businessId/restoreId, provisionado solo en la base LOCAL desechable. Conserva
NORMAL/OUTLIER/SHIFT, checkpointId, testCycleId, epoch, fecha real, revisión
checkpoint/rama, modelos antes/después, executionIds (máximo 1000) y diferencias
de conteos por colección. No duplica dataset, prompts ni artifactData.

## A.3.7.9.5 propuesta

1. Certificar fencing entre procesos locales y Action/ACK retrasados con tokens
   persistidos; inyectar SIGKILL y recuperar lease sin preemptar owner vivo.
2. Auditar y cerrar bypasses fuera de Mongoose (scripts administrativos, clientes
   directos/credenciales Atlas, DDL/startup); plugin no intercepta raw driver externo.
3. Protocolo de quiescencia de entregas Node-RED/Telegram ya en vuelo y confirmación
   de supresión end-to-end. Mantener worker cloud deshabilitado en modo test.
4. Señal de generación/refresh al frontend y descarte de respuestas anteriores al
   restore; invalidación comprobada en varios procesos backend/ML.
5. Fixture LOCAL del volumen medido (~96.4 MiB, 56k docs) y límites por colección,
   ensayo de disco/tiempo/transaction lifetime, política explícita de recuperación.
6. Solo después: diseñar habilitación administrativa cloud separada con verificación
   de índices, backup/espacio, autorización explícita y criterios GO. Ninguna ejecución
   Atlas de restore queda autorizada por los tests de esta fase.
