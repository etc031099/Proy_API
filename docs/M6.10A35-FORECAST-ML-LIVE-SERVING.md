# M6.10A.3.5 — Forecast ML LIVE serving

## Scope

This phase connects the already trained and promoted Ridge artifacts from A.3.4 to the authenticated V3 forecast endpoint and dashboard. It does not train, promote, change, or rewrite an artifact.

## Serving contract

- Historical requests at or before the frozen V3 cutoff keep the existing MA28 result and evaluation contract.
- LIVE requests use the exact ACTIVE registry pointer scoped by authenticated business, V3 scenario, and requested horizon.
- Ridge is eligible only for 7- and 14-day horizons. One day returns `MODEL_NOT_APPROVED`, with no model artifact lookup and no MA28 fallback.
- Missing ACTIVE artifacts, insufficient history, unavailable features, invalid artifacts, or scoring failures return an explicit status and a null prediction. No fallback converts these states into a LIVE forecast.
- The model artifact is read from the registry and re-verified by the ML service: tenant, scenario, horizon, model family/recipe, feature and policy hashes, byte count, and artifact SHA256.
- Only the required metadata and bounded artifact bytes are sent in the authenticated backend-to-ML request. The operational snapshot retains its own 1.5 MiB validation; the combined forecast envelope is capped at 2 MiB.

## Response and display

The product forecast response exposes the selected horizon's total, model family/version, training revision, data cutoff, feature/promotion-policy versions, snapshot revision/hash, pending-training comparison, observed series, and MA28 baseline where available. The dashboard presents MA28 only as a statistical baseline; it never substitutes that value for a missing Ridge prediction. The active-model panel reads 1/7/14 metadata without retaining completed cache entries, so a registry promotion is visible without an operational revision bump.

## Validation performed

- Backend dashboard focal tests cover ACTIVE 7/14 artifacts, unavailable artifacts, the 1-day no-artifact path, no numeric fallback, historical MA28 preservation, and safe active-model metadata.
- Frontend dashboard and evaluation focal tests cover Ridge metadata, the MA28 baseline label, and the unapproved 1-day state.
- Forecast request schema tests enforce LIVE/detail/single-SKU scope and reject artifacts outside Ridge LIVE requests.

## A.3.5.3 focused serving-contract fix and local E2E (2026-10-16)

### Diagnosis and contract decision

`app.py::execute_v3` is the common caller for LIVE domain handlers and consistently unpacks `(data, cutoff)` so it can build response metadata from the operational cutoff. The MA28 LIVE adapter already returns `(data, live.as_of_date)`, as do the other domain adapters. Historical `forecast_data()` also returns `(data, cutoff)` and uses the frozen `2026-10-12` date. Ridge LIVE alone returned the result dictionary directly. This produced the observed `ValueError: too many values to unpack (expected 2)` and an HTTP 500 normalized by the backend to 503. The canonical contract is therefore the existing uniform tuple, not a new app-level branch or a second response shape.

The minimal fix makes the Ridge branch return `(_run(...), live.as_of_date)`. This preserves forecast latency accounting and uses the snapshot's operational date for response metadata. The model row continues to use `observationsClosedThrough` (T) for `observationsThrough`, `observationCutoff`, and the forecast start date (T+1); those values are not substituted for the operational response cutoff. The historical `forecast_data()` path and MA28 semantics were not changed.

The earlier historical HTTP 503 did not reproduce in the controlled rerun: with the local service secret aligned, historical forecast returned HTTP 200 before and after the fix. No separate historical code defect was established; the initial 503 remains unattributed to a code path. Historical behavior is covered by the existing real-runtime HTTP regression test and the local E2E below.
