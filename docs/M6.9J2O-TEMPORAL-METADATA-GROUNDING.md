# M6.9J.2O — Grounding de números del período de análisis

## Hallazgo

La evidencia cloud reportada para “¿Qué clientes debería intentar recuperar y por qué?” muestra `UNSUPPORTED_NUMBER`, campo `observations[0].interpretation`, valor `30`, clasificado como `QUANTITY_WITH_UNIT`. La respuesta usó `get_customer_intelligence`; el rango informado fue `2026-09-16` a `2026-10-15`.

La inspección local confirma el origen del rango. `buildGroundedPlan` usa `resolveOperationalPeriod`; cuando la consulta no especifica periodo, ese parser crea una ventana móvil predeterminada de 30 días. Para la fecha operativa `2026-10-15`, produce `2026-09-16`–`2026-10-15`. El executor devuelve el periodo solicitado en `result.metadata.period`, y `buildGroundedContext` ya lo exponía como límites de fecha.

El defecto estaba en la frontera de grounding: `numericEvidence` reconocía fechas ISO exactas, pero eliminaba sus componentes para impedir que año, mes y día se usaran como métricas. No derivaba la duración del rango. Por eso la prosa equivalente a “los últimos 30 días” se rechazaba aunque el periodo real estuviera citado.

## Convención temporal y regla

El parser local crea ventanas móviles con `startDate = endDate - (days - 1)`. El servicio de serving resuelve los rangos como fechas calendario locales inclusivas y reporta `days = end - start + 1`; los filtros de ventas incluyen ambos extremos. Para `2026-09-16`–`2026-10-15`, el conteo es 30 días.

El contexto grounded deriva `analysisWindowDays` solo de límites ISO válidos, ordenados e inclusivos que ya llegaron en metadata de la skill. Si metadata futura incluye un conteo `days` marcado `inclusive`, se usa únicamente cuando concuerda con los extremos; de lo contrario, se deriva de esos extremos bajo la convención verificada. No se introduce un 30 fijo ni una excepción para clientes.

La duración se conserva en un campo tipado separado. Solo una expresión de ventana reciente como “últimos N días” puede usarla. No se agrega al conjunto general de cifras permitidas: un rango de 30 días no autoriza 30 unidades, tickets, porcentajes ni cantidades comerciales. Fechas autorizadas siguen habilitando únicamente la fecha ISO completa, no sus componentes como métricas.

## Casos de validación

- Periodo `2026-09-16`–`2026-10-15`: “últimos 30 días” pasa.
- Con el mismo periodo, “últimos 60 días” y “últimos 90 días” siguen fallando como `QUANTITY_WITH_UNIT`.
- “30 unidades” no queda autorizado por una ventana de 30 días.
- Porcentajes sin evidencia, descuentos inventados y la afirmación prohibida de probabilidad de abandono siguen rechazándose.
- Fechas de última compra `2026-08-22`, `2026-09-02`, `2026-09-10` y fecha de consulta `2026-10-15` se pueden citar como fechas completas. Los componentes por separado no se tratan como métricas.
- Horizontes de forecast 1, 7 y 14 días siguen fundamentados por `horizonDays`; 28 días conserva la aclaración operativa existente.
- Metadata de periodo ausente, inválida o invertida no genera `analysisWindowDays`.

## Alcance y comprobaciones

El cambio solo toca el proyector de contexto y el numeric grounding del backend, agrega una prueba focal y la incluye en `npm --prefix backend run test:grounded-acceptance`. No modifica schema, códigos de limitations, límites de salida, routing, skills, lógica de clientes, forecast, modelos, Telegram, WRITE safety ni precios.

La prueba focal J.2O pasó **12/12**. La suite reusable pasó **460/460**, incluyendo los 80 casos de aceptación J.2N y las pruebas de J.2M, J.2K, J.2I, J.2H y proveedores. TypeScript, ESLint focal, sintaxis JavaScript/JSON y `git diff --check` pasaron.

No se hicieron llamadas reales a DeepSeek o Gemini ni se consumieron tokens reales. No se consultó cloud ni se modificaron datos. La evidencia cloud de este informe es la transcrita en el reporte de fase; el smoke cloud queda pendiente para después de publicar y desplegar el backend.
