`intent=FORECAST`, `productQuery=null`, `horizonDays=7`, sin aclaración.

```json

```

del estado. La condición anterior solo propagaba el producto cuando había `ese/este/esto/eso`.

fixture, no una medición de cloud ni una estimación real para Cocinero.

## Precedencia y protección final

1. Las selecciones ordinales y confirmaciones siguen su flujo determinístico existente.
2. Una referencia explícita del mensaje, incluido un `productQuery` literal validado, se resuelve
   mediante J.2S y tiene prioridad sobre el producto anterior.
3. Un follow-up contextual compatible puede usar el producto activo dentro del tenant/TTL existente.
   Además de pronombres, se reconocen elipsis como «y cuanto crees que salga esta semana» y
   «y como viene esta semana». Una petición explícitamente global no hereda ese filtro.
4. Sin producto resoluble, inventory/cross-sell piden referencia; un forecast contextual también
   pide aclaración y no ejecuta un agregado silencioso. Forecast genuinamente global sigue disponible.
5. Clientes no hereda filtros de producto. «y ese proveedor como anda» sin proveedor seleccionado
   solicita identificación; no se inventa una relación producto/proveedor.
6. `pan`, `primor`, `eso`, `hazlo` sin referente/intención suficiente conservan aclaración o selección
   determinística, sin enviar todo al NLU. Los 19 intents, schema, resolver y WRITE no cambian.

Se añade `languageDecision` a respuesta/historial y tipos UI: intención, uso de fallback,
`entitySource` (`explicit`, `active_context`, `resolver`, `none`) y SKU contextual resuelto cuando
corresponde. Solo usa datos seguros ya presentes en estado; no incluye prompts, reasoning ni secretos.
La traza representa la decisión principal y su entidad de producto; no es un log completo por tarea.
