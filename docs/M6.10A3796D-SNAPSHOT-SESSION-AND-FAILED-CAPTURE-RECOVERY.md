## Diagnóstico: qué sabemos y qué no

El código anterior de `mlTestCheckpointService.withSnapshot` iniciaba una transacción con readConcern snapshot y readPreference primary. Mantenía la transacción abierta durante toda la lectura BSON, hashing y las esperas de inserción secuencial de chunks. Los chunks se escribían fuera de la sesión de lectura, pero sus esperas prolongaban la transacción abierta. El commit llegaba solamente al terminar todas las colecciones.

La transacción de lectura no definía writeConcern ni maxCommitTimeMS explícitos. Los cursores tenían maxTimeMS 45000; el presupuesto total de captura ya era 120000 ms. No se aumentó ninguno en esta fase.

`codeOf` convierte el error nativo 251 en CHECKPOINT_SNAPSHOT_TRANSACTION_FAILED. 251 significa NoSuchTransaction y por sí solo NO demuestra por qué fue abortada la transacción.

`markFailed` guardaba el código funcional pero después se relanzaba el error nativo. El executor reconocía códigos string con prefijos funcionales: el número 251 terminaba convertido en ML_TEST_OPERATION_FAILED. Los logs antiguos no conservaban codeName, labels, fase ni tiempos por etapa.

Los ~77 s cloud incluyen adquisición, lectura, hashing, esperas de chunks y fallo. No es posible reconstruir su distribución exacta a partir del log histórico. El preflight de ~62 s y el diseño anterior evidencian exposición al límite de duración de transacciones; no permiten afirmar retrospectivamente el parámetro real de Atlas ni su tier. No se accedió a cloud para averiguarlo.

Prueba local demostrativa: Mongo 7 devolvió transactionLifetimeLimitSeconds=60 (solo lectura; no se cambió). Una transacción antigua abierta durante una espera de 95 s falló con 251. Durante esa misma espera la captura corregida llegó a READY, mantuvo el mismo atClusterTime y rechazó un writer que intentó entrar.

## Corrección de lectura

Se utiliza una única sesión del driver `startSession({snapshot:true, causalConsistency:false})`, sin transacción de lectura larga. Todas las consultas de origen usan esa sesión, readConcern snapshot y readPreference primary. El driver fija el primer atClusterTime confirmado por mayoría y lo reutiliza entre colecciones y getMore.

No se sustituyó el snapshot por lecturas independientes. Una prueba inserta una mutación externa entre dos lecturas y verifica que el snapshot sigue viendo el valor previo. Otra comprueba que los comandos de lectura usan el mismo atClusterTime.

Los BSON originales se transmiten por streaming a chunks de hasta 4 MiB. No se materializa un buffer de 101 MB. Se conservan manifiesto, scope, hashes, reread/verificación de chunks, finalización atómica y restore exacto. Quiescence y el registro durable de writers siguen bloqueando mutaciones durante lectura, persistencia y verificación.

La transacción final corta READY + TEST_ACTIVE no se elimina. Los límites continúan: 128 MiB, 200000 documentos, 128 chunks, 512 MiB RSS y 120 s de captura; no hay retry genérico, fallback a lectura no consistente ni aumento de timeout.

Requiere MongoDB 5.0+ y soporte de snapshot sessions del driver. SnapshotTooOld / SnapshotUnavailable fallan cerrado con códigos específicos; el historial de snapshots de Atlas sigue siendo un límite real.

## Recuperación administrativa, no restore

Nueva ruta privada: POST /api/ml-test/recover-failed-checkpoint, body exactamente {} y sin query.

Usa authenticate + authorize('admin') existentes y el executor. Scope server-side fijo demo V3; target certificado y flag ML_TEST_CLOUD_RESTORE_ENABLED obligatorio. No acepta checkpointId, tenant, epoch, actor o bypass desde cliente.

Acción: ABORT_FAILED_CHECKPOINT. Únicamente abandona una captura que nunca llegó a READY:

- Control FAILED, checkpoint activo válido y mismo scope.
- Checkpoint FAILED sin readyAt, nunca restaurable.
- Protocolo nuevo: marcador de captura y readyAt explícito.
- Protocolo legacy: dataVersion nulo, sin manifiesto/hash completo, totalBytes/totalChunks cero. Se permiten chunks parciales preservados. Un manifiesto legacy completo es ambiguo y se rechaza.
- Sin restoreId, owner/heartbeat/lease de restore ni restoreFinish.
- Sin lastCheckpointId previo, otro checkpoint READY, writers o trabajo incompatible.
- Epoch BSON Long válido, no negativo y con margen para incrementar.
- Auditoría STARTED obligatoria; epoch y ciclo de esa acción deben coincidir con el control.

Una transacción corta con snapshot/primary/majority hace CAS del control FAILED con checkpoint/ciclo/epoch esperados, incrementa resetEpoch en uno, registra recibo de abandono en el checkpoint y confirma la auditoría SUCCEEDED. Solo entonces se publica NO_TEST/maintenance=false.

No borra checkpoint ni chunks; no restaura, edita o elimina datos operacionales. El checkpoint conserva status FAILED, failureCode y diagnóstico, agregando metadatos abandoned*. El ciclo queda como tombstone; el siguiente checkpoint adquiere nueva identidad/epoch.

Concurrencia: una llamada gana el CAS; la otra falla explícitamente. Repetición posterior: solo se reconoce un recibo persistido coherente con el control y una auditoría SUCCEEDED de esa misma identidad; no vuelve a incrementar epoch. Si se pierde el ACK del commit, el handler no sobrescribe la auditoría atómica SUCCEEDED con FAILED.

Status y restore siguen accesibles durante maintenance. La nueva ruta no se cuenta como writer de sí misma, pero mantiene auth/admin/flag/certificación y todas las precondiciones. No se ha invocado en cloud.

## Diagnóstico seguro

ML_TEST_CHECKPOINT_FAILURE incluye únicamente:
checkpointId, fase, colección allowlisted, sessionPhase, durationMs, name/code/codeName, labels allowlisted y categoría segura.

No incluye message, stack, URI, credenciales, documentos o artifacts. El código funcional preciso se conserva en HTTP/auditoría. GET status vuelve a sanitizar los campos persistidos.

Métricas permitidas: totalMs, snapshotSessionMs, snapshotTransactionMs, chunkWriteMs, verifyMs, finalizeTransactionMs, bytesStreamed, maxChunkBytes y peakRssBytes. El resultado interno de captura incluye los tiempos finales; la metadata escrita dentro de la finalización contiene solamente las métricas conocidas antes del commit (no se inventa su duración posterior). El pico RSS es muestreo, no una garantía de capturar cada micro-pico de asignación.

## Riesgos y siguiente paso (no ejecutado)

- No se conoce el tier, versión/parámetros ni motivo original detallado del aborto de Atlas.
- Snapshot sessions evitan transactionLifetimeLimitSeconds, pero no el límite de historia, red, cursores o presupuesto de operación. Cualquier fallo permanece cerrado en FAILED.
- Una muerte abrupta o writer abandonado mantiene maintenance; no hay liberación por TTL que pudiera abrir una carrera.
- La recuperación legacy solo admite evidencia inequívoca de captura nunca READY. Casos ambiguos requieren investigación explícita.
- Un commit con resultado incierto puede requerir consultar status y repetir únicamente la acción idempotente apropiada; no se agregaron retries genéricos.
- El protocolo presupone writers operativos sujetos al fencing certificado; escrituras administrativas externas no coordinadas no se deben realizar durante el flujo.
- Antes de usar cloud se necesita publicación/deploy autorizados de backend y validación read-only del target/status. El cloud actual permanece intacto.
- Después, solo bajo autorización separada, la recuperación autenticada puede abandonar la captura FAILED existente; verificar NO_TEST/epoch/audit/evidencia antes de intentar una nueva captura. No ejecutar restore de la captura fallida.
