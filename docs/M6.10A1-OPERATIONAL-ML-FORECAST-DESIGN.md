## 3. Horizonte, origen y estrategia recomendada

| Alternativa | Ventaja | Riesgo/costo | Decisión de diseño |
|---|---|---|---|
| Tres modelos directos globales, uno porh | Target idéntico al total 1/7/14; sin alimentar predicciones como lags | Tres fits y posible incoherencia acumulativa | Base recomendada para primera implementación, si supera gates |
| Un modelo conh como feature | Comparte información, un artefacto | Requiere validación porh, target/rate cuidadosamente definido; correlación entre ejemplos | Próximo experimento acotado razonable, no implementado |
| Recursivo diario | Una salida aprendida diaria y suma | Error se propaga, lags futuros fabricados, precio/stock futuro incierto | No recomendado para primera versión |
| Multioutput directo | Una API/objeto con tres targets | Purga al horizonte máximo reduce datosh 1; misma dificultad de cobertura/coherencia | No necesario para este primer diseño |

Unidad de activación: **un bundle** de tres estimadores y una única versión. Un solo puntero activo por `(businessId,scenarioId,strategyId)`; featureVersion es una propiedad del bundle, no otra clave que permita dos champions simultáneos. No activar h1 de una versión y h14 de otra. En ausencia de un nuevo modelo que pase, no se inventa un bundle champion.

Modelo diario: origen T al cierre del día; features solo hastaT, labels T+1…T+h. Para servir el díaD, último origen completo D−1 y horizonte D…D+h−1. No interpretar el total deh 1 como «ventas restantes desde esta hora». El día parcialD queda fuera de features diarias. Reconciliación futura acumulativa p 7≥p 1, p 14≥p 7 se evalúa DESPUÉS del postproceso, con los mismos gates; no prometer que tres modelos directos son coherentes sin comprobarlo.

**Actualización automática no equivale a reacción numérica intradía a cada venta.** Toda venta encola trabajo y actualiza la vista parcial, pero nuevas etiquetas/ventanas diarias se habilitan cuando existen cierres. Si el requisito final exige nowcast que cambie con cada venta intradía, harían falta features de hora/progreso y un entrenamiento temporal intradía: ese contrato no está demostrado por el benchmark diario. Se deja como decisión de alcance, sin reutilizar una cantidad parcial como si fuera un día completo.

## 8. Diseño de eventos y coordinador ML

### 8.1 Flujo futuro

```text
POST comercial autenticado
  → transacciónMongo: operación + ledger/journal + revision + ML update request
  → commit
  → respuesta alusuario
  → wakeup opcional, sin esperarentrenamiento

Outbox durable → coordinador pornegocio/dominio → debounce/microbatch
  → export PIT de datos a revisiónfija
  → refresh de features/cierres; verificar madurez de labels
  → TRAIN → CANDIDATE → VALIDATE → PROMOTE / REJECT
  → artefactos persistidos + puntero ACTIVE atómico
  → inferencia con bundle activo y datosactuales válidos
```

No reutilizar directamente `InventoryAlertOutboxEvent`: su enum y payload son de avisos de stock. Reutilizar patrón de transacción, identidad única, claim, lease, ACK/retry y separación postcommit en un modelo nuevo pequeño. Hook central propuesto junto a `bumpV3OperationalRevision`, enla misma sesión, con allowlist de evento relevante y deduplicación por cambio lógico. No en controladores individuales que omitan assistant uotro canal. El hook no hace HTTP ni entrenamiento en la transacción.

|PRODUCT_CREATED|product CREATE|NuevoSKU/categoría/descriptor|Refresh catálogo, dirty, coldstart ML; esperar evidencia antes de refit con labels|
|PRODUCT_CHANGED|product UPDATE/DEACTIVATE|Cambia descriptor/población|Revisión catalog causal, refresh/inferencia, evaluar elegibilidad defit|
|DAILY_CLOSED|No job de cierre ML durable actual|Parcial→cerrado; habilita labels|Programar catchup por día local independientemente de que llegue otra venta|

Eventos de nombres conceptuales no existentes se implementarán explícitamente; no se tienen por ya cubiertos. Un cambio en nombre/contacto sin efecto sobre inputs no debe crear un entrenamiento. `dataVersion` seguirá aumentando por cambios globales aunque no todos afecten forecast.

### 8.3 Debounce y madurez

Propuesta inicial configurable: quietwindow 60 s, maxwait 5 min desde primer evento relevante, trigger de 20 eventos para adelantar consolidación una vez haya ventana mínima; entrenamiento completo como máximo una vez cada 15 min mientras haya datos elegibles nuevos/correcciones. Son parámetros operativos propuestos, no gates ajustados por resultados de modelo.

20 ventas en 1 min→20 eventos/idempotency keys, un pedido consolidado a última revisión elegible. Un lote puede habilitar más de un job si llega una corrección durante el fit; no se promete entrenamiento exactamente una vez en presencia de crash. Se promete efecto idempotente y una promoción por candidateKey.

Si el hash del dataset elegible no cambió porque solo hay un día parcial, finalizar refresh como `WAITING_LABELS/NO_NEW_ELIGIBLE_DATA` y programar wakeup para próximo cierre. Ese evento sí fue capturado, pero no se afirma reentrenamiento. Labels de h 14 requieren 14 días futuros completos desde su origen; un día nuevo no añade 14 días de etiquetas.

## 9. Actualización, SLA y disponibilidad gratuita

Se distinguen cuatro relojes:

| Estado | Significado | Objetivo académico propuesto |
|---|---|---|
|Dato comercial persistido|Commit operación/ledger/journal/outbox|En la propia transacción antes del ACK|
|Features/estado fresco|Agregados dirty procesados a revisión conocida|≤2 min con backend/coordinador disponibles; inferencia valida revisión actual|
|Modelo entrenado|Fit sobre labels maduros y features versionadas|Iniciar≤5 min tras debounce con worker activo;≤10 min end-to-end como objetivo pendiente de medición|
|Modelo promovido|Gates+artefacto+CAS completos|Versión nueva visible≤30 s después del commit de activación|

Con modelo activo anterior se sirve con features actuales compatibles durantecola/fit/rechazo; `trainedDataVersion` puede ser menor que `sourceDataVersion` y se informa, no se finge fit actual.

Estos objetivos son **condicionales a disponibilidad**, no garantías 24/7 en Free. Render documenta suspensión por 15 min de inactividad, filesystem efímero, ausencia de disco persistente Free y solo ciertos tipos Free; un background worker dedicado no es un recurso Free actual. También hay 750 horas mensuales compartidas y límites de transferencia. [Documentación oficial Free](https://render.com/docs/free).

### 9.1 Ejecución recomendada sin servicios pagos

Primera opción para este escenario académico: **worker Python local en el PC existente**, procesando jobs por HTTPS contra backend durable mientras está encendido, con librerías ya disponibles. No necesita puertos entrantes ni credenciales de DB en el ML cloud: el worker reclama trabajo/exporta datos mediante endpoints internos acotados. Inference ML permanece cloud con artefacto/registro persistentes en Mongo vía backend.

El worker debe ejecutarse como proceso supervisado/tarea del SO en implementación posterior, no depender de una conversación de Codex abierta. El intérprete empaquetado usado en esta auditoría demuestra ejecutabilidad local, pero la ruta estable e instalación operativa del worker deben formalizarse; no se reparó el Python Windows Store ni se instaló nada.

Backend conserva outbox; wakeup postcommit es best effort y su fallo no pierde evento. Poll worker 10–30 s recupera pendientes. Node-RED puede drenar/enviar señales y reutilizar su infraestructura, pero sus timers no despiertan un contenedor que está dormido ni garantizan ejecución cuando se agotan horas. Tras arranque, cualquier worker habilitado debe reconciliar desde cursor y detectar cierres omitidos, no confiar solo en la última notificación del timer.

Alternativa futura: entrenamiento compacto background en el servicio ML actual con un thread/proceso controlado y leases. **No recomendada aún**: faltan benchmark RAM integrado, CPU real y validación de latencia de serving. No añadir un subprocess pesado al runtime 403MiB sin medir. Node-RED actual no incluye un trainer Python configurado; no se presume capacidad por compartir servidor.

Si el requisito exige actualización automática cloud 24/7 sin PC disponible ni tolerancia a suspensión, hay una decisión arquitectónica pendiente: **la infraestructura gratuita actual no demuestra ese SLA**. No se introduce infraestructura pagada ni promesas incompatibles con Free. Modelo apto y disponibilidad son dos condiciones diferentes.

## 10. Concurrencia, idempotencia y revisión

Un coordinador por `(tenant,scenario,domain)` con documento de estado; recipeVersion pertenece al job. Dos recetas distintas también comparten el mismo lock del dominio. El worker tendrá además un único slot de cómputo para evitar entrenamientos simultáneos de distintos dominios o negocios en el mismo equipo.

```json
{
  "state": "IDLE|TRAINING|PENDING_RETRAIN",
  "requestedDataVersion": "<última revisión relevante>",
  "runningDataVersion": "<snapshot fijado al reclamar>",
  "lastObservedDataVersion": "<cursor de journal>",
  "lastFeatureDataVersion": "<refresh aplicado>",
  "lastTrainedDataVersion": "<fuente real del último fit>",
  "lastPromotedDataVersion": "<fuente del bundle activo>",
  "leaseToken": "<aleatorio>",
  "fencingToken": "<contador monotónico>",
  "leaseUntil": "<UTC>",
  "nextEligibleAt": "<UTC>"
}
```

Estado del worker y estado de artifact son conceptos separados. `PENDING_RETRAIN` indica que llegaron cambios durante un fit; no se inicia otro mientras lease está vigente. Lease de 60 s, heartbeat 15 s, deadline global acotado y renovación condicionada al token; valores a validar con mediciones del pipeline. Si se pierden heartbeats, otro claim aumenta fencingToken; un worker antiguo no puede promover ni ACK por compare-and-set con token viejo.

`eventId` derivado de `(businessId,revision,eventOrdinal,eventKey)` o identidad del journal existente; índice único. Una transacción con varios eventos genera dirty por revisión una sola vez, conservando eventIds para auditoría. Revisiones se comparan como int64/BigInt, no lexicográficamente ("100" no es menor que"99").

`jobKey=tenant+recipeVersion+trainingWindow+labelsThrough+featureHash+sourceDataHash`. Una redelivery no regenera job resultado ni artefacto; mismos datos elegibles→mismo candidateKey. Un retry puede recomputar un fit tras crash, pero no duplicar promoción/versión activa: garantía de efecto único, no de computación exactamente una vez.

Si llega revision R+1 mientras se entrena R, se conserva candidate R con su fuente verdadera; `requestedDataVersion` no retrocede al terminar. Puede promoverse R si es posterior al activo, pasa gates y entra en tolerancia de frescura, etiquetando lag; luego se drena pendiente. Candidate viejo que compite contra otro activo ya cambiado exige reevaluación contra ese active y CAS o queda rechazado por conflicto. Ni cursor ni fuente de modelo se deducen del orden de HTTP.

## 11. Registro/versionado mínimo y persistencia

### 11.1 Registro futuro

Campos del bundle: modelId, strategyId, version, tenant/scenario, dataset lineage, createdAt, trainedAt, dataCutoff, labelsThrough, trainingWindow, trainingRowsPorHorizonte, featureVersion, recipeVersion, trainedDataVersion, snapshotHash, trainingDataHash, provenanceMix, sourceCodeSha, libraryVersions, seeds, metricsPorHorizonte, baselineMetrics, activeComparatorVersion, gatesPorHorizonte, resourceMetrics, artifactHashes, triggerReasons, eventRange, status, reasonCodes.

Estados: TRAINING→CANDIDATE→ACTIVE/REJECTED; error técnico→FAILED; previo activo→SUPERSEDED al promover. Los rechazos distinguen NO_NEW_DATA, INSUFFICIENT_EVALUATION, QUALITY_GATE_FAILED, RESOURCE_LIMIT, ARTIFACT_INVALID, LEASE_LOST. NO_NEW_DATA no debe registrar un modelo falsamente entrenado.

Puntero operativo en colección pequeña `MLActiveModel` (nombre propuesto), clave única tenant/scenario/strategy, referencia a bundle completo. No inferir activo como«última fila por fecha». Exactly one significa unicidad del puntero y transición atómica; es válido que antes del primer ML aprobado no exista un bundle activo yla migración siga pendiente.

### 11.2 Persistencia recomendada

Artefactos observados son pequeños: bundles 15KiB–347KiB aproximadamente. Recomendar **Mongo BinData inmutable**, un documento por artefacto/horizonte≤5MiB y metadata separada, usando el driver Mongo ya incluido en Mongoose. No hace falta añadir pymongo a FastAPI: backend almacena y exporta binarios por HTTP interno autenticado, con hash/tamaño y límites independientes del snapshot serving.

Mongo documenta BinData como alternativa para archivos menores a 16MiB. GridFS se evaluó y no es necesario para estos tamaños; si crecieran los artefactos, debes considerar límites y otra receta en una fase posterior. GridFS no admite transacciones multidocumento; no se puede suponer una activación atómica porel solo hecho de usar GridFS. [Fuente oficial Mongo](https://www.mongodb.com/docs/manual/core/gridfs/).

Protocolo: guardar bytes staged, bundle manifest y hashes; verificar descarga y deserialización confiable; luego una transacción pequeña cambia registro/puntero y estados. Un crash antes de commit deja staged no activo; después de commit hay referencias persistidas completas. Nunca editar un archivo activo inplace.

El filesystem de Render es solo cache temporal. Al arrancar, backend resuelve puntero; ML descarga bundle, verifica hash, versiones/tamaño/tenant y realiza predict sanity antes del swap de handle. Cada request fija un handle inmutable; no mezcla versiones si hay cambio durante petición. Conservar bundle previo verificado para rollback. Sin bundle válido, readiness operativo ML false; no caer silenciosamente aHGBM5/MA28. Readiness legacy actual y health liveness tienen alcances distintos y deben conservarse mientras se añade estado del ML activo.

Retención inicial propuesta: activo+dos previos ycomo máximo tres rechazados recientes, con presupuesto de artefactos 50MiB; metadata compacta sin frames, revisar cuota efectiva antes de habilitar. No se leyó capacidad libre At las ni se creó colección. GCsolo artefactos propios huérfanos/terminales fuera de referencias activas, con política recuperable; jamás datos comerciales ni artefactos históricos aprobados del repo. No confiar en disco efímero, Redis Free no durable ocommits automáticos para guardar cada fit.

Joblib/pickle solo de worker propio con identidad autorizada; hash no elimina riesgo de un productor no confiable. Rechazar uploads de usuarios, rutas arbitrarias, manifests sin firma/contexto y versiones sklearn incompatibles antes de cargar. Integridad de hash y autorización de publicador son controles diferentes.
