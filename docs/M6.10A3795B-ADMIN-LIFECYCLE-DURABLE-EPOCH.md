## 1. Contrato administrativo integrado

`createMlTestAdminExecutor(...).execute(req, action)` recibe un contexto de
sesión confiable del backend (`req.user` del middleware authenticate existente),
NO un objeto user deserializado del cliente. No se añadió una API destructiva
pública ni un sistema de roles nuevo.

Acciones permitidas:

| Acción | Precondición/resultado |
| --- | --- |
| CREATE | Admin, escritores pausados por el operador servidor, fuentes sin trabajo en vuelo; checkpoint verificado READY, TEST_ACTIVE |
| STATUS | Admin; lectura sin DDL, inserts ni updates; incluye checkpoint/restore IDs, lease y fallo sanitizado para reanudar |
| RESTORE | Checkpoint READY; reemplazo y verificación; TEST_ACTIVE |
| RESTORE_AND_FINISH | Checkpoint READY; reemplazo y verificación bajo RESTORING; NO_TEST |
| RECOVER_AND_FINISH | FAILED/RESTORING con intención finish persistida y MISMO restoreId; lease vencido; verificar antes de NO_TEST |

No existen FINISH, FORCE_NO_TEST ni ABANDON que cambien el estado directamente.
El body acepta únicamente checkpointId/restoreId UUID y branch NORMAL/OUTLIER/SHIFT
para restauraciones; CREATE y STATUS exigen body vacío. Query vacío. Se rechaza
businessId/scenarioId/resetEpoch/testCycleId tanto en body como query, incluso
si coinciden con el valor autorizado.

Sin sesión: 401. No admin/inactivo/tenant ajeno: 403. Campos inválidos: 400.
Conflictos/lease/estado: 409. Feature flag, certificación o target no válidos:
503. No se devuelven exception messages internos, URI, headers o secrets.

Scope único server-side:

```text
businessId = req.user.businessId = MINIMARKET-PASCO-V3
scenarioId = minimarket-pasco-v3
```

## 2. Cloud preparado pero apagado

`ML_TEST_CLOUD_RESTORE_ENABLED` ausente, false, TRUE u otro valor => deshabilitado.
Únicamente el literal `true` permite pasar la primera puerta, y NO basta por sí
solo. El constructor servidor debe indicar la certificación
`m6.10a3795b-admin-epoch-v1` y un admin real de la sesión.

Se validan las cuatro variables FORECAST_CLOUD_* de destino, Atlas SRV con TLS,
host real de MongoClient, nombre de base, business y scenario autorizados, y que
`db.client` sea exactamente el mismo cliente. Luego se emite una capability
interna ligada a esas instancias mediante WeakMap. JSON/body/query no pueden
crear esa capability ni trasladarla a otro cliente/base.

El core conserva nombres *Local* por compatibilidad. Sin capability válida sigue
rechazando Atlas y bases no desechables. El ejecutor autorizado pasa la capability
al MISMO core para provisión aditiva, captura, verificación y restore. No hay
segundo camino de restore que evite hashes, snapshot, CAS o fencing.

La prueba positiva del destino cloud emplea exclusivamente objetos mock y una
URI ficticia: NO crea MongoClient ni establece conexión. Probar un objeto env
local con flag true no cambia process.env ni configuración cloud.

## 3. Continue frente a finish

```text
RESTORE:
TEST_ACTIVE eN -> RESTORING e(N+1) -> verificar -> TEST_ACTIVE e(N+1)

RESTORE_AND_FINISH:
TEST_ACTIVE eN -> RESTORING e(N+1) -> verificar -> NO_TEST e(N+2)
```

El estado NO_TEST y el último incremento ocurren en una sola actualización CAS
que exige restoreId, owner nonce, epoch y RESTORING. No existe ventana
TEST_ACTIVE intermedia durante finish.

El control NO se borra: conserva resetEpoch, testCycleId, lastCheckpointId,
restoreId/restoreFinish, finalizedAt y epochChangedAt como tombstone durable.
activeCheckpointId pasa a null para permitir otro ciclo autorizado. Se rechaza
overflow de int64. Una reanudación usa el epoch ya adquirido, no lo retrocede.

Repetir un finish completado devuelve el recibo idempotente; NO vuelve a
reemplazar datos. Así una venta NUEVA posterior a finalizar no se borra por
reintentar la solicitud vieja. Se valida checkpoint/restore/branch del recibo.

## 4. FAILED, interrupción y abandono seguro

- Restore interrumpido: control RESTORING hasta caducar lease; reanudar con el
  mismo restoreId y la MISMA intención continue/finish.
- Restore con error capturado: FAILED y lease expirado; no hay salto directo a
  NO_TEST. Una intención finish se recupera con RECOVER_AND_FINISH.
- Falló un continue: primero RESTORE con su restoreId original; luego un
  RESTORE_AND_FINISH NUEVO. No se cambia silenciosamente la intención del ID viejo.
- Captura fallida/incompleta sin checkpoint READY: permanece FAILED o
  CHECKPOINT_CREATING. No se puede restaurar ni abandonar hacia NO_TEST sin una
  fuente certificada. El contrato normal RECHAZA esa salida. Una recuperación de
  emergencia requiere investigación y procedimiento autorizado separado; NO se
  implementa un bypass para desbloquear producción sin prueba de integridad.

Esta última limitación es intencional y debe explicarse antes de iniciar la
prueba: una captura fallida puede requerir mantener la demo en mantenimiento.
No se promete un desbloqueo automático ni una reconstrucción desde chunks
incompletos. La prueba local verifica ese bloqueo y el fallo auditado.

## 5. Identidad de trabajo durable

La identidad serializable es estrictamente:

```json
{"resetEpoch":"4","testCycleId":"<uuid>","present":true}
```

Se compara contra Mongo antes de entrar a un trabajo recibido con token. Los
tokens viejos se rechazan con STALE_TEST_EPOCH también en NO_TEST, no solamente
por el estado TEST_ACTIVE. En una transacción fresca NO_TEST también se escribe
el control como fence, conservando el conflicto real con un reset concurrente.

Persistencia:

- ForecastMlUpdateState.manualTestEpoch: identidad de la solicitud manual;
- ForecastMlUpdateState.claimedTestEpoch: identidad del claim del coordinator;
- InventoryAlertOutboxEvent.testEpoch y InventoryAlertChannelDelivery.testEpoch:
  identidad de la reclamación de entrega;
- dispatch GitHub: input testEpoch emitido por el backend, no por el usuario;
- Actions: FORECAST_TEST_EPOCH pasa por GITHUB_ENV entre binder/check/run.

ACK/fail/worker process exigen token cuando el tenant ya tiene epoch > 0. Un
claim legacy sin token falla cerrado (TEST_EPOCH_REQUIRED), no se trata como
trabajo recién creado. Una reclamación NUEVA recibe el token actual.

Los servicios siguen capturando una identidad actual para operaciones nuevas;
no se bloquean permanentemente las ventas/manual/worker al terminar la prueba.

## 6. Workflows retrasados, incluido schedule

El nuevo paso READ-ONLY `bind-v3-ridge-workflow-epoch.js`, antes de --check, lee
la fecha created_at del run concreto desde GitHub. Verifica repository/runId/event
de esa respuesta, sin imprimir su body/headers/token. Necesita actions:read con
el GITHUB_TOKEN limitado del job, no un secreto nuevo.

Un schedule sin manualRequestKey no tiene token del backend al encolarse. Por
eso no puede limitarse a tomar el epoch al arrancar: si created_at es anterior a
epochChangedAt, se rechaza. Si faltan fecha/metadata requeridas, falla cerrado
con TEST_QUEUE_IDENTITY_REQUIRED. La comparación temporal requiere relojes UTC
correctos; la precisión de segundos de GitHub puede rechazar conservadoramente
un run nuevo en el mismo segundo del cambio. Se puede solicitar otro tras el
corte, no modificar timestamps ni relajar el epoch.

Los manuales además deben traer el token original. Después del primer ciclo,
un manual legacy sin token no se reasigna al epoch actual.

El runner valida nuevamente antes de crear historial/entrenar y conserva la
identidad durante el ciclo. Un reset entre binder/check/run invalida el token.
La denegación previa al ciclo informa que no hubo writes, no una ejecución válida.

La prueba multiproceso despierta un workflow manual viejo DESPUÉS de NO_TEST,
llama al prepare real del runner y obtiene STALE_TEST_EPOCH antes de historial
y Python. Un test offline separado cubre schedule antiguo/nuevo y timestamp
ausente. No se invocó GitHub real ni se entrenó.

## 7. Auditoría

`mltestadminaudits` está fuera de la allowlist y sobrevive al restore. Índice
único aditivo por actionId; nunca syncIndexes/dropIndexes. Se registra STARTED
antes de las mutaciones y SUCCEEDED/FAILED después, con actor, action, scope,
checkpointId, testCycleId, epoch, timestamp y failureCode sanitizado.

En fallos se intenta recoger el control final para registrar el epoch/checkpoint
real, no solamente los anteriores. Si falla una escritura de auditoría después
de la operación, no se declara rollback ficticio; el recibo/control permite
determinar el resultado y repetir idempotentemente.

Denegaciones de autenticación/flag/target emiten un evento de log servidor
estrictamente sanitizado, sin escribir en una base no autorizada. STATUS es
read-only y no inserta eventos/índices. No hay secrets, payloads ni artifacts en
la auditoría.
