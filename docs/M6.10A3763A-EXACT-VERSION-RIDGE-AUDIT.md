# A.3.7.6.3a — Exact-version Ridge audit foundation

## Scope and phase boundary

A.3.7.6.3 is split as authorized in section 23 of its specification. This subphase
implements only exact artifact loading and internal scoring. It does not claim
that attributable impact has been captured or persisted. There is no route,
worker hook, database write, training, promotion, or change to impact.status.

## Exact-version loader

`forecastRidgeAuditModels.createForecastRidgeAuditModels().loadForExecution`
reads a finalized execution by businessId/scenarioId/executionId. It permits only
7/14-day entries and requires a durable confirmed promotion: PROMOTED outcome,
PROMOTED decision, EXECUTION change source, matching candidate/after version,
and training-job reference. At least one horizon must meet those conditions.

Artifact reads use the captured before/after versions, not the current Registry
pointer or a maximum version. Missing versions stay non-comparable. A companion
non-promoted horizon is reusable only if both equal versions were captured with
change source NONE and a non-promotion decision. The returned `promoted` flag
keeps that distinction explicit. It does not invent a new companion model.

The loader validates scope, ACTIVE/SUPERSEDED status, actual byte length/SHA256
using the existing Buffer/Uint8Array/BSON Binary helper, model/recipe/feature
metadata, frozen policy, source hash against stored lineage, historical V3
dataset provenance, recorded dates/revision, and artifact database reference.
The promoted after-version must also match the execution's trainedDataVersion.
Errors never mutate the execution or Registry.

The internal envelope contains allowlisted metadata and base64 artifact bytes.
This is an internal transport, not a history response or a persistence format.
It must never be returned through a public API or stored in impact detail.

## Internal Python audit scorer

`ml.service.v3_ridge_audit` accepts exact expected versions and a caller-supplied
dataset/LiveV3Context. Its shared validator verifies strict JSON schema, bytes,
hash, tenant, scenario, horizon, feature hash/version, recipe, policy, dimensions,
finite coefficients, and serialized model version. ACTIVE and SUPERSEDED are
allowed only through the audit wrapper. The public loader remains ACTIVE-only.

`score_audit_horizon` builds canonical CAUSAL27 features once per SKU from that
one context and calls canonical score_ridge for both artifacts. It does not
fetch another snapshot. Missing evidence yields null predictions with a code;
null is never treated as zero. The product universe is explicit, unique and
bounded to 200 rows; exceeding the bound fails without truncation.

## Deferred subphases

- 3b: capture one operational snapshot with a consistent revision/asOf/closure
  and fingerprint, persist a bounded prediction diff and immutable version-set
  identity, manage PENDING/COMPLETE/PARTIAL/NOT_CAPTURED, CAS and retry ownership.
  If that same snapshot cannot be reconstructed after restart, mark NOT_CAPTURED;
  never compare against a new revision. Existing promotion status must survive
  every impact failure. Integrate only after confirmed worker promotion.
- 3c: pass both forecast sets over that identical snapshot to canonical
  LiveInventorySupplierAdapter, compare nullable fields and rankings over the
  same universe, and persist bounded SKU details. Do not duplicate formulas.

No snapshot is durably pinned by 3a. No deltas, Inventory comparison, impact
recovery or impact persistence are implemented yet. GET paths are unchanged.
