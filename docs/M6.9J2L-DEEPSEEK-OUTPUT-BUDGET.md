# M6.9J.2L — DeepSeek grounded output budget

## Cloud evidence and cause

For “¿Qué productos debería reponer esta semana y por qué?”, the reported
DeepSeek `deepseek-flash` request completed all three READ skills and returned
content, but synthesis was rejected with `OUTPUT_TRUNCATED`: `finish_reason=length`,
input 1822, output 300, total 2122, cache 0, provider latency 2.38 seconds.
Reported cost was USD 0.00045330–0.00090660. The observed 300/300 output and
explicit `length` finish reason confirm that the request cap was reached. This
response did not reach grounded schema or numeric validation, so it neither
confirms nor disproves the prior J.2K numeric-context issue.

The limit had two gates: the handler requested 300 tokens, and provider
configuration defaulted to 300 while rejecting values above 300. Raising only
`DEEPSEEK_MAX_OUTPUT_TOKENS` could not increase the transmitted budget.

## Fixture sizing and selected cap

The JSON fixtures include keys, arrays, evidence references, quotes and punctuation
in the measured size:

| Fixture | JSON chars | UTF-8 bytes | Estimated tokens |
| --- | ---: | ---: | ---: |
| 1 compact observation | 206 | 208 | 70 |
| 2 compact observations | 377 | 381 | 127 |
| 3 compact observations | 548 | 554 | 185 |
| 3 compact observations + 1 limitation | 665 | 671 | 224 |

Estimates use `ceil(UTF-8 JSON bytes / 3)`, the repository's existing sizing
heuristic. This is not DeepSeek tokenizer output or measured API usage. The largest
representative fixture estimates at 224 tokens, leaving at least 276 tokens of
headroom under the chosen cap. Fixture text is deliberately compact and is not a
claim that every future provider response will have this size.

`DEEPSEEK_MAX_OUTPUT_TOKENS` now defaults to **500** and remains configurable up
to a hard ceiling of **600**. The grounded call supplies a bounded request ceiling
of 600; the provider transmits the lower of that ceiling and the validated
environment setting. The example environment is set to 500. No unlimited output is
allowed. Production must set `DEEPSEEK_MAX_OUTPUT_TOKENS=500` in Render in the
later, separately controlled deployment step.

The schema and parser remain exactly J.2H: 1–3 observations, 0–2 limitations,
required evidenceRefs/interpretation/advisoryRecommendation, no nulls or extra
fields. Per-text maximum 900 characters and combined maximum 2160 remain upper
validation barriers. No partial JSON is accepted or repaired.

## Prompt and safety behavior

The prompt now explicitly requests concise Spanish prose, one short direct sentence
for each interpretation based only on its evidenceRefs, and one short actionable
sentence for each advisoryRecommendation. It asks the model not to restate names,
SKU or metrics within an observation, to use `limitations=[]` unless a material
limitation applies, and to avoid introductions and unnecessary methodology.
The existing J.2K prohibition on numbered prose and visible numeric citations stays
in place.

`finish_reason=length` continues to produce `OUTPUT_TRUNCATED` before JSON parsing.
No JSON fragment is accepted or repaired, no retry is scheduled, and there is one
grounded provider call at most. Deterministic and OUT_OF_DOMAIN routing remains
provider-free. WRITE state handling is unchanged. Usage telemetry still records
actual reported tokens; the cap is not treated as consumed tokens.

## Theoretical cost comparison

Using the existing 2026-10-15 DeepSeek Flash tariff, 1822 uncached input tokens,
zero cache hits, and assuming the full output cap is consumed:

| Output cap | Estimated off-peak–peak total | Increase vs 300 |
| ---: | ---: | ---: |
| 300 | USD 0.00045330–0.00090660 | — |
| 450 | USD 0.00054330–0.00108660 | USD 0.00009000–0.00018000 |
| 500 | USD 0.00057330–0.00114660 | USD 0.00012000–0.00024000 |

These are maxima for the stated input/cache assumptions if every output token is
used. Increasing the cap does not mean each response consumes that amount; cost
telemetry continues to use actual provider usage. Pricing data was not changed.

## Local validation and limits

The J.2L tests cover 1/2/3-observation fixtures, three observations plus a
limitation, `stop` and normal validation, a 499-token response under the 500 cap,
`length` with partial JSON, usage preservation, one-call/no-retry behavior, cap
configuration and theoretical cost. Related J.2K/J.2I/J.2H and provider regressions
are run separately. No real DeepSeek/Gemini calls, new tokens, cloud operations or
commercial mutations are part of this phase.

## One later cloud re-test

After the publication checkpoint, deploy the matching backend revision and set
Render `DEEPSEEK_MAX_OUTPUT_TOKENS=500`. Then verify the deployed SHA and health,
and send the previously approved replenishment question exactly once in the
existing authenticated V3 session. Record skill statuses, provider/model, calls,
latency, actual usage/cache/cost, finish reason, content presence/length and grounded
validation result. Do not retry. If the result is truncated or rejected, stop and
report the precise sanitized diagnostic; do not increase the cap or alter grounding
automatically. That one call will be the first evidence after J.2K that reaches
grounded validation.
