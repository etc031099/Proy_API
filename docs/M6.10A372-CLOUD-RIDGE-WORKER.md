# A.3.7.2 — Entrypoint cloud del worker Ridge

La CLI `backend/scripts/run-v3-ridge-worker-cloud.js` prepara el consumo cloud de pendientes mediante el **mismo** `createForecastRidgeTrainingWorker().runEligible(...)`. No configura un scheduler, workflow, endpoint HTTP ni botón manual. No dispone de modo bootstrap, force, 1d, cambio de fechas o alteración de política.

## Configuración explícita

Requiere, sin cargar dotenv ni recurrir a variables locales:

- `FORECAST_CLOUD_MONGO_URI`: URI Atlas dedicada, con credenciales, TLS válido y database explícita.
- `FORECAST_CLOUD_EXPECTED_DATABASE`: database exacta de esa URI.
- `FORECAST_CLOUD_EXPECTED_BUSINESS_ID`: scope esperado de V3.
- `FORECAST_CLOUD_EXPECTED_SCENARIO_ID`: escenario esperado de V3.
- `FORECAST_TRAINING_PYTHON`: executable real que importa las dependencias ML del repositorio; nunca cae a `python` si falta esta variable.

Business y escenario deben coincidir con `backend/src/config/v3Operational.js`. No se aceptan switches para sobrescribirlos. Ni `MONGODB_URI` ni `FORECAST_LOCAL_MONGO_URI` se usan como fallback.

## Modos y preflight

Desde la raíz del repositorio, con las variables ya configuradas en la PowerShell del operador:

```powershell
node .\backend\scripts\run-v3-ridge-worker-cloud.js --check
node .\backend\scripts\run-v3-ridge-worker-cloud.js --status
```

Solo después de revisar ambos resultados, y con autorización para procesar:

```powershell
node .\backend\scripts\run-v3-ridge-worker-cloud.js --run
```

Los tres modos validan URI/scope, conexión, database efectiva, replica set writable primary, revisión V3 y lineage verificados, todas las colecciones e índices declarados de revision/journal/event/state/job/registry/artifact, y ACTIVE exacto para 7d y 14d. No se llama a `init`, `createCollection` ni `createIndexes`: `autoCreate=false` y `autoIndex=false` se establecen antes de importar modelos y también en la conexión. Si faltan colecciones/índices, aborta; su preparación es una operación separada del despliegue.

El preflight usa `FORECAST_TRAINING_PYTHON` con cwd raíz del repositorio para importar `v3_ridge_training`, `v3_live_ridge` y `v3_ridge_policy`, comprobar la política congelada y validar los bytes ACTIVE mediante `load_verified_ridge_artifact`. La conversión BSON → bytes y SHA256 se obtiene del registry productivo; el loader productivo verifica de nuevo metadata, schema, receta, dimensiones y parámetros. Los bytes/base64 viajan internamente por stdin, nunca aparecen en el reporte. No se hace fit, scoring ni export completo del dataset en preflight.

- `--check`: solo preflight, cero writes y cero entrenamiento. Exige ACTIVE existentes porque este entrypoint actualiza modelos, no los inicializa.
- `--status`: agrega lecturas de estados y proyección de elegibilidad, sin ejecutar `refreshWatermarks` ni reclamar trabajo. Cero writes y cero entrenamiento.
- `--run`: solo llama al worker para horizontes cuya proyección sea elegible. El worker vuelve a refrescar y reclamar atómicamente; la lectura previa nunca otorga un claim.

## Elegibilidad y resultados

La proyección de lectura reproduce el avance de watermark y la recuperación de lease vencido de `refreshWatermarks`, y delega la decisión a `coordinator.eligible`. No cambia debounce (15 min), cooldown (24 h), madurez, prioridad de correcciones ni fencing.

El reporte distingue `NO_PENDING_WORK`, `DEBOUNCE_NOT_ELAPSED`, `NOT_MATURE`, `COOLDOWN_ACTIVE`, `LEASE_ACTIVE`, `PREVIOUS_FAILURE_NOT_RETRYABLE`, `ELIGIBLE` y `CLAIM_NOT_ACQUIRED`. Los resultados del worker se traducen a `NO_PROMOTION_INSUFFICIENT_HISTORY`, `CANDIDATE_PROMOTED`, `CANDIDATE_REJECTED` o `FAILED`.

Cada horizonte informa también `promotionReadiness`, calculada por el protocolo Python real. Ser elegible para procesar no equivale a tener las 107 ventanas maduras necesarias para evaluación. El entrypoint no evita el ACK seguro del worker ni crea candidatos artificiales: con historia insuficiente el worker devuelve `NO_PROMOTION_INSUFFICIENT_HISTORY` y conserva ACTIVE. Ese outcome no es un error técnico.

`dataVersion` y los campos `activeModelVersionAtPreflight` / `activeTrainedDataVersionAtPreflight` describen la lectura inicial. `candidateModelVersion` describe el outcome de esa invocación. No se afirma que una lectura inicial sea la revisión finalmente reclamada si llegan nuevas operaciones durante la ejecución.

## Límites y writes

- Procesamiento secuencial 7d/14d; máximo un `runEligible` por horizonte, dos por ciclo.
- Python preflight: 30 s. Python entrenamiento: 120 s por job, mediante el `runPython` existente.
- Ciclo CLI: 8 min; conexión/selección Mongo 10 s y socket 15 s. El watchdog final detiene el proceso con error sanitizado; el lease durable de 5 min y fencing permiten recuperación. No introduce otro lock ni modifica el lease. Un proceso local Python no escribe Mongo directamente.
- `--run` puede actualizar estados/leases/ACK y jobs, persistir/rechazar candidatos y promover mediante registry. Las ventas, journal y revisión no se modifican por esta CLI. No genera eventos comerciales ni modifica datos para volverlos elegibles.
- Mientras se entrena o se rechaza un candidato, ACTIVE sigue sirviendo. Una promoción ya confirmada no se revierte por un posterior fallo de ACK; el worker existente recupera el outcome idempotentemente.
- `writesPerformed=0` es exacto en CHECK/STATUS y cuando RUN no invoca al worker. Tras invocarlo, se informa `writesPerformed=null` y `writesMayHaveOccurred=true`: no se inventa un conteo de operaciones internas; incluso un claim perdido puede haber refrescado estados.

## Salida y validación offline

La CLI devuelve un único JSON resumido, sin URI, passwords, mensajes Mongo/Python crudos, artifacts, payloads comerciales o datos personales. Los códigos externos no reconocidos se reducen a `WORKER_FAILED`. Los logs informativos del coordinator se suprimen en esta CLI para conservar una sola salida. Exit code 1 para fallo; 0 para espera, rechazo de calidad o historia insuficiente.

Pruebas focales: `backend/test/forecastCloudWorker.test.js`, más unitarias existentes de coordinator/worker. Mongo, claims y outcomes del worker se simulan; no certifican una promoción cloud real. La prueba Python opcional usa `FORECAST_WORKER_TEST_PYTHON` **solo en tests**, artifacts sintéticos y el loader real, sin entrenamiento ni conexión cloud. No forma parte de las variables de producción.

No se ejecutó la CLI contra Atlas durante esta fase. La validación real queda en manos del operador empezando por CHECK/STATUS; no se creó workflow ni se hizo deploy.
