# A.3.7.6.2 — Execution history integrated with manual requests and the existing worker

## Real pipeline and integration points

The pipeline is unchanged: operational outbox/state -> coordinator eligibility ->
`runEligible` -> training job -> candidate -> Registry policy/CAS promotion.
`requiredOrigins=107`, debounce, cooldown, maturity, Ridge recipe/features,
approved 7/14 horizons and existing lease/fencing are not changed.

1. `forecastManualUpdateService.request`: the existing snapshot transaction
   writes manual pending State and creates/reuses Execution by manualRequestKey
   in the same Mongo session. It does not claim/start the worker.
2. `createWorkflowDispatcher`: after commit, sends only mode plus the opaque
   manualRequestKey. Dispatch failure leaves the durable request and marks the
   audit DEFERRED where still applicable. A later audit race never invalidates
   acceptance that has already committed.
3. `forecastCloudWorker`: `RUN` begins the scoped execution, then runs the same
   preflight and eligibility, and reports each horizon and final outcome.
4. `forecastRidgeTrainingWorker.process`: job upsert captures the exact Registry
   before version with its existing expected generation. Execution gets the job
   reference in that transaction, then evaluation/candidate results in existing
   save/candidate hooks.
5. Registry promotion hook: writes the promoted job outcome, horizon execution
   result and impact=PENDING in the SAME session as promotion. Failure rolls back
   promotion rather than confirming a pointer without basic audit evidence.
6. Cycle completion computes a truthful global result from both horizon outcomes.

Event remains a signal, State remains current pending/lease authority, Job remains
the training record, Execution remains audit. No second training pipeline exists.

## Identity and correlation

The execution now separates immutable `requestSource` from `triggerSource`
(actual executor). A manual request can therefore remain requestSource=MANUAL
and manualRequestKey=its original key while triggerSource=SCHEDULED or CLI.
Binding occurs only through the domain before RUNNING. The optional unique
GitHub/CLI identities can be attached then; they cannot be arbitrarily replaced.

The GitHub input is NOT business authority. Scope always comes from the checked
cloud environment; an explicit manual key must match durable scoped manualPending
State. A completed/already-running matching request can return as a duplicate
without running again. A forged/non-durable/foreign key cannot claim work.

A schedule or CLI cycle that finds one manual pending request reuses its Execution,
not another execution with the same manual key. A manual request predating this
feature is reconstructed only from actual durable request metadata: its timestamp
must exist; original request revision is unknown, not invented.

GitHub schedule uses SCHEDULED. workflow_dispatch with backend correlation uses
MANUAL. A GitHub operator dispatch without correlation is CLI (not mislabeled
automatic). Repository/runId identify the principal execution; runAttempt is
preserved without another principal row. A previous unfinished GitHub attempt is
marked INTERRUPTED/PARTIAL only for a higher attempt and only without a live
coordinator lease. A stale audit adapter cannot finalize a newer attempt.

Outside GitHub, RUN now requires an explicit stable invocation key:

```powershell
# Set once per logical operation; preserve this value for recovery/retry.
$env:FORECAST_WORKER_INVOCATION_KEY = [guid]::NewGuid().ToString()
node .\backend\scripts\run-v3-ridge-worker-cloud.js --run
```

Do not regenerate the key to recover the same operation. A recorded CLI
interruption can be resumed under the same identity, retaining the prior attempt.
Repeated terminal runs return the existing execution rather than claiming work.
CHECK/STATUS neither require this identity nor create history/claims/indexes.

## Evidence and outcomes

- Preflight captures observed revision, closed boundary and pending state.
- Exact availableOrigins are taken from existing preflight/trainer protocol
  evidence. Unknown stays null, required stays 107. Per-horizon values are not
  collapsed into an invented common count.
- Each job records the before version before it could promote; generation CAS
  remains authoritative. After is read from the actual Registry in the transaction
  or after a non-training decision; no max(version) lookup is used.
- Horizon evaluated revision/closure are recorded separately. If horizons use
  different revisions, the global evaluated revision is null rather than a false
  common revision.
- External Registry changes can be recorded with activeChangeSource=EXTERNAL;
  they do not turn a failed/non-promoting execution into its own promotion.
- Reusing an already-final training job links its real result but is explicitly
  REUSED_TRAINING_RESULT, not a claim of a new promotion in that attempt.
- Both promoted -> PROMOTED. Both evaluated without promotion ->
  EVALUATED_NO_PROMOTION. Both no work -> NO_PENDING_WORK. Ineligible-only outcomes
  -> NOT_ELIGIBLE. Mixed/completed-plus-failed -> PARTIAL. Both technical failures
  -> FAILED. An observed interrupted cycle -> INTERRUPTED or PARTIAL if a horizon
  already promoted.
- A confirmed horizon promotion sets impact=PENDING atomically. Without promotion,
  impact is NOT_APPLICABLE. There are no prediction/Inventory SKU calculations.

## Index provisioning / enabling safely

Backend connection options previously did not override Mongoose autoIndex/default
autoCreate; only Event/State init was explicitly awaited in app startup. The new
startup step explicitly calls additive createCollection/createIndexes for Execution,
then verifies named keys, uniqueness and partial filters. It never calls syncIndexes
or drops old indexes. Failure prevents the manual transaction through the same
read-only index gate; no request is accepted without required history indexes.

The cloud CLI sets autoCreate=false/autoIndex=false before importing models.
Preflight now verifies Execution along with the other seven models, without
provisioning. RUN also verifies history indexes before its first history write.

Deployment sequence for a later authorized phase:
1. Publish matching backend/runner/workflow code.
2. Deploy backend, let the additive startup provisioning complete, and verify the
   history indexes. Do not start the new worker against an unprovisioned collection.
3. Run the existing read-only worker CHECK; it must accept all eight schemas/indexes.
4. Only then enable/run the new RUN integration and send correlated manual requests.

No such operation is executed in this implementation phase. An older workflow
rejecting the new input makes dispatch DEFERRED; it does not erase the request.

## Explicit limits / failure windows

- SIGTERM/SIGINT/cycle watchdog try to persist interruption with a bounded 2-second
  exit allowance. SIGKILL, host loss or database outage cannot guarantee that write.
- A hard kill can leave global RUNNING even after a committed horizon promotion;
  the horizon and impact metadata remain durable because they committed with Registry.
  Higher GitHub attempts recover only after lease protection permits it. A hard-killed
  CLI row without a recorded interruption is not silently stolen: explicit future
  recovery is needed. There is no new recovery scheduler or lease implementation.
- No audit can record a connection failure that occurs before it can access Mongo.
  Existing manual rows remain durable; errors before any durable RUN row are only
  in the sanitized CLI/GitHub result. A CHECK failure that prevents RUN remains
  read-only and does not create an execution merely for the check.
- A competing workflow encountering an already-owned manual request returns a
  duplicate/no-op; it does not replace the actual executor's GitHub identity.
- This phase has no historical backfill, public history API or frontend.

## Offline validation

Tests use the real domain/schema, actual worker and coordinator decision functions,
injected fake training responses, and rollback-capable transaction/Registry fakes.
They do not call Python fit, GitHub, Atlas, bootstrap or production promotion.
They verify correlation, source, idempotency, unknown origins, before/after,
transaction hooks/rollback, mixed results, stale attempts and unchanged status.
Index provisioning/verification is tested with index metadata fakes. This is not
certification against a running Mongo replica set; live index/transaction checks
remain required before enabling production, with separate authorization.
