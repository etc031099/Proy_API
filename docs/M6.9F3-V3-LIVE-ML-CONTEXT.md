# M6.9F.3 — V3 Live ML Context Ingestion

Status: local implementation; LIVE analytics remain disabled pending M6.9F.4.

## Contract and routing

The existing authenticated `POST /v3/intelligence/{domain}` routes accept the additive top-level `dataMode` field (`HISTORICAL` by default) and optional `operationalSnapshot`. Existing domain `mode` values (`summary`, `detail`, `rank`, etc.) keep their prior meaning. This naming is necessary to preserve the established request contract.

- `HISTORICAL`: snapshot must be absent and `context.asOfDate` must stay within the frozen M6.3 cutoff. Existing engine calls and response bodies are unchanged.
- `LIVE`: `context.asOfDate` must be after 2026-10-12 and equal the snapshot boundary; a snapshot is mandatory. The request is authenticated with the existing `X-ML-Service-Secret` header. The public API returns `LIVE_ANALYTICS_NOT_READY` (501) after successful ingestion until F.4 wires calculations. It never answers a post-cutoff query from the historical engine.
- Request body limit for V3 routes: 1.5 MiB. It is enforced before JSON parsing; no truncation is performed.

## Typed snapshot and validation

`ml/service/v3_schemas.py` defines strict Pydantic models for snapshot metadata/counts, catalog changes and product/contact projections, sale/purchase headers and lines, transaction changes, stock states, and closed product-days. Extra fields are rejected. The contract binds business `MINIMARKET-PASCO-V3`, scenario `minimarket-pasco-v3`, dataset version/hash, cutoff 2026-10-12, delta start 2026-10-13, and `America/Lima`.

`ml/service/v3_live_context.py` enforces completeness, dataVersion int64 range, size/counts/coverage, as-of/capture/watermark boundaries, post-cutoff timestamps, no future rows, unique event/stable/line keys, references to base or snapshot entities, unique SKU ownership, ledger stock coverage, complete closed-day product/date coverage, and sale-to-closed-day reconciliation. Snapshot hash is SHA-256 over UTF-8 compact canonical JSON matching the backend rule: keys sorted, arrays recursively canonicalized, and `capturedAtUtc`, `snapshotHash`, and `payloadBytes` excluded (the latter is calculated after signing). A golden test checks cross-language hash parity. Hash is integrity checking, not authentication; auth remains mandatory. Snapshot Pydantic models are frozen after validation.

## Historical base + LIVE overlay

The canonical package and M6.5/M6.7 artifacts stay read-only. `LiveV3Context` holds references to the frozen base plus an immutable Pydantic snapshot and mapping-proxy overlays. It does not deep-copy the dataset, rewrite package files, or recalculate an engine.

- Products: CREATE adds only to the overlay; UPDATE/DEACTIVATE replaces the as-of projection while the historical record remains unchanged. Duplicate SKU identities and bad prior identity are rejected.
- Sales: base sales remain separately addressable; completed post-cutoff sales are exposed as an iterator. Cancellation events are applied as an overlay, never by editing base rows.
- Purchases: pending/completed/receipt evidence and line costs remain explicit. Pending purchase quantities do not alter `stockStates`. Receipt quantities are accumulated separately by purchase line.
- Inventory: stock lookup comes only from backend `MONGO_LEDGER` stockStates; ML does not sum a second ledger.
- Customers/suppliers/offers: base maps are extended/overridden from typed catalog changes; new suppliers do not receive invented historical performance.
- Closed sales days: only complete dates through `observationsClosedThrough` are accepted. The current partial day remains outside this table.
- Forecast: new SKU status is surfaced as `COLD_START`; no fallback MA28 is calculated in F.3.
- Market Basket: remains frozen at `MINIMARKET-PASCO-V3-MBA-v1`, cutoff 2026-10-12; LIVE tickets are never added to the artifact.
- Freshness helpers expose LIVE `asOfDate`, `dataThroughUtc`, `dataVersion`, historical cutoff, and context-engine version; MBA exposes its own frozen cutoff/version.

## Cache and worker isolation

The worker-local bounded context store keys by business/scenario, historical dataset version/hash, snapshot version, `dataVersion`, `snapshotHash`, `asOfDate`, closed-observation boundary, engine version, and normalized period/filter slots. Same snapshot reuses its immutable context. Revision N+1 receives a distinct key and context; no Redis, push invalidation, auth caching, or cross-worker correctness dependency is used. A changed hash for the same dataVersion/as-of/closed-day boundary is rejected as `SNAPSHOT_VERSION_MISMATCH`. Store publication and LRU mutation are protected by an `RLock`.

## Errors and F.4 boundary

Stable ingestion errors include `LIVE_SNAPSHOT_REQUIRED` (422), `LIVE_SNAPSHOT_INVALID` / `SNAPSHOT_HASH_MISMATCH` (422), `TENANT_MISMATCH` (403), `SNAPSHOT_VERSION_MISMATCH` (409), `POST_CUTOFF_DATA_INVALID` (422), `LIVE_SNAPSHOT_TOO_LARGE` (413), and `LIVE_ANALYTICS_NOT_READY` (501). Invalid/partial snapshots are never cached or served.

F.4 must adapt the existing M6.6/M6.8 engines to these contexts, add revisioned derived-result cache keys, calculate 28 closed demand observations through D-1, and preserve cold-start/unknown-cost/availability semantics. Explicitly unresolved before such a calculation is safe: the backend snapshot currently records cancellation keys as Mongo transaction IDs, while the frozen ML base addresses transactions by canonical sale/purchase codes. The current validator intentionally rejects unmatched transaction changes rather than silently missing a historical cancellation. F.4 requires a verified stable-key bridge (and closed-day cancellation reconciliation) before supporting cancellation of frozen transactions. The current backend contract also emits no `RECEIVE` events yet; its schema/overlay is prepared, but actual delayed receipt analytics remain unsupported.

## Tests and local measurement

`ml/tests/test_m6_9f3_live_context.py` covers typed snapshot parsing, deterministic hash, overlay immutability, new entities, stock authority, pending purchase semantics, revision/cache isolation, same-version hash conflict, pre-cutoff/future rejection, cross-tenant/reference rejection, closed-day coverage, and API auth/missing-snapshot/oversize/fail-closed behavior. Existing M6.9B historical routes remain the regression baseline; no benchmark TEST is rerun.

Performance is measured with small synthetic snapshots only (parse/validation, overlay construction, and RSS delta), not with real operational data. LIVE engines, forecast semantics, assistant date switching, page integration, cloud deployment, Atlas, and real-data insertion are explicitly outside F.3.
