# M6.9F.2 — Backend revision and operational snapshot

Status: **backend implementation prepared; LIVE remains gated**. This phase does not expose the snapshot to ML, change V3 date routing, write cloud data, or enable live serving. It implements the Mongo models, transactional hooks, explicit bootstrap gate, and internal builder for M6.9F.3.

## Tenant and historical lineage

`resolveV3OperationalScenario(businessId)` accepts only the server-derived `MINIMARKET-PASCO-V3` and requires a completed `HistoricalScenario` whose scenario ID, dataset version, canonical source SHA-256, reference date, and timezone match the approved M6.9F.1 lineage. No request body field can select a tenant or scenario. Other businesses return no revision changes; an attempt to build a V3 snapshot for another business is rejected.

## Revision, bootstrap, and ownership

`V3OperationalRevision` has one document per business (`_id=businessId`) and stores `revision` as Mongoose `BigInt`, persisted as BSON int64. A missing row represents conceptual revision **0**; it does not create a synthetic historical event. The first confirmed analytical WRITE after a verified bootstrap increments to 1. The counter is checked against signed int64 exhaustion and serialized as a decimal string.

Bootstrap is explicit through `bootstrapV3OperationalRevision`; ordinary reads and application startup do not write it. The helper checks for post-cutoff transactions not marked as canonical imports, non-import ledger movements, and new non-scenario products/contacts. Since imported V3 product/contact timestamps cannot establish whether their analytical fields were later edited, the helper requires an explicit `attestNoUnjournaledBaseCatalogChanges: true` acknowledgement when imported base catalog records exist. Without that acknowledgement, or when any unjournaled operational rows are found, it fails closed. This phase did not run bootstrap against local or cloud business data.

`V3OperationalChange` is append-only by convention and has unique `(businessId, revision, eventOrdinal)` identity. Each event is written with its operation and the revision in the same Mongo session. Catalogue changes carry bounded analytical `before` and `after` projections; transaction create/cancel events carry only required sale/purchase fields. No credentials, email, phone, address, auth internals, or arbitrary Mongo documents enter the snapshot.

The single revision owner is the service boundary for a logical operation, not every stock movement or side effect. PendingAction’s outer transaction remains the owner for assistant writes. Preview, reads, cancellations of pending actions, non-V3 tenants, no-op stock adjustments, and non-analytical contact edits do not increment.

| Confirmed operation | Revision/event | Transaction behavior |
|---|---|---|
| Sale create | One bump; sale projection | `writeTransaction`, including direct CRUD and confirmed assistant action |
| Purchase create | One bump; purchase projection | Same shared transaction service; current purchase is immediate receipt |
| Sale/purchase cancellation | One bump; `CANCEL` event | Same cancellation transaction as reversing ledger movements |
| Purchase receipt | No hook: no operational receipt route exists | F.2 does not invent one; future `RECEIVE` requires a real atomic path |
| Purchase cancellation | Covered by transaction cancellation hook | Reverses ledger and records one cancel event |
| Stock adjustment/opening | One bump for a non-zero API adjustment; opening with product create shares one revision | Movement remains stock source of truth; no duplicate per movement |
| Product create/update/deactivate | One bump only when the analytics projection changes; offer and preferred-supplier edits are included | Product controller / shared creation service |
| Customer/supplier create/update/deactivate | One bump only when name, type, active state, or stable analytical identity changes | Contact controller; balance, contact details, and notes are excluded |
| Supplier offer create/update | Included in product projection change | Embedded `Product.supplierPrices`; no separate offers collection |
| Alerts, preferences, login, reads | No bump | Not snapshot analytics inputs in F.2 |

V3 transactions use majority write concern. V1/V2 keep their existing transaction behavior. Repeated PendingAction confirmation is already idempotent in the owning action repository; F.2 adds no independent retry or action execution path. Transaction conflicts fail closed rather than retrying business writes.

## Snapshot v1

`buildV3OperationalSnapshot({ businessId, asOfDate, now, minimumDataVersion })` is an internal backend service for F.3. It is not yet wired to an HTTP or ML endpoint.

- `asOfDate <= 2026-10-12`: returns `mode: HISTORICAL` with no snapshot, leaving the existing historical serving path unchanged.
- `asOfDate > 2026-10-12`: returns a V3 operational snapshot only after verified bootstrap and scenario validation.
- Future dates and invalid calendar days are rejected. Day boundaries use America/Lima; delta begins at `2026-10-13T05:00:00.000Z`.
- Today is captured only through `capturedAtUtc`; earlier LIVE dates are read through the Lima day’s end.
- `observationsClosedThrough = min(asOfDate - 1 day, operationalDate - 1 day)`. The current partial day is not emitted as closed forecast evidence.
- Sales and purchases are projected from the append-only operation journal, so mutable current transaction status cannot rewrite a prior as-of snapshot. Cancellation events apply only from their effective time.
- Purchase records use `IMMEDIATE_PURCHASE` because the current purchase flow immediately increases stock. Pending is represented as `NONE`; no receipt, promise, or punctuality is invented.
- Stock is bulk-reconstructed from `InventoryMovement` through the requested cutoff. Current-date totals reconcile with `Product.stock`; mismatch, negative stock, or a foreign product reference is an explicit error.
- New catalog rows are represented by revisioned projections, not a full resend of the canonical 80-product base. Stable V3 keys are preserved; operational entities without stable codes receive `OP-P-`, `OP-C-`, or `OP-S-` keys.
- `closedSalesDays` contains explicit zero rows only for fully covered Lima days and visible products. Availability remains `UNKNOWN`; no available-hours evidence is fabricated.

The payload metadata includes schema/contract version, authenticated tenant/scenario, historical lineage, cutoff/delta start, timezone, operational/as-of dates, captured/data-through watermarks, closed-through date, decimal `dataVersion`, completeness, counts, cost coverage, availability coverage, logical hash, and UTF-8 payload byte count. Sale-line cost is `UNKNOWN` if the source transaction did not capture it. A configured current product cost is not substituted for historical cost-at-sale.

## Consistency, hash, limits, and privacy

The builder uses a causal Mongo session. It reads a majority revision floor on primary, then starts a read-only snapshot transaction and serially reads scenario, revision, journal, catalog, and ledger. The snapshot must be at least the requested floor. A below-floor/transient snapshot is discarded and retried once; a second failure returns a controlled consistency error. No parallel queries share a transactional session, no partial result is returned, and the builder does not mutate the business database.

Canonical SHA-256 sorts object keys and unordered arrays, includes semantic data/version/as-of boundaries, and excludes only non-semantic capture time. The resulting response has a strict 1.5 MiB UTF-8 limit. Counts are bounded (5,000 products; 30,000 revision events; 100,000 ledger movements; 30,000 closed product-day rows). Limits fail with explicit 413 errors; data is never silently truncated. Query errors, incomplete extraction, lineage mismatch, unverified bootstrap, and ledger inconsistency fail closed.

## Tests and current limitations

Focal unit tests cover the int64 schema/index, Lima boundaries, canonical hash stability, sale/purchase projection, missing cost, pre-cutoff/future exclusion, as-of cancellation, closed-day zeros/partial-day exclusion, and payload rejection. A separate local replica-set integration test covers bootstrap at zero, committed increment, rollback of document+revision+event, non-V3 isolation, and end-to-end snapshot assembly. It requires `MONGODB_TEST_URI` pointing to an empty dedicated local `*_test` replica-set database; it is not run against Atlas or production.

Known blockers handed to F.3/F.7:

- No local replica-set URI was configured for this implementation run, so real transaction/snapshot semantics and indexes still require the controlled integration gate.
- No actual business-data bootstrap/attestation was performed. LIVE is intentionally unavailable until the dedicated audit/authorized bootstrap is completed.
- There is no deferred purchase receipt workflow. F.2 therefore cannot produce `RECEIVE` events or received quantities.
- Ordinary sale writes currently do not persist cost-at-sale; sale COGS coverage is explicitly unknown rather than fabricated.
- Availability hours/stockout exposure are not captured by the existing backend.
- No snapshot consumption, endpoint, ML merge, forecast update, or operational-date switch is included; those are F.3 and later.
- Direct database edits that bypass backend write hooks are not revisioned and are unsupported for LIVE freshness.

## F.3 contract handoff

F.3 may consume only a returned `mode: LIVE` snapshot, validate schema/hash/size/tenant/scenario lineage, merge the operational delta over the immutable historical base, and preserve the historical path byte-for-byte. It must not bypass `bootstrapStatus=VERIFIED`, infer missing data as zero, treat unknown cost/availability as known, or enable a live clock before validating the merged context.
