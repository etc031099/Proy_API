# M6.9F.4B — V3 live backend contracts

## Scope

This phase adds backend persistence contracts needed by future live analytics adapters. It does not add a public receive route, UI, ML adapter/schema, or new purchase workflow. Existing immediate purchases remain unchanged. Only one full first receipt of a pending deferred purchase is supported; partial receipts are explicitly unsupported.

## RECEIVE

`receiveV3Purchase` is an internal service contract. The caller supplies the authenticated V3 `businessId`, purchase document id, stable `receiptKey`, receipt timestamp, and optionally observed per-line costs. It accepts only a tenant-owned purchase with verifiable product/supplier ownership and either:

- a frozen V3 pending purchase with matching `stableCode`, `stableLineKey`, canonical product/SKU, ordered quantity, and zero previously received quantity; or
- a post-cutoff deferred purchase explicitly marked `purchaseLifecycle.fulfillmentMode = DEFERRED`.

In one Mongo replica-set transaction the service appends one purchase `InventoryMovement` per line using `applyStockChange`, advances the purchase to `completed`, records `purchaseLifecycle.receiptState = COMPLETE` and the receipt lines, appends one `V3OperationalChange` with operation `RECEIVE`, and bumps `dataVersion` exactly once. Any failure aborts all writes. The movement ledger stays append-only. Increasing on-hand stock and completing the purchase removes it from pending/incoming calculations; no second incoming quantity is emitted by the receipt event.

The idempotency key is unique per business in both the purchase lifecycle and operational journal indexes. The real Mongo integration verifies the created unique partial indexes and their key fields/filter. Replaying the same key, purchase, and cost evidence returns the original revision without stock, event, or revision changes. Reusing the key for another purchase or different cost evidence returns `RECEIPT_ALREADY_APPLIED`. The request fingerprint covers normalized cost evidence; the timestamp is deliberately not the identity.

Cost fields are integer cents and nullable. Provenance is one of `OBSERVED_RECEIPT_COST`, `ORDER_COST`, `HISTORICAL_COST`, or `UNAVAILABLE`; `PRODUCT_CURRENT_COST` is a reserved contract value and is never selected as a fallback by this service. Unavailable values remain null, not zero. A movement with unavailable provenance cannot carry fabricated numeric cost fields; known purchase movement valuation must agree with quantity × unit cost. Cost currency must match the purchase currency.

## Cancellation references

The existing transaction cancellation flow keeps its inventory compensation behavior: it appends cancellation movements and never edits/deletes historical movements. For a V3 frozen sale, `recordV3Transaction(..., operation: CANCEL)` records a reference event, not synthetic reversal sale lines. The original frozen record stays unchanged. Its identity must resolve exactly through the tenant-owned `Transaction` document, approved `scenarioId`, `stableCode`, canonical source/date, and every `stableLineKey`; product identity and quantities are checked against canonical lines. Fuzzy matching by amount, customer, approximate date, description, or SKU alone is not used.

Live transactions use the same event shape with an internal transaction id as `transactionKey`. Downstream consumers can apply the CANCEL event to derive effective `ACTIVE`/`CANCELLED` state and reverse revenue, units, tickets, spend, frequency, and preferences without counting a synthetic reversal as another sale. Credit-sale restrictions and existing API state transitions remain in force.

## Snapshot compatibility and hashing

The F.2 snapshot builder resolves transaction references in bulk, tenant-scoped, and emits public stable keys instead of Mongo ids for cancellation/receipt transaction identity. RECEIVE lines contain stable line key, SKU/product key, ordered and received quantities, nullable unit cost, cost provenance, and currency. CANCEL contains the original stable transaction code and affected stable line keys. Semantically meaningful fields participate in the existing canonical logical hash; repeated identical state yields the same hash and a new journal event/revision changes it.

Snapshots remain contract v1 when they contain only legacy v1 information. The builder marks contract/snapshot version v2 when it includes a v2 deferred purchase, RECEIVE, or v2 cancellation. The existing 1.5 MiB payload ceiling and `dataVersion` consistency behavior are preserved. No F.3 ML schema or serving code changed in this phase; its current live snapshot contract does not yet consume the full v2 receipt/cancellation evidence. That is a planned F.4D adapter responsibility, not a deploy-ready ML change.

## Validation

- F.4B focused unit tests: 3/3 passed.
- F.4B real Mongo integration: 5/5 passed on a local `rs0` PRIMARY using a random, dedicated `inventory_v3_f4b_<uuid>_test` database. It covered post-cutoff cancellation reference/stock compensation, full historical receipt, one revision bump, cost evidence, idempotent replay and mismatched replay rejection, deterministic snapshot hash, wrong-tenant denial, and rollback after a forced journal failure. The runner drops only its generated test database in `finally` and disconnects.
- The integration does not target `inventory_billing`, Atlas, or any live business data.

The F.2 integration test uses the fixed database name `inventory_billing_m6_9f2_test` and its cleanup drops that whole database. It must only be run after verifying that exact database is an empty disposable test database. This phase's random-database integration independently exercises the snapshot read path and cancellation/receipt mappings.

## F.4C/F.4D handoff

F.4C can use the snapshot v2 contract to apply effective cancellation state to analytical domains. F.4D must extend the strict ML snapshot schema/merge logic for historical and deferred RECEIVE evidence, stable transaction/line references, and nullable cost provenance before these v2 snapshots are sent to ML. Until then, keep the live analytics adapter path from consuming v2 receipt/cancellation snapshots. Partial receipt support, public endpoints/UI, and operational workflow changes are out of scope.
