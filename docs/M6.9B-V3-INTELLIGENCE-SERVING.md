# M6.9B — V3 Intelligence Serving

## Status and source boundary

This phase adds an additive FastAPI serving layer. It does not change the assistant, backend routing, frontend, V1/V2 contracts, or cloud configuration. Analytics are computed by the approved Python M6.5–M6.8 engines; the endpoints are adapters, not duplicate implementations.

The local runtime binds one allowlisted pair: business `MINIMARKET-PASCO-V3`, scenario `minimarket-pasco-v3`, dataset SHA `a90b913b6ee83174165b39eaab1526525b3aacc53cae1abe6c3f5a54a469cac8`. The request cannot supply a Mongo URI, select another tenant, or broaden this binding. The response labels its source `CANONICAL_V3_BUNDLE`.

The serving package is immutable and cutoff-bounded. It loads the canonical local V3 generated package, verified M6.5 moving-average manifest and (when available) the approved M6.7 artifact. The M6.7 artifact is hash/version/scenario/cutoff checked once at startup; serving does not import `mlxtend`, mine baskets, benchmark, train, or retune. The M6.8 adapters reuse the loaded dataset and operational indexes. No result cache is added; cached indexes are process-local, not conversation data or cross-tenant response caches.

Local Mongo was checked read-only through the existing loopback-only M6.6A reader. Its marker and counts were V3/80 products/2,155 purchases/40,445 movements. The served inventory projection was compared against a fresh Mongo-derived M6.6 snapshot: 80 SKUs, zero differences across stock aggregates, demand, coverage, policy, risk, classification, reorder decision, recommended quantity, and supplier dependency. The full snapshot has ten differences, all inside per-order `pendingOrders` details (`purchaseCode`, expected date, and order-level quantity allocation); those internal order records are intentionally excluded from the serving contract. Atlas was not contacted.

## Routes and request contract

All POST routes reuse the existing `X-ML-Service-Secret` / `ML_SERVICE_SECRET` internal authentication. The secret is not returned or logged. Missing/wrong auth is 401/403. Every request has `requestId` and a strict `context` containing `businessId`, `scenarioId`, optional `datasetVersion`/`datasetSha256`, `timezone`, and optional `asOfDate`. Extra fields are rejected. The runtime checks the business/scenario/version/hash/timezone against its single server-owned V3 binding; a body cannot select arbitrary business data. `asOfDate` defaults to `2026-10-12` and may only narrow to the approved history, never exceed the reference date. All dates use `America/Lima`; there is no business-semantic `datetime.now()`.

Page size is 1–20 (default 5), offset is bounded to 10,000, and entity batches are bounded to 80; Business Health observations are separately capped at 5. Unknown entity identifiers do not fall back to a global query. Detail requests require a stable SKU/code. V3 routes are:

| Route | Main request modes | Engine / contract behavior |
|---|---|---|
| `POST /v3/intelligence/business` | summary, compare, rank; inclusive period and optional category/subcategory/SKU filters | M6.8 Business Intelligence; revenue, COGS, gross margin, units, tickets, average ticket, comparisons and requested rankings |
| `POST /v3/intelligence/inventory` | summary, detail, rank, recommendations; SKU batch, risk/ABC/XYZ/flag filters | M6.6 Inventory Intelligence using M6.5 `MOVING_AVERAGE_28`, 1/7/14-day horizons; no purchase/write action |
| `POST /v3/intelligence/forecast` | detail, compare, rank, summary; SKU batch and horizon | M6.5C frozen `MOVING_AVERAGE_28`; only 1/7/14 days are approved |
| `POST /v3/intelligence/cross-sell` | SKU recommendations, category rules, summary | Read-only M6.7 frozen artifact; output explicitly describes co-occurrence, not causality |
| `POST /v3/intelligence/customers` | detail, rank, segment, preferences/activity, optional exact period | M6.8 Customer Intelligence; projected fields omit email, phone and synthetic-profile audit |
| `POST /v3/intelligence/suppliers` | detail, rank, summary, alternatives, dependency | M6.8 Supplier Intelligence; no arbitrary “best supplier score” |
| `POST /v3/intelligence/health` | compact domain composition and optional period | M6.8 health composed with M6.6/M6.7; `healthScore` remains null |

Success uses a versioned `{requestId,status,data,metadata}` envelope. Metadata includes scenario, as-of date, timezone, dataset version/SHA, contract/engine versions, source, duration and process-local p50. The response is JSON-normalized with non-finite numbers rejected. Inventory omits order-level purchase codes and pending-order records. Customer output is explicitly projected to avoid contact fields.

`GET /v3/intelligence/health` distinguishes service alive, V1 ready, V3 readiness, per-domain readiness, and load/RSS metrics. `GET /v3/intelligence/ready` reports V3 package readiness without changing existing `/health` or `/ready` semantics. Missing optional MBA artifact leaves unrelated domains available; cross-sell returns a `PARTIAL` result and health identifies the missing domain. Forecast/inventory remain unavailable if their approved baseline manifest is missing.

## Stable errors

| HTTP | Code | Meaning |
|---:|---|---|
| 400 | `INVALID_REQUEST` | Pydantic/schema failure or unsafe pagination |
| 401 / 403 | authentication codes | Missing or incorrect internal caller secret |
| 403 | `TENANT_MISMATCH` | Business is outside the fixed V3 binding |
| 404 | `PRODUCT_NOT_FOUND`, `CUSTOMER_NOT_FOUND`, `SUPPLIER_NOT_FOUND` | Stable entity identifier absent |
| 409 | `AMBIGUOUS_ENTITY` | A required stable entity identifier is missing |
| 409 / 422 | `SCENARIO_NOT_SUPPORTED` | Scenario or dataset lineage is not approved |
| 422 | `INVALID_PERIOD`, `UNSUPPORTED_HORIZON`, `INSUFFICIENT_HISTORY` | Date range, unapproved 28-day horizon, or inadequate history |
| 503 | `ARTIFACT_UNAVAILABLE` | Required package/engine artifact unavailable or invalid |
| 500 | `INTERNAL_SERVICE_ERROR` | Sanitized unexpected engine failure; raw exception is not returned |

V3 failures do not alter the old V1 health/readiness/prediction schema. Startup failure of V3 is recorded with a sanitized code and does not prevent V1 startup.

## Loading, memory, latency, and packaging

Startup verifies the generated package manifest and file hashes, then loads the V3 dataset once. It validates the existing frozen forecast strategy manifest and market-basket artifact lineage, then reuses M6.8 records/indexes and engine objects. No request accepts credentials or a datasource URI. No new result cache is enabled before measurement.

The V3 dataset validator invokes the repository’s canonical Node generator to verify the configuration SHA, and M6.8 static-definition loading uses the same generator. Therefore a future ML deployment must package the approved V3 data/artifacts and the compatible Node canonicalizer/runtime. These files are intentionally ignored/not committed as source data; **cloud packaging/lineage is a stop gate for M6.9E/deployment**, not something this local-only phase claims to have solved.

Health is the only path that composes all domains; ordinary routes call only their required domain except supplier’s existing inventory dependency. Business summaries return the requested KPIs/trends/margins without returning all product rankings; rankings are returned only in rank mode. The outer envelope and nested response JSON tree are Pydantic-validated and reject non-JSON/non-finite values.

## Validation and parity

M6.9B tests exercise route schemas, internal auth, tenant/scenario/hash binding, date/future-cutoff guards, unsupported 28-day horizon, entity errors, output limits, artifact-unavailable/partial behavior, and V1 readiness compatibility. Direct-engine/API parity cases cover business last 7 days, a single inventory SKU, approved SKU forecast 7d, MBA recommendations, one customer, one supplier, and Business Health. Local Mongo validation uses only the existing read-only loopback M6.6A reader; no Atlas or database writes are part of this phase.

Regression commands run for M6.5C frozen forecast contract, M6.6 inventory, M6.6A parity logic, M6.7 artifact rules, M6.8 business/customer/supplier, existing ML service V1 tests, and M6.9B. No TEST holdout recovery, benchmark, training, retuning, or mining command is run as part of serving.

### Final local measurements

One local request per route, same warmed process, measured after startup (observations only, not an SLA):

- business — 69 ms; inventory single — 4,054 ms; inventory ranking — 4,126 ms; forecast single — 54 ms; cross-sell — 0.05 ms; customer — 1,213 ms; supplier — 3,709 ms; full Business Health — 7,442 ms.
- Runtime RSS: baseline 166 MiB; after V3 dataset/forecast manifest 309 MiB; after MBA artifact 311 MiB; after first analytics request 542 MiB. This relatively high request peak and slow inventory/supplier/health calculations are visible follow-up optimization targets; no result cache was enabled in this phase because repeated/warm behavior and load profile need measurement before selecting safe TTL/capacity.
- Startup manifest checks: forecast manifest 0.4 ms; MBA artifact load/hash 10.8 ms.
- Regression run after final V1-compatibility correction: 101 tests passed, including existing ML service, M6.5C recovery, M6.6, M6.6A parity logic, M6.7, M6.8, and M6.9B; the focused M6.9B suite is 21/21. (The separate full M6.5C test contract was included; no TEST holdout/benchmark/training was rerun.)
- The direct engine ↔ endpoint comparisons in the M6.9B suite passed for all seven domains. The local Mongo M6.6A extraction and serving projection comparison passed read-only (80 products, 2,155 purchases, 40,445 movements; 0 projected differences). Full-engine Mongo parity includes internal per-order pending-order details absent from the public inventory contract; the endpoint projection excludes those details. Atlas was not contacted.

## V1/V2 and next phase

The existing `/health`, `/ready`, and `/v1/predict/demand` response contracts remain in place and are regression-tested. V3 is additive and separately ready; no V1/V2 tenant is routed to V3. M6.9C may now add backend-only READ adapters/skills and deterministic routing against these internal contracts. It must retain server-side tenant binding, trace/evidence controls, per-domain availability, and the existing preview/confirmation boundary. No assistant/router/UI capability is enabled by M6.9B.
