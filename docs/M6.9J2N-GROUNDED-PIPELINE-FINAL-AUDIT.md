## Findings, baseline and fixes

The first query-matrix pass was 59/82 test assertions PASS (80 queries plus manifest
and quality controls). Some failures were test-harness problems: the first resolver
incorrectly matched every unknown phrase to a product, WRITE requests bypassed
the action wrapper, and a cancellation assertion required a repeated pendingAction
field even on the established draft-cancellation response. Those fixtures were
corrected without changing product resolution or confirmation rules.

Reproducible production defects corrected in J.2N:

1. **Incomplete/wrong grounded plans.** Supplier wording captured a replenishment
   question before the Inventory→Forecast→Supplier plan; stock plus demand queried
   an unnecessary supplier; bounded health, sales interpretation and customer
   recovery requests missed their intended grounded path. Specific rules now cover
   these shapes. The 50 grounded matrix rows verify skill order and context domain
   membership, not only classification.
2. **External temporal questions.** `qué clima hay mañana` reached forecast; `precio
   del bitcoin`, `presidente del Perú` and a recipe shape missed the high-precision
   external gate. Explicit external-question shapes are now recognized. Catalogue
   and mixed business references still bypass that gate's external templates.
3. **Total input budget mismatch.** A promotion context fit the raw 6400-byte
   context bound but, together with the shared prompt and JSON escaping, exceeded
   the neutral provider's 8000-byte envelope bound. The context builder now fits
   both limits, trimming structured facts and recomputing allowed limitations.
   Neither limit was increased. Impossible/unexpected context construction fails
   closed before generation with distinct safe reasons and retained minimal facts.
4. **Duplicate references/codes.** Duplicate evidenceRefs and repeated limitation
   codes were accepted. Shared schema and parser now enforce uniqueItems with
   DUPLICATE_ITEMS diagnostics. Cardinalities, field names and text bounds remain.
5. **Factual number representations.** Exact cited ISO dates, cents rendered as
   PEN/S/ amounts, and support/confidence ratios rendered as percentages could be
   rejected. Representation-specific validation now accepts those forms only from
   typed, cited facts. Their converted numbers are not added to the general number
   whitelist. Unknown dates cannot be assembled from coincident numeric components;
   an unrelated stock does not authorize a money/percentage claim. USD is never
   converted into PEN. Rejected numbers keep their original encounter order.
6. **Credential-shaped free text.** The context sanitizer did not cover DeepSeek
   sk- keys, JWTs, Cookie assignments and equivalent secret assignments. Those
   forms are now redacted in allowed free-text fields and rejected in generated
   prose. Unknown raw document fields remain outside the projection.
7. **Ambiguous WRITE extraction under DeepSeek.** The action wrapper attempted the
   legacy structured Gemini extraction for an incomplete purchase. With DeepSeek
   selected this is now a deterministic product/quantity clarification before
   provider execution. Gemini-selected legacy extraction is unchanged; no WRITE
   state transition, confirmation predicate or action execution was added.
8. **Forecast horizon and evaluation scope.** The grounded planner silently used 7
   for explicitly requested 14 or 28 days; adding a SKU also changed model-evaluation
   mode into product-detail mode. Explicit forward horizons 1/7/14 are preserved;
   unsupported horizons clarify before skills/provider. A past sales window is not
   reused as forecast horizon. Candidate-scoped projection retains the approved
   expectedUnitsNext1d/7d/14d fields and explicit horizon rather than only 7d.
   Evaluation plus SKU clarifies global evaluation
   versus product forecast instead of inventing per-SKU model metrics.

No critical architectural redesign was needed. The fixes do not add skills, routes,
models, tools, RAG, providers, retries or a Gemini fallback.

## Final contracts and budgets

The GROUNDED path serializes the frozen schema from `groundedOutputSchema.js` into
the prompt and uses the same object for parsing. It accepts a root object with
only observations (1–3) and limitations (0–2). Every observation requires unique
evidenceRefs (1–4 existing refs), interpretation and advisoryRecommendation; each
text is nonempty and <=900 characters, combined <=2160. Limitations are unique
authorized codes, still string[] with <=240 characters per item. No null or extra
properties. A single complete fenced JSON block is supported; free prose around
JSON, arbitrary fragment extraction, invalid/partial JSON and trailing objects fail.

`synthesis.js` also contains SYNTHESIS_SCHEMA and NARRATIVE_SCHEMA for the existing
legacy structured Gemini routes. They use evidence UUIDs/section ordering and a
separate renderer. They are not used by handleGrounded, the DeepSeek adapter or its
parser. Merging them would change V1/V2 behavior without necessity; tests keep the
provider boundaries separate. Historical documentation is not runtime schema.

Output remains DEEPSEEK_MAX_OUTPUT_TOKENS default 500, configurable through 600.
The bounded internal 600 ceiling is clipped by the effective environment setting.
JSON mode and the existing endpoint remain. stop proceeds to validation; length
is always OUTPUT_TRUNCATED, even if text looks parseable. No retry, partial-JSON
repair or second-provider fallback. Mock usage tests cover 150/250/300/400/499/500;
those values are declared mock envelopes, not measured tokenizer counts.

## Numeric policy and its limits

Numeric permission is scoped to the observation's cited facts, not to question
text or unrelated evidence. Exact finite values pass. One- and two-place decimal
representations may match `Number(fact.toFixed(places))`, including comma decimals.
7.16→7.2 and 34.75→34.8 pass. Integer rounding 5.03→5 does not independently grant
permission. Exact date tokens are authorized from cited facts or explicit scope
dates (asOfDate, frozenCutoff, closed-through date and period boundaries).

PEN monetary mentions derive only from Cents fields with PEN/inherited PEN currency.
Support/confidence percentages derive from ratios in [0,1]; Pct/Percent/Percentage
fields already use percentage units. Grouped/ambiguous money strings are rejected;
no currency conversion or new commercial calculation is performed. New safe numeric
categories CURRENCY_AMOUNT and DATE_VALUE identify failures without logging prose.

J.2I package identity remains exact amount/unit plus recognizable product words:
900 ml/750 g do not authorize 900/750 units. SKU suffixes do not authorize numbers.
J.2J/J.2K bounded leading structural markers remain supported; inline numeric refs,
unknown indices and quantities still require evidence. Correct entity codes must
be present in cited evidence. Duplicate references are rejected rather than used
to create additional permission.

This remains a bounded rule-based validator, not a proof of arbitrary natural
language. General raw number matching is value/reference based, not a universal
metric-to-unit type checker: another exact 5 in the same cited facts can authorize
5, independently of coverage 5.03. Arbitrary names, every causal paraphrase and
every arithmetic relation cannot be semantically verified by these rules. Specific
code/number guards and prohibited-claim patterns are tested; no claim of complete
semantic entailment is made. Replacing that policy would require a separate design.

## Deterministic limitations

J.2M's six codes remain RECOMMENDED_QUANTITY_UNAVAILABLE, FORECAST_UNAVAILABLE,
SUPPLIER_RELATION_UNAVAILABLE, ANALYTICS_PARTIAL, ANALYTICS_UNAVAILABLE and
CONTEXT_EVIDENCE_OMITTED. The builder derives code/message/evidenceRefs only from
explicit state in sent evidence and refreshes them after trimming. The validator
intersects the sent allowlist with currently supportable codes; backend constants
render the Spanish text. Complete facts produce []; ordinary uncertainty and
generic warnings cannot become limitations. One/two authorized codes pass;
three fail cardinality, duplicate/unknown/unauthorized codes fail closed.
The previous partial/failed-skill no-generation gate remains active.

NONE means acceptance. OTHER is the sanitizer's fixed fallback for an unrecognized
reason, not an instruction to display it. TEXT_FIELD_INVALID remains a legacy
accepted diagnostic value but has no current emission branch in this pipeline;
text problems use schema reasons, OUTPUT_TEXT_TOO_LONG or UNSAFE_CONTENT. This
distinction avoids inventing a test for an unreachable throw site.

Schema subreasons are JSON_PARSE_FAILED, REQUIRED_FIELD_MISSING, WRONG_TYPE,
TOO_MANY_RECOMMENDATIONS, FIELD_TOO_LONG, UNKNOWN_FIELD, EMPTY_RECOMMENDATIONS,
TOO_MANY_ITEMS, EMPTY_ARRAY, EMPTY_TEXT and DUPLICATE_ITEMS. N-SCHEMA-* and
N-JSON-* exercise each, with J.2H retaining the exact shared-schema regression.
Unknown property diagnostics report their containing object, never generated keys.

Limitation subreasons are NO_ALLOWED_LIMITATION_CONTEXT, UNKNOWN_LIMITATION_CODE
and LIMITATION_NOT_AUTHORIZED. Only known codes can appear in limitationCode.
J.2M verifies each reason, its public projection and sanitized logs.

## Provider, context and skill failures

DeepSeek internal codes are DEEPSEEK_CONFIGURATION_INVALID, DEEPSEEK_TIMEOUT,
DEEPSEEK_NETWORK_ERROR, DEEPSEEK_AUTH_FAILED, DEEPSEEK_RATE_LIMITED,
DEEPSEEK_UNAVAILABLE and DEEPSEEK_INVALID_RESPONSE. Neutral failureKind maps them
to CONFIGURATION/TIMEOUT/NETWORK/AUTHENTICATION/RATE_LIMIT/UNAVAILABLE/
INVALID_RESPONSE, then execution exposes AGENT_PROVIDER_FAILED with sanitized
diagnostics. N-PROVIDER-* tests cover each; known usage/cost survives completion
rejection, absent usage remains null and an unknown tariff remains null.

Before synthesis, status PARTIAL/NO_DATA or other non-ready results suppress the
provider and retain available facts. Inventory failure also skips dependent
forecast, while an independent supplier read can finish. The safe skill-code set
is ARTIFACT_UNAVAILABLE, SCENARIO_NOT_SUPPORTED, TENANT_MISMATCH, INVALID_PERIOD,
SNAPSHOT_BOOTSTRAP_REQUIRED, SNAPSHOT_CONSISTENCY_UNAVAILABLE, SNAPSHOT_TOO_LARGE,
LIVE_SNAPSHOT_UNAVAILABLE, INVENTORY_RESPONSE_INVALID, AGENT_INVALID_SKILL_ARGS,
AGENT_SKILL_TIMEOUT and ML_SERVICE_UNAVAILABLE. Unknown exceptions become
INTERNAL_ERROR. Fixed synthesized codes are SKILL_NOT_READY and
INVENTORY_CANDIDATES_UNAVAILABLE. These are failures[] codes, not provider
validationReason values. Safe fields: skillId, kind, code and bounded httpStatus.
Fixtures: N-SKILL-*, J2C and J2A cross-tenant/incomplete tests.

Context resolution failure returns grounded_unavailable without skills/provider;
no verified V3 binding cannot admit grounded V3 analysis. Period/horizon/scope
clarifications and OUT_OF_DOMAIN also return before generation. Execution budget
or invalid invocation can produce AGENT_INVALID_REQUEST, AGENT_INVALID_SKILL_ARGS,
AGENT_BUDGET_EXCEEDED, AGENT_SKILL_TIMEOUT, AGENT_EXECUTOR_NOT_READY or
AGENT_SKILL_EXECUTION_FAILED at the registered execution boundary. Their internal
exceptions are never copied to the provider; the safe mapping above or the existing
orchestrator error response handles them. Legacy Gemini error families remain
separate in contracts.js/execution.js and are never a DeepSeek fallback.

## UX, telemetry, WRITE and security findings

The exact supplied inventory fixture contains Primor 11/0/7.16/MEDIUM/18/10.75,
Cocinero 7/0/5.03/HIGH/24/9.75 and Arroz 17/57/3.42/MEDIUM/12/34.75. N-QUALITY
checks clear priorities, relevant quantities, incoming before another purchase,
and candidate-scoped forecast. Mock synthesis exists only in test helpers;
production does not hardcode these products or recommendations. Successful
rendering shows synthesis once, not the three skill DTOs. Replenishment fallback
contains a brief rejection message and <=3 factual lines; unrelated supplier
catalogues are filtered before synthesis. Other-domain fallback is bounded to
four lines per consulted skill, and context failures retain two lines per result.

The matrix's 15 deterministic cases show zero provider calls, zero tokens and zero
estimated cost. All ten external cases additionally show zero business skills.
WRITE tests use the actual action wrapper with local mocks; simple entity selection
does not confirm, valid purchase data creates a preview, cancellation prevents
execution, and DeepSeek receives no tools. No actual sale, purchase or stock change
was performed. Existing J.2B/J.2A WRITE regressions are included. Action state
transitions themselves were not changed.

Telemetry assertions cover provider/model, one call, declared input/output/total,
cache decomposition, nonnegative latency, actual-usage-based cost range and finish/
validation reasons. Mock values do not measure production latency or tokenization.
No API key, Authorization value, JWT, cookie, Mongo URI, Telegram token, raw
provider response, full prompt or reasoning_content is persisted to diagnostics.
Known credential shapes are redacted before provider context and rejected in
generated prose; logs/public projections use fixed allowlisted fields. API keys
remain in the adapter closure. No real credentials are used by the tests.

## Remaining risks and exact next cloud phase

Offline fixtures prove the acceptance boundary and finite supported routes, not
future natural-language quality or universal semantic truth. A real response can
still violate the schema/grounding and must fall back safely. The numeric and
name/causality limitations above are retained design limits, not silently claimed
as solved. Product matching tests use the existing matcher; arbitrary product-name
grounded advice does not gain a new permissive resolver. Infrastructure cold starts,
actual usage/cost/latency and the provider's live behavior are not measured here.

No critical architectural blocker was found for the controlled final battery.
Next phase: publish J.2M and J.2N together after verifying a clean worktree; deploy
Proy_API at that SHA, and align frontend/Vercel because unpublished J.2M changed
diagnostic UI. Keep DEEPSEEK_MAX_OUTPUT_TOKENS=500; no ML or Node-RED deployment.
Use the existing authenticated V3 session. Predeclare five READ synthesis questions:
replenishment priorities, customer retention, supplier review, sales strategy and
promotion/associations (the last also checks the total input budget). At most one
paid generation per question, no retries; stop at the first failure. First verify
one deterministic stock query and one external sports query at zero tokens.
Record deployed SHA, skill statuses, finish/validation reasons, measured usage/
cache/cost/latency and readable results; retain no raw provider text or prompts.
No WRITE execution belongs in that cloud battery. Do not start it automatically.
