# M6.9B.1 — Rendimiento y memoria del serving V3

Estado: optimización local. No se hizo deploy ni se conectó a Atlas/Mongo. Se conservaron fórmulas, umbrales, datasets y contratos del serving M6.9B.

## Perfilado y cuello de botella

El perfil se tomó sobre `V3IntelligenceRuntime` y los adapters, con datos canónicos locales. cProfile antes del cambio observó 4.81 s dentro de `InventoryIntelligenceV3.snapshot()`; 3.56 s correspondían a 80 llamadas individuales al wrapper de forecast. Cada llamada volvía a construir la segmentación de 80 SKU y a recorrer sus series (aprox. 2.45 M conversiones de fecha). El bundle ya dispone de `predict_forecast_batch`; el cambio agrupa los mismos SKU y cutoff en una llamada, sin modificar el módulo congelado M6.5C. Otros 0.81 s se iban leyendo/parsing cinco NDJSON en cada snapshot; el runtime ya había cargado y validado sus filas operativas al iniciar.

Además, inventory volvía a leer product-day y definiciones estáticas. Customer y supplier reconstruían snapshots en cada consulta; Supplier y Business Health también pedían inventory aunque ya existía un snapshot reutilizable. Health recomponía todos los dominios y volvía a calcular los 80 forecasts.

## Cambios

- `v3_baseline_bundle.predict_many()` invoca una vez el batch aprobado y proyecta por SKU exactamente el mismo contrato de `predict()`. Inventory snapshot, forecast multi-SKU y Business Health usan el batch. `ml/src/v3_forecast.py` no se modifica para preservar el SHA congelado de M6.5C.
- El runtime construye una sola instancia de inventory con dataset, registros operativos ya validados y definiciones UTF-8 cargadas una vez. Inventory deja de releer products, movements, purchases, purchase-items, product-day y definiciones en cada snapshot.
- El runtime comparte snapshots derivados read-only para Inventory (LRU 3 cortes), Customer (4 cortes) y Supplier (4 combinaciones corte/periodo). Se protegen con lock de proceso para evitar cálculo duplicado concurrente.
- Las claves incorporan business, scenario, dataset version/hash, fecha, versión de motor y parámetros (periodo/filtros cuando el resultado base depende de ellos). La auth se valida antes de entrar al cálculo; no se cachean decisiones de autorización. Cada worker tiene su propia caché; no se asume singleton entre procesos.
- Los filtros se aplican después a snapshots base; el filtro de producto en Supplier crea proyecciones nuevas para no mutar el valor cacheado. También se corrigió que el adaptador trataba como mapa la lista `productAlternatives` devuelta por M6.8.
- Cross-sell y forecast conservan artifacts eager y validados; FP-Growth no se recalcula. Business Health reutiliza los snapshots y obtiene los 80 forecasts en batch, sin score ni cambios de fórmula.

Las cachés son bounded y worker-local. El lock serializa la inicialización de una entrada fría en un worker; no cambia resultados y evita duplicados. Escalar workers replica la memoria de contexto/caché por worker.

## Empaquetado reproducible para cloud

El paquete `data/minimarket-pasco-v3/generated/` está ignorado por Git y hoy el loader verifica todos sus 23 archivos según el manifest. Por tanto, el runtime realmente necesita el conjunto canónico generado completo; un bundle reducido no ofrecería ahorro material sin rediseñar las verificaciones/contratos de fuente. Se conserva el dataset canónico como fuente de verdad y se regenera en el build desde las definiciones versionadas:

```text
node scripts/generate-minimarket-v3.js --seed 2026
```

La salida debe conservar `logicalDatasetSha256=a90b913b6ee83174165b39eaab1526525b3aacc53cae1abe6c3f5a54a469cac8`; el startup V3 vuelve a validar los hashes de archivos, configuración, manifest y artifacts antes de readiness. El manifiesto pequeño aprobado `ml/models/minimarket-pasco-v3/baseline-manifest.json` se deja versionable; no se suben los datos generados.

Tamaños locales exactos:

- Definiciones canónicas versionadas: 144,198 bytes (~0.138 MiB).
- Dataset generado de runtime (23 archivos): 79,298,281 bytes (~75.63 MiB).
- Artifact MBA versionado: 357,343 bytes (~0.341 MiB).
- Manifiesto forecast versionado: 2,292 bytes (~0.002 MiB).
- Datos runtime adicionales presentes en el deploy una vez generado: 79,657,916 bytes (~75.97 MiB), más código/dependencias ya parte de la imagen.

No hay actualmente un descriptor Render ML versionado que fije repo/branch/build command. La operación cloud futura debe configurar explícitamente el build command anterior antes de iniciar FastAPI; no basta con el checkout de Git. El readiness V3 debe seguir fallando controladamente si falta el dataset/artifact. Esto resuelve el plan y lineage, pero el wiring del servicio Render y la validación del build limpio siguen siendo gates de M6.9E; no se ejecutó cloud en M6.9B.1.
