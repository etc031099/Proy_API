# M6.9I.2 — Diagnóstico diferencial de Telegram

## Evidencia observada

Para `ABA-SAZ-003` (mínimo 2), una edición manual de 3 a 2 produjo una alerta Telegram. Tras editar de 2 a 3, una venta de una unidad confirmada en el asistente dejó stock 2, pero no produjo el aviso esperado. No se hicieron nuevas operaciones reales para este diagnóstico.

## Causa en el código

La edición manual (`updateProductStock`) llama a `notifyLowStock` después del commit. La API directa de ventas también lo hace. El asistente usa `transactionExecutor('sale')` y `writeTransaction` dentro de la transacción de `PendingAction`; este ejecutor recibía `lowStockNotifications`, pero las descartaba. Por ello no invocaba el notificador básico al confirmar la venta. No hay evidencia local de un error de entrega Telegram para esa venta: la llamada ni siquiera estaba programada en esa ruta.

`notifyLowStock` aplica `previousStock > minStockLevel && newStock <= minStockLevel`. No conserva estado por producto: `lastAlertAt` de `TelegramConnection` registra fecha del último envío de la conexión, pero no participa en deduplicación. Así, el paso de 2 a 3 rearma implícitamente un futuro cruce de 3 a 2. Un descenso de 2 a 1 no genera otro aviso básico. La búsqueda de la conexión se limita al `businessId`, chat vinculado y preferencia `lowStockAlertsEnabled`.

## Cambio

El ejecutor de venta del asistente registra las notificaciones del resultado transaccional para ejecutarlas únicamente después de que `PendingAction` confirma el commit. Preview, cancelación, error, rollback y confirmación repetida no programan un segundo envío. No se alteraron los umbrales ni el cuerpo de los mensajes.

Las **reglas personalizadas de stock** son un subsistema diferente: `applyStockChange` evalúa cruces y recuperaciones en la misma transacción, guarda eventos por negocio, producto, regla y movimiento, y entrega mediante outbox. La preferencia visible «Avisar cuando el stock se recupera» (`stockRuleResolvedAlertsEnabled`) se aplica a estas reglas, no al aviso básico de mínimo. Una recuperación solo notifica si existe una regla aplicable, esta preferencia está activa y el evento llega al canal de entrega. No se verificó si `ABA-SAZ-003` tiene una regla personalizada activa.

Una orden de compra **pendiente** no aumenta stock ni genera recuperación. `receiveV3Purchase` cambia existencias al recibirla y pasa por el evaluador transaccional de reglas. El `create_purchase` actual del asistente usa la compra inmediata de `writeTransaction`, que sí incrementa stock tras confirmación; no es un flujo de orden pendiente ni un comando de recepción diferida. Esta distinción impide atribuir una alerta de recuperación a la simple creación de una orden diferida. No se amplió el asistente para recibir compras.

## Validación local

- Antes del arreglo, el test de venta del asistente falló: registraba cero callbacks post-commit cuando se esperaba uno.
- Después, 24/24 pruebas focales de Telegram, cruces, recuperación y reglas pasaron; el control específico de efecto post-commit pasó 1/1.
- El ciclo con mínimo 2 cubre `3→2`, `2→3`, `3→2`, `2→1` para aviso básico; y `LOW→NORMAL→LOW→NORMAL` para reglas personalizadas.
- Sintaxis JavaScript y `git diff --check`: correctos.
- La ejecución amplia de `automations.test.js` tuvo un fallo de entorno al conectar a `127.0.0.1` (`EACCES`); el test focal relevante se ejecutó por separado y pasó. No se contabiliza la suite amplia como aprobada.
