# A.3.7.9.3 — Núcleo de checkpoint ML y preflight de solo lectura

## Alcance y estado de habilitación

Snapshot completo, sin delta ni compensaciones. No existe restore, API pública,
UI, dispatch ni entrenamiento en esta implementación. **Restore cloud: NO-GO**.
La captura se admite exclusivamente con Mongo replica set local y una base
desechable `ml_checkpoint_<32 caracteres hex>_test`.

Los writers productivos todavía no consultan el control/epoch: `TEST_ACTIVE`
representa solamente el estado del núcleo local. El CAS no constituye un bloqueo
de ventas ni workers productivos. `localWritersPaused=true` es una precondición
explícita del llamador local, no una protección distribuida implementada.

## Tres entidades nuevas

- `MlTestControl`: businessId único, checkpoint/ciclo activos, estado,
  resetEpoch BSON int64, timestamps y failureCode. El servicio solo incrementa
  epoch mediante `$inc` condicionado por CAS; no existe operación para bajarlo.
- `MlTestCheckpoint`: identidad/scope, creador opcional, CREATING/READY/FAILED,
  hora de captura, revisión real, cierre Lima al capturar, modelos/pointers,
  referencias de artifacts, manifiestos, conteos, bytes y hashes.
- `MlTestCheckpointChunk`: stream BSON binario, colección, ordinal, número de
  documentos terminados en el bloque, bytes y SHA256.

Todos tienen autoCreate=false y autoIndex=false. No se registran en startup.
La provisión local aditiva crea únicamente estas tres colecciones e índices;
un conflicto de índice detiene la captura. No hay syncIndexes/dropIndexes.

Índices:

| Colección | Nombre | Clave | Único |
|---|---|---|---|
| mltestcontrols | ml_test_control_business_uq | businessId | Sí |
| mltestcheckpoints | ml_test_checkpoint_id_uq | checkpointId | Sí |
| mltestcheckpoints | ml_test_checkpoint_status | businessId, scenarioId, status, createdAt desc | No |
| mltestcheckpointchunks | ml_test_checkpoint_chunk_uq | checkpointId, collection, chunkIndex | Sí |

inventoryalertchanneldeliveries, stockalertrules, pendingactions, actionaudits,

forecastmlupdateevents, forecastmlupdatestates, forecastmlupdateexecutions,

historicalscenarios, minimarketv3records.

Las cuatro colecciones de acciones se incluyen porque las confirmaciones del
asistente y el motor de automatizaciones pueden escribirlas y dejar referencias
a operaciones. No se cambia ese comportamiento.

Usuarios, auth, Telegram connections, configuración/secrets, las tres entidades
nuevas y cualquier archivo de prueba/restore quedan fuera de la allowlist.
Se rechaza otro escenario importado del mismo tenant. El scope autorizado procede
de config/v3Operational y no acepta otro tenant/escenario del llamador.

## BSON, chunks y hashes

El cursor del driver lee documentos BSON crudos (`raw:true`) ordenados por `_id`.
No pasa por JSON, hidratación Mongoose, proyecciones, defaults ni campos ocultos:
incluye artifactData y preparedCandidate cuando existan.

Chunks de hasta 4 MiB; un documento BSON mayor se divide entre varios bloques.
El stream mantiene el prefijo de longitud BSON de cada documento y permite
reconstruir bytes/tipos exactamente, incluidos Long, Decimal128 y Binary/subtype.
`documentCount` cuenta los documentos que TERMINAN en cada chunk; un chunk con
fragmentos de un documento grande puede tener cero documentos terminados.

SHA256 por chunk, SHA256 del stream por colección y hash BSON canónico del
manifiesto completo. Las claves de índices se representan como pares ordenados
para preservar el orden compuesto. READY exige releer y verificar chunks,
frames BSON, conteos, hashes, scopes y totales. Corrupción deja FAILED; no READY.

## Consistencia y límites

Lectura secuencial en una sesión/transacción Mongo con readConcern=snapshot y
readPreference=primary. Requiere replica set. Los chunks se persisten fuera de
la transacción de lectura, mientras el checkpoint sigue CREATING.

listIndexes/listCollections se leen fuera de esa transacción; se comparan sus
manifiestos antes/después. No se garantiza equivalencia ante DDL que cambie y
vuelva a su estado original: captura local requiere también ausencia de DDL.

Límites iniciales: 128 MiB BSON de documentos, 200000 documentos y 45 segundos
para el recorrido. Si se exceden, falla explícitamente; no se cambia a una
lectura inconsistente o a otro mecanismo. Estos son límites de esta herramienta,
no una afirmación sobre capacidad general de Atlas.

CAS NO_TEST -> CHECKPOINT_CREATING con epoch incrementado. La finalización de
checkpoint READY y control TEST_ACTIVE es una transacción corta con majority.
Se rechazan manual requests, jobs/ejecuciones, leases o entregas/automatizaciones
en curso. Señales pendientes por sí solas no bloquean la captura.

El reloj no se restaura: observationsClosedThroughAtCapture es metadata histórica;
no sustituye el watermark de lecturas futuras ni altera maturity/cooldown.

## Ejecución y validación

Desde backend:

```powershell
node --test test/mlTestCheckpoint.test.js
node test/integration/mlTestCheckpoint.run.js
node --test test/forecastMlUpdateCoordinator.test.js test/forecastCloudWorker.test.js
```

El runner de integración reutiliza MONGODB_TEST_URI local de backend/.env y crea
un nombre aleatorio de base de prueba. Solo esa base se elimina al finalizar.
No inicia contenedores ni usa credenciales cloud. Si Mongo no está disponible,
falla explícitamente: no se considera PASS la semántica transaccional.

Desde la raíz, preflight cloud autorizado de solo lectura:

```powershell
node .\backend\scripts\preflight-v3-ml-test-checkpoint-cloud.js
```

Requiere en la sesión FORECAST_CLOUD_MONGO_URI,
FORECAST_CLOUD_EXPECTED_DATABASE, FORECAST_CLOUD_EXPECTED_BUSINESS_ID y
FORECAST_CLOUD_EXPECTED_SCENARIO_ID. No carga .env ni usa URI local por fallback.
No necesita Python. No inicializa modelos ni crea índices/colecciones/control.

Entrega solo métricas agregadas: BSON real por colección, cantidad de documentos,
chunks estimados (mismo chunker que captura), documento mayor, total, colección
mayor, tamaños declarados/reales de artifacts ACTIVE y duración de lectura.
No imprime documentos, artifacts, URI, credenciales o errores crudos.

El tamaño total corresponde a documentos fuente BSON sin overhead de almacenamiento,
índices o compresión. Los chunks están calculados exactamente para ese recorrido;
la capacidad/espacio libre de la cuenta cloud debe verificarse por separado.

### Evidencia de A.3.7.9.3B

- Prueba concurrente focal: 2 PASS (una captura READY con epoch 1; el segundo
  intento recibe CHECKPOINT_CONTROL_BUSY). El control termina TEST_ACTIVE.
- Integración completa en Mongo replica set local: 5 PASS, 0 FAIL. Incluye
  preflight read-only, snapshot consistente y corrupción/epoch monotónico.
- Pruebas del checkpoint offline: 13 PASS. Regresiones coordinator/cloud worker:
  26 PASS, 1 SKIP (preflight Python optativo).
- Preflight cloud no ejecutado en esta fase. No se creó checkpoint cloud y no
  se ejecutó restore/training/dispatch/deploy.

La causa del primer fallo fue que resúmenes BSON opcionales contenían propiedades
`undefined`; al persistirse en Mongo, el driver las representó como `null`, y el
hash del manifiesto no coincidía al releerlo. Los resúmenes ahora normalizan esos
campos opcionales a `null` antes de calcular el hash. La provisión local explícita,
el CAS y las restricciones de índices permanecen sin cambios.

### Evidencia previa de esta sesión

- Pruebas nuevas offline: 13 PASS. Incluyen round-trip de tipos, documento >4 MiB,
  chunking/hashes, scope, exclusiones y rechazo de corrupción con estado FAILED.
- Regresiones coordinator/cloud worker: 26 PASS, 1 SKIP (preflight Python optativo).
- Preflight cloud detenido antes de conectar: CHECKPOINT_CLOUD_ENV_REQUIRED.
  FORECAST_CLOUD_MONGO_URI y FORECAST_CLOUD_EXPECTED_DATABASE están UNSET en Codex.
  Conteos, tamaños por colección/total, chunks y tiempo cloud: NO MEDIDOS.
- No se creó checkpoint cloud ni se ejecutó restore/training/dispatch/deploy.

Esta evidencia no autoriza habilitar captura o restore productivos.
