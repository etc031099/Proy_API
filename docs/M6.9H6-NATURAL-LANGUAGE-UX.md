# M6.9H.6 — Natural-language assistant UX

## Scope

This phase adds bounded natural-language aliases and presentation behavior to the existing V3 router and entity-resolution flow. It does not add another resolver, change analytics, connect cloud services, or execute business writes.

## Validation

`backend/test/assistantNaturalLanguageH6.test.js` covers 103 semantic phrases across stock/product questions, sale and purchase parsing, category/brand queries, ambiguity/ordinal selection, follow-up context, write safety, and out-of-domain routing. Focused existing regressions also passed:

- product resolution and follow-up context: 6/6
- guided purchase/selection/cancellation: 6/6
- action-input ambiguity and preview safety: 2/2
- H.6 semantic suite: 5 test blocks passed, covering the 103 phrases plus targeted cases
- JavaScript syntax and `git diff --check`: passed

H.6-FIX1 adds six focused natural-language tests and five guided/orchestrator regression tests; all 11 passed. A broader run of four existing test files reported 506/507 passing. The lone failure was the P2D case `¿sí se descontarán 3 unidades?`: it expected the READ response to repeat `pendingAction`. The actual response contract omits that field on READ turns; the authoritative pending operation and `operationDraft` remain stored, and a short “sí” after the READ re-presents the preview instead of executing. Classification: **B, fixture/assertion out of alignment with the response contract**, not a WRITE-state loss. The test now checks persisted PENDING state, READ suspension, explicit reconfirmation behavior, and cancellation without execution. No production code changed for this discrepancy.

The first H.6 run exposed gaps in plural/case handling, `opcion 2`, stock follow-up, and the cancellation phrase `ya no`. These were fixed and covered by the final passing suite.

## Behavior added

- Bounded stock-query forms resolve common human terms and plural variants through the existing entity lookup. A simple stock question returns a compact stock-only response, for example `Pan francés: 21 unidades disponibles.` It does not show forecast, coverage, ABC/XYZ, risk, or price by default.
- Common category requests map to existing category/subcategory prefixes for soft drinks, cookies, milk, and bread. Brand requests recognize a small explicit set including Gloria, Inca Kola, and Coca-Cola. Results continue through the existing candidate-resolution flow; category or brand is not silently treated as a unique SKU.
- Brand/category plus depletion phrases now resolve candidates through that same resolver, then call the existing inventory condition over the bounded matched SKU set: `low_stock` for “por acabarse/con poco stock”, and `should_reorder` for “debería reponer/pedir”. Neither adds a threshold. If reorder evidence is unavailable, the assistant says so rather than implying no matches or inventing a quantity. The response stays compact (human product name and stock/status); an empty filtered result is stated explicitly.
- Product presentations remain separate candidates identified by their existing stable product identities. Candidate ordering remains the existing resolver’s deterministic ordering.
- A follow-up such as `esa no, la otra` may choose the other item only when the saved candidate list contains exactly two options and a product is already selected. This is a READ selection and never confirms a pending WRITE.
- When a V3 product candidate list is active, an explicit action plus ordinal and quantity (for example `vende 2 de la segunda`) consumes that saved candidate and proceeds through the existing resolver and preview. An out-of-range ordinal is rejected safely. For a pending purchase draft, `5 de la segunda` can select and set quantity in one turn, then produces a preview. Cancellation remains available; candidate selection is not confirmation. No test in this phase invokes a write executor.
- `saca` has no existing, unambiguous operation mapping in the codebase; it can mean sale or a stock adjustment. The V3 router therefore asks whether the user means a sale or stock correction, before resolving a product or preparing a write. It is not silently converted to a sale.
- Narrow typo normalization is limited to the explicitly tested forms; this is not general-purpose autocorrection.

## LLM and out-of-domain behavior

The supported H.6 business-query cases are tested through deterministic routing and entity resolution; the tests do not invoke an LLM/provider. In a local orchestrator test with a synthetic provider, each of four out-of-domain examples went to the existing classifier once and the mock reported 17 tokens per example. These are fixture values, not actual Gemini usage. Real provider calls/tokens and live responses were not measured. Full out-of-domain rejection and cost control remain for the future DeepSeek/cost phase.

## Limitations

- Category and brand aliases are intentionally bounded, not exhaustive Spanish morphology or fuzzy search.
- Only stock questions have a compact response mode in this change. Price, coverage, and full-detail intent modes were not broadly redesigned.
- Brand/category depletion filters are bounded to 20 matched SKUs (and the existing contract's 504-character product-reference limit). If a search exceeds that bound, the assistant asks to narrow the search rather than claiming it examined the entire catalog.
- `saca` still requires clarification because the existing system has no definitive movement meaning for it; use `vende` to request a sale preview.
- Out-of-domain routing was measured only with a synthetic provider fixture (one classifier call and 17 fixture tokens per sample); production provider cost/response remains unconfirmed.
- Clickable UI candidate rendering was not changed; existing support is reused.
- No cloud, deployment, database, sales, purchase, or stock mutation was performed.
