# A.3.7.9.6C — Operative checkpoint quiescence

Cloud CREATE uses `captureOperationalCheckpoint` after the existing admin,
target, flag and certification gates. The local certification API still requires
its explicit local pause assertion; that assertion cannot authorize cloud capture.
`ML_TEST_WRITERS_PAUSED` is no longer an HTTP executor configuration mechanism.

## Admission and capture

- Ordinary demo HTTP mutations and existing worker/service `runCycle` calls
  atomically register an opaque writer ID on `MlTestControl`. The first writer
  can initialize a pristine `NO_TEST` control without changing its epoch.
  The existing model plugin also admits standalone NO_TEST/epoch-zero writes
  for their complete promise, preserving the previous ordinary model contract.
  Transactional standalone writes retain the control-document commit conflict.
  Once a test epoch exists, explicit cycle context remains mandatory as before.
- Admission and the existing `NO_TEST -> CHECKPOINT_CREATING` CAS write the
  same document. Only one checkpoint owns the next epoch and cycle.
- `CHECKPOINT_CREATING` closes admission, activates the existing maintenance
  guard and suppresses external effects. Prior writers either complete or fail
  their old epoch fence, then remove their admission IDs.
- Existing busy jobs/dispatches are rejected before acquiring maintenance; capture
  waits up to 30 seconds for durable admissions to drain and then rechecks
  ML jobs, executions, manual work and deliveries before reading
  the snapshot. It never sets a caller-supplied paused boolean to authorize cloud.
- Snapshot persistence, BSON preservation, hashes, verification and the atomic
  `READY / TEST_ACTIVE` transition retain the existing implementation and limits.

HTTP admission lasts until response completion, not merely until Express `next()`
returns. Read-only requests do not acquire writer IDs. The authenticated checkpoint
and restore routes own their lifecycle and are not counted as ordinary writers.
Status and restore recovery remain reachable during maintenance; critical business
routes retain their existing 503 maintenance response.

## Failure and recovery

Writer IDs have no expiry or automatic deletion: a timeout or disconnected
request is not proof that an in-flight write stopped. An aborted HTTP response
retains its blocker. A failed drain/capture leaves `FAILED` (or an abruptly killed
owner leaves `CHECKPOINT_CREATING`), never silently reopens writers. Status exposes
only the state and admission count, not IDs. A retry cannot steal this owner.

As in the certified contract, a failed capture without a verified READY source has
no force-NO_TEST or restore escape. It requires explicit administrative investigation;
this phase does not add a destructive recovery bypass. A successful READY source
keeps the existing restore-and-continue/finish and same-restore-ID recovery flow.

Deploy the updated backend and ensure any other application writer/worker uses
the same updated fencing code. Drain old deployed processes/jobs before the cloud
attempt. External scripts using the raw Mongo driver are administrative actors and
must remain stopped; they do not acquire application admission automatically.
The restore feature flag and cloud target certification remain mandatory.
