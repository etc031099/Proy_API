# A.3.7.9.5 — Certificación local de robustez / cloud NO-GO

## Decisión

**Certificación local aprobada; NO-GO para ejecutar restore cloud todavía.**

Los mecanismos probados abajo funcionan en Mongo 7 replica set local, en bases
aleatorias desechables. No se creó checkpoint/control/índice en Atlas, no se
restauró cloud, no hubo entrenamiento real, dispatch real ni deploy.
`cloudRestoreEnabled=false` y la restricción local de los servicios permanecen.

El criterio de autorización de acciones CLOUD no está cerrado: actualmente NO
existe una entrada administrativa cloud de crear/restaurar/finalizar. Se añadió
una validación reutilizable de sesión admin y scope server-side, pero no está
conectada a acciones mutantes ni equivale a un endpoint protegido ya certificado.
No se debe habilitar cloud sustituyendo simplemente `assertLocalTarget`.

Pendientes antes de GO:

1. Integrar y probar el boundary administrativo en el futuro ejecutor cloud y
   definir la finalización/abandono explícitos; conservar epoch monotónico y
   bloqueo tras captura interrumpida. No hay recuperación automática a NO_TEST.
2. Vincular de forma durable claims/dispatch al cycle/epoch antes de permitir
   finalizar una prueba y volver a NO_TEST. La certificación actual rechaza el
   workflow retrasado mientras TEST_ACTIVE/RESTORING; no certifica un workflow
   antiguo que arranca después de una futura finalización de prueba.
3. Verificar capacidad/latencias del ejecutor cloud elegido con los límites
   definidos. Las medidas siguientes son loopback, no una medición de Atlas.

No se autoriza A.3.7.9.6 restore Atlas con este resultado.

## Procesos reales e interrupciones

`mlTestCertification.run.js` crea bases `ml_checkpoint_<uuid>_test` exclusivamente
en loopback. Padre e hijos validan el destino. Los hijos usan conexiones Mongo
independientes y los servicios reales; no comparten AsyncLocalStorage/memoria.
Las pausas se inyectan solamente en el helper de pruebas, sin hooks nuevos en
producción. El padre termina el hijo con `kill('SIGKILL')` (TerminateProcess en
Windows), espera su salida y verifica Mongo desde otra conexión.

| Caso | Resultado comprobado |
| --- | --- |
| Muerte después del primer chunk de captura persistido | CHECKPOINT_CREATING y CREATING; ningún READY; epoch=1; no reapertura automática |
| Muerte tras commit de products durante restore | RESTORING; epoch=2; antes de expirar lease devuelve RESTORE_CONTROL_BUSY |
| Muerte durante lectura de chunks de verificación final | RESTORING; epoch=2; no publicación como TEST_ACTIVE |
| Reanudación explícita | Mismo restoreId después de vencer lease real; TEST_ACTIVE; epoch sigue 2 |
| Repetición del mismo restoreId | idempotent=true; no incremento ni doble archivo |

No se editan fechas/leases/epochs del fixture para acelerar estas pruebas.
Cada recuperación espera el lease de 60 s real. Una sesión Mongo del proceso
muerto también puede tardar en liberar recursos: la suite completa duró 248 s.
Una captura muerta queda cerrada y requiere futura recuperación administrativa;
no se declara resumible ni se abre el sistema automáticamente.

## Fencing multiproceso

Proceso A conserva el token anterior. Proceso B hace restore real y aumenta el
epoch. Luego A intenta una venta mediante transactionWriteService y mutaciones
Mongo reales de ACK/state, execution finish, artifact persistence y Registry
pointer. Las cinco son rechazadas con STALE_TEST_EPOCH. No se cambian stock ni
artifacts. La garantía procede del control Mongo y sus transacciones/hooks,
no de comparar dos variables compartidas en el padre.

Las pruebas ACK/persist/finish/pointer ejercitan los modelos y fencing; no
ejecutan entrenamiento ni una promoción metodológica real.

El hijo de dispatch retrasado invoca `productionDependencies(...).executionHistory.begin()`
del runner real contra la base LOCAL. Su `prepare/connect` termina con
TEST_CLOUD_WORKER_DISABLED antes de crear ejecución, llamar Python, ACKear o
promover. Se conserva la cantidad previa de ejecuciones y pythonCalls=0.
No se envía una petición a GitHub.

## Entregas externas y límite físico

Outbox y canal Telegram conservan el contexto de epoch durante cada proceso de
entrega. Se verifica nuevamente justo antes de enviar y antes de confirmar el
resultado. Un consumidor con token antiguo también queda suprimido aunque el
estado sea NO_TEST con otro epoch. Los consumidores ya suprimían nuevos envíos
en TEST_ACTIVE/RESTORING.

Prueba multiproceso: una reclamación de entrega queda pausada en A antes de
enviar; B captura/restaura; A continúa: sends=0, acks=0. Usa el dispatcher real
con transporte/repository de entrega sintéticos; el control/epoch es Mongo real.
Una prueba offline separada verifica el rechazo del ACK obsoleto.

**No existe atomicidad entre un envío HTTP y una transacción Mongo.** Un envío
que ya salió físicamente antes del reset no se puede retirar. Incluso un check
inmediatamente anterior deja una ventana pequeña antes del socket. Por eso el
checkpoint exige quiescencia de entregas en vuelo y el modo test debe preceder
las ramas. El test de carrera no demuestra revocación de paquetes ya enviados.
La persistencia de epoch en claims entre reinicios/finalización queda pendiente.

## Límites

`mlTestOperationBudget.js` fija para el ejecutor local:

- captura: 120 s incluyendo verificación del checkpoint;
- restore: 300 s; verificación individual: 120 s;
- fuente: 128 MiB, 200.000 documentos;
- máximo: 128 chunks; target de chunk: 4 MiB;
- guard de memoria: 512 MiB RSS del proceso.

El margen temporal considera los 62,461 s del preflight cloud previo, además de
las medidas locales. No se traslada el presupuesto anterior de 45 s a captura.
El maxTimeMS de cursor sigue en 45 s; no fue necesario cambiarlo.
Son presupuestos cooperativos comprobados entre operaciones/chunks/documentos,
no un watchdog que interrumpa cualquier await o un Mongo sin respuesta. El
ejecutor cloud futuro necesita límites de socket/proceso y validar también el
transactionLifetimeLimit del servidor. No se modificó configuración Mongo.

Las guardas de memoria se aplican también al scanner read-only; no tiene writes.
Un incumplimiento no publica READY/TEST_ACTIVE. El manifiesto persistido también
rechaza totales fuera del máximo antes de reconstruir sus chunks.

## Mantenimiento y UI

- Después de autenticar, GET/POST críticos V3 se bloquean con HTTP 503,
  `code=ML_TEST_MAINTENANCE`, Cache-Control=no-store, durante RESTORING,
  CHECKPOINT_CREATING, FAILED o un estado desconocido.
- GET `/api/intelligence/test-control/status` queda disponible, autenticado,
  no-store, tenant-scoped; expone únicamente state/resetEpoch/testCycleId,
  maintenance y cloudRestoreEnabled=false. No inicializa modelos ni índices.
- Un tenant ajeno recibe NO_TEST sin leer el control del tenant V3.
- BI comprueba el status al montar, al recuperar foco/visibilidad y cada 30 s
  solamente en una pestaña visible, sin peticiones solapadas.
- Cambiar cycle/epoch invalida el cache existente y remonta BI, incluyendo
  inventario, pronóstico, diagnóstico e historial. Se descarta también la
  selección previa de producto. Respuestas del árbol anterior no repueblan la UI.
- Durante mantenimiento se oculta el árbol anterior y aparece
  “Restableciendo prueba…”. Un fallo de lectura también oculta valores antiguos.
- No es push instantáneo: una pestaña visible puede tardar hasta el siguiente
  sondeo; una oculta se valida al volver. El backend bloquea nuevas lecturas
  críticas durante el intervalo. El boundary se limita a BI, no a todas las
  pantallas CRUD de la aplicación.

## Autorización

No se añadieron endpoints mutantes. Las funciones locales siguen rechazando
Atlas y bases no desechables. El nuevo helper authorizeAdminAction exige usuario
autenticado activo/admin, business de sesión igual al autorizado y rechaza
businessId/scenarioId/resetEpoch/testCycleId en body; el scope sale del servidor.
Los tests cubren permisos/scope, pero **la función no está conectada a un futuro
ejecutor cloud**. Esto es una preparación, no certificación end-to-end de crear,
restaurar y finalizar desde una sesión cloud. Es un motivo explícito de NO-GO.
