## Previous contract and confirmed local defect

The application already expected structured JSON, not free text:

```json
{"observations":[{"evidenceRefs":["E1"],"interpretation":"Hecho sustentado.","advisoryRecommendation":"Recomendación sustentada."}],"limitations":[]}
```

Both root fields required; observations 1–3, limitations 0–2. Each observation
required evidenceRefs (nonempty array referencing supplied evidence), interpretation
and advisoryRecommendation (nonempty strings, each <=900 characters). Combined
interpretation/recommendation text <=2160 characters. Limitations <=240 characters
each and literal members of the provided constraints. Extra fields rejected at root
and observation level; null rejected. No optional fields or numeric priority enums.

The previous prompt said `JSON compacto: observations (1–3: evidenceRefs,
interpretation, advisoryRecommendation), limitations (vacío o regla aplicable de
constraints)`, but provided neither a JSON example nor exact types/required fields,
additionalProperties policy or string limits. It left the array type of evidenceRefs
and limitations implicit. JSON mode enforced JSON syntax, not the application schema.
Local malformed-shape fixtures reproduce the generic rejection. This confirms an
underspecified prompt/validator contract and insufficient structural diagnostics;
it does not prove which variant occurred in the historical cloud response.

## Final contract and parsing strategy

`backend/src/agents/groundedOutputSchema.js` defines the shared frozen JSON Schema,
which is serialized into the synthesis system instruction and traversed by the
local parser. Existing field names are retained to preserve the provider-neutral
integration and evidence-scoped grounding. Introducing summary/recommendations
would add a second incompatible shape without evidence that a rename is necessary.

The schema above remains the only accepted shape. No optional fields, no nulls,
no extra properties. Each evidenceRefs array now explicitly allows 1–4 strings
of 1–16 characters. All text must contain a non-whitespace character. The previous
900/2160/240 character limits remain; the prompt explicitly states the global limit.
At most three observations/recommendations; four fail, never silently truncate.
There is no summary field. Interpretation can be short and grouped; it need not
repeat every product. Quantities are optional mentions within grounded prose,
never mandatory duplicated structured fields. No factual fields are added.

The prompt now requires only this object, shows its exact shape and the shared
schema, and explicitly requires arrays, mandatory fields and no null/extra fields.
The existing 100–180 token target and hard 300 token request cap remain unchanged.

Transport keeps `response_format: {type: 'json_object'}` on the existing non-beta
Chat Completions endpoint. The official JSON mode guide recommends JSON instructions
and an output example: <https://api-docs.deepseek.com/guides/json_mode/>.
No endpoint or pricing change. JSON mode is not claimed to enforce the full schema.

Pure JSON passes. A single whole-response fenced block (`json` or unlabeled,
with line breaks) is unwrapped before JSON.parse. Prose before/after JSON, mixed
fences, concatenated objects or invalid JSON fail. No fragment extraction/repair.

## Diagnostics and grounding

Layer SCHEMA runs first and adds schemaReason/schemaField. Reasons include
JSON_PARSE_FAILED, REQUIRED_FIELD_MISSING, WRONG_TYPE, TOO_MANY_RECOMMENDATIONS,
FIELD_TOO_LONG, UNKNOWN_FIELD, EMPTY_RECOMMENDATIONS, TOO_MANY_ITEMS, EMPTY_ARRAY,
EMPTY_TEXT. Existing validationReason categories remain for compatibility;
schemaReason provides the precise detail. Unknown fields report their containing
object, never arbitrary provider-generated key names. Public projection and the
expandable activity diagnostic carry these sanitized fields.

Layer GROUNDING retains evidence references, known entity codes, factual numbers
and rounding, safe content, allowed limitations and prohibited-claim guards.
Failures preserve their distinct validationReason (UNKNOWN_ENTITY,
UNSUPPORTED_NUMBER, EVIDENCE_REFERENCE_INVALID, UNSUPPORTED_SEMANTIC_CLAIM,
UNSAFE_CONTENT, LIMITATION_NOT_ALLOWED), never OUTPUT_SCHEMA_INVALID. No relaxing
of these guards. Existing code-based entity checking is retained; this phase does
not introduce semantic entity-name recognition or claim it proves arbitrary prose.

Usage/cache/cost accounting remains upstream and unchanged even when validation
rejects content. No raw response, prompts, reasoning or credentials are logged or
persisted. On rejection the existing compact safe fallback preserves facts; on
acceptance only natural synthesis is shown, with full evidence in activity.
