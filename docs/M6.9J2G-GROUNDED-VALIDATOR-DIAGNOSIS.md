## Reproducible local cause

The validator previously imposed 360 characters on each interpretation/recommendation string. A legitimate grouped explanation could exceed that bound while the complete provider output remained within 300 tokens. A local 467-character fact-based string reproduced `OUTPUT_SCHEMA_INVALID`. This is a demonstrated local false-positive class, **not a proven diagnosis of the original cloud response**.

Per-field text bound is now 900 characters, with a 2160-character overall prose bound (the former maximum of six 360-character fields). The cap of 300 output tokens and the maximum of three observations/recommendations remain unchanged. Safety/content checks apply to the complete field; no text is silently truncated. Other factual/semantic rules are retained.

Two diagnostic transport gaps were also found: the message controller omitted `grounded` from its explicit HTTP envelope, and the frontend had no synthesis-diagnostic view. Safe diagnostics now cross that HTTP boundary and history projection and appear in an expandable activity detail only for rejected GROUNDED_LLM synthesis.

## Literalness, numbers, recommendations and remaining limitations

The validator does not require each interpretation or recommendation to appear literally in facts. “Priorizaría Cocinero”, HIGH versus MEDIUM, 5.03 versus 7.16, 57 incoming versus zero, quantities 18/24/12 and reasonable decimal rounding pass the focused fixtures. Written linguistic cardinals (“dos productos”, “tres candidatos”) are not treated as fabricated numeric metrics. Digit-based numeric claims remain checked; no blanket exemption for small numbers was introduced.

Supplier codes are authorized only by the evidence actually cited, including the J.2E candidate-SKU filtering. Supplier omission does not establish that no supplier exists. A recommendation needs cited available evidence but need not be a literal engine field.

Potential false positives still worth diagnosing rather than broadly weakening: exact limitation wording, newline/control-character rejection, unsupported integer rounding, and numeric formats not covered by the current parser. The rule-based validator is not a full semantic proof system: it checks numeric membership/rounding and recognized code forms, not every natural-language entity, number-to-field association, comparison direction, or possible causal paraphrase. These limitations existed before this phase. No broad semantic-parser replacement or free-text relaxation was introduced.

A new structured provider contract is unnecessary for the demonstrated length issue: observations with evidenceRefs already exist. Reconsider a field-key claim contract only if the next real diagnostic demonstrates a need.

## Sanitized diagnostics

The backend allowlists provider/model, response received, HTTP status, contentPresent/contentLength, finishReason, usagePresent/parse result, validationPassed/result/reason and an optional fixed validationField path. Unknown reasons become OTHER. Diagnostic values, raw prose, prompts, reasoning_content, credentials and arbitrary error messages are excluded.

Backend logs emit `[GroundedValidation]` with a `groundedValidation` object containing only those fields. Public activity shows rejection state, stable technical reason, optional field, finish reason and whether content was received. Accepted/deterministic answers do not show this failure detail. Known paid usage remains recorded even when validation rejects synthesis.
