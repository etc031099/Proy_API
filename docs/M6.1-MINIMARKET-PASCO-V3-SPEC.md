# M6.1 — Especificación del escenario Minimarket Pasco V3

Fecha de diseño y consulta de fuentes: **2026-10-12**. Estado: **diseño completo; implementación por fases**.

Complemento **M6.1.1**, 12/10/2026: Customer Intelligence, Supplier Intelligence, snapshot integral y paridad local/Atlas (§26–30). Conserva el diseño M6.1 del commit `bf711e1824360aa187ea1d73265fcfa2841acdb4`; únicamente amplía documentación. Los requisitos de esas secciones precisan las reglas comerciales y de publicación cuando un apartado anterior sea más general.

## 1. Visión, alcance y baseline

Un minimarket ficticio situado en Cerro de Pasco, Pasco, Perú, con productos reconocibles, tickets variados, compras derivadas de necesidades de stock y métricas explicables. La demo debe permitir recorrer una operación cotidiana y distinguir una consulta determinística de una interpretación LLM fundamentada.

Baseline publicado: `8ffb2379d9721dd8933adba3a1ef7904f7fa558f`; backend 1192/1192, auditoría P0=0, P1=0, P2=70, P3=0. Esta fase únicamente especifica el nuevo escenario. No genera datos, modifica esquemas, entrena modelos, importa, configura cloud ni cambia el escenario M5.

Identidad propuesta y fijada para el diseño:

| Propiedad | Valor |
| --- | --- |
| Nombre visible | Minimarket Pasco · Demo V3 |
| scenarioId | `minimarket-pasco-v3` |

No existe una colección Business que deba crearse mediante un ObjectId inventado: el sistema actual usa un `businessId` lógico String en User y documentos de negocio. Los ObjectId de usuario, producto y contacto son detalles internos generados/resueltos por los flujos futuros. V3 requiere cuenta propia, siguiendo la arquitectura de un usuario por negocio.

## 2. Transparencia y límites

- Las marcas y productos comerciales propuestos existen o pertenecen a familias comerciales verificables en Perú. La presencia en un catálogo nacional no demuestra disponibilidad local en Cerro de Pasco.
- Tickets, demanda, precios de venta/costo, clientes, proveedores, entregas, promociones y movimientos son **sintéticos de demostración**. No son estadísticas ni ventas observadas de Pasco.
- Todos los multiplicadores de comportamiento local son **supuestos de simulación**. No se atribuyen hábitos a mineros, empresas o personas reales.
- Los nombres ficticios pueden coincidir casualmente con nombres existentes; no se añade identidad fiscal, teléfono enrutable ni domicilio exacto de un tercero.
- La calidad ML mide desempeño sobre este generador. No demuestra generalización a un minimarket real, precisión garantizada, causalidad ni pérdida monetaria futura.
- Una fecha simulada fija no significa que el servicio esté actualizado al día real del navegador. Fuera de esa fecha se muestra el corte de la demo.

## 3. Catálogo y ficha maestra

Cada fila de las siguientes tablas, junto con las reglas de esta sección y la ficha del proveedor, define una ficha completa. No son 80 registros generados ni un seed implementado.

Campos comunes y derivación exacta:

| Campo | Definición |
| --- | --- |
| productKey | `v3.` + SKU; inmutable, independiente del nombre visible |
| SKU | Código de tabla; único dentro del tenant; no es un GTIN/EAN comercial |
| name / brand | Nombre humano y marca de tabla; `Sin marca` para genéricos |
| category / subcategory | Encabezado de categoría y columna de subcategoría |
| presentation | Envase de tabla; unidad vendible completa, sin fraccionar |
| unitOfMeasure | `unit` para stock, compras y ventas; enteros de envases/paquetes |
| sizeValue / sizeUnit | Cantidad y unidad g/ml/L/un del nombre; no convertir peso en unidades de inventario |
| containedUnits | 1 salvo paquete de 4 panes, 8 panes, 4 rollos o 10 toallas; su venta sigue siendo una unidad de paquete |
| demoSalePrice / demoPurchaseCost | Columnas V/C en PEN; redondeadas a céntimos; referencias de diseño, no tarifas oficiales |
| approximateMarginPct | `100*(V-C)/V`; margen bruto unitario previo a gastos e impuestos; no markup |
| baseUnitsPerDay | μ = 1.65 × w; la columna w de las tablas representa el peso previo a calibración. El factor 1.65 es el punto de partida para compatibilizar ≈34 tickets/día, 3.2 líneas/ticket y cantidades variables; no demanda garantizada |
| minStockInitial | `max(1,ceil(2*μ))`; umbral visual inicial, distinto de reorder point |
| safetyStockInitial | `max(1,ceil(3*μ))`, salvo perecibles: `max(1,ceil(μ))` |
| reorderPointInitial | `ceil(μ*L) + safetyStockInitial`; L = lead time medio del proveedor principal |
| principalSupplier / leadTime | Código de tabla + ficha de proveedor; política inicial usa su L |
| active | true para los 80 productos; el estado final de stock lo deriva la simulación |
| perishable | Sí solo donde aparece P; significa vida útil corta relevante para la operación |
| shelfLifeDays | Valor P explícito, o null para vida útil no modelada; hipótesis demo, no vencimiento certificado de marca |

Ejemplo resuelto: BEB-GAS-001 tiene V=3.50, C=2.65, margen≈24.29%, w=3.6, μ=5.94, proveedor SUP-01/L=4, mínimo=12, seguridad=18, reorder point=42. No se usa el reorder point como una recomendación ML futura. La suma de pesos w es 85.47 y la suma de priors μ es 141.0255 unidades/día; equivale a unas 51,474 unidades/año antes de calendario, cestas y disponibilidad. La calibración en M6.3 actualizará el factor y las fichas derivadas conjuntamente, antes de congelar datos.

La columna **Fuente** usa identificadores de §24: E = producto/presentación localizada; R = familia/marca localizada, presentación propuesta a verificar en M6.2; G = genérico de simulación. E no implica precio demo verificado. M6.2 comprobará los R sin aumentar el catálogo ni inventar marcas; un ajuste menor de presentación conserva productKey y exige registrar el cambio antes de generar datos. No se afirma que los 80 envases hayan sido verificados individualmente hoy.

## 7. Generador determinístico futuro

Un generador local de código, sin proveedor LLM, produce todo el escenario a partir de configuración versionada. Contrato conceptual: `generateBusinessScenario(referenceDate, seed=2026, catalog, suppliers, customerProfiles, policy, generatorVersion)`.

1. Validar maestros, cobertura de ofertas, precios, tamaños y unidades; ordenar claves estables.
2. Usar PRNG con algoritmo/versiones fijados y substreams derivados de SHA-256 de seed + escenario + módulo + productKey/supplierCode/fecha. No usar hash nativo no estable, Math.random ni IDs aleatorios como fuente de comportamiento.
3. Materializar calendario, promociones y cambios de precios anunciados; abrir stock y lotes con costo/vida útil. No hay necesidad de generar ventas antes del histórico para rellenar lags.
4. Por día: recibir pedidos cuyo horario llegó, retirar lotes vencidos, generar llegadas de clientes por horario, formar cestas deseadas, limitar ventas al stock utilizable, completar tickets/cobros, cerrar el libro y emitir pedidos según inventario.
5. Procesar eventos por `(timestamp, eventPriority, sourceEventId)`; llegada antes de venta en empate, reverso después del original. Conservar causalidad y secuencia explícitas.
6. Exportar maestros, tickets, líneas, pedidos/recepciones, pagos, cancelaciones, movimientos, ledger, panel diario, calendario y truth sintética de evaluación.
7. Manifest: parámetros, versión de generador, seed, corte, conteos, checksums, balance de stock/dinero, proporción de promoción y stockouts. Mismos inputs ⇒ mismos registros y checksums canónicos.

Solo se calibra en M6.3/M6.4 con estadísticas de generación **anteriores al test** y criterios de coherencia, no buscando que un modelo gane. Cualquier cambio posterior de generador obliga a nueva versión y manifest; no se mezclan datasets de versiones distintas. No se garantiza igualdad de binarios Parquet entre librerías, sí de registros normalizados y su hash.

No se utilizará LLM por ticket, compra, cliente, línea ni día. Los 80 maestros se revisan una vez; la generación masiva usa código. En M6.3 no se conecta Atlas ni se crean credenciales.

## 8. Demanda, horarios y contexto Pasco

Se modelan **llegadas de tickets y cestas**, no series independientes que luego se sumen incoherentemente. El número de llegadas por día y misión usa Negative Binomial mediante mezcla Gamma–Poisson: `Z_d ~ Gamma(k,k)`, `N_d | Z_d ~ Poisson(λ_d*Z_d)`, con media λ_d y varianza `λ_d + λ_d²/k`. k inicial 15, configurable; shock diario compartido induce correlación. Poisson sirve como control de menor dispersión. Valores de k no se estiman de ventas reales de Pasco.

`λ_d = λ_base * weekdayFactor * monthFactor * paydayFactor * holidayFactor * trendFactor`. λ_base se calibra una vez hacia ≈34 tickets/día; después la simulación de stock puede reducir tickets efectivos. El μ del catálogo proporciona pesos iniciales de SKU; popularidad fija `p_i` 0.8..1.2 asignada por substream, evitando que todos vendan lo mismo.

Probabilidad de elegir SKU i en misión/horario: normalización de `μ_i*p_i*categoryWeight*subcategoryWeight*hourWeight*promotionUplift*(price_i/basePrice_i)^elasticity_i*trend_i`. La escala global de μ afecta la política inicial, pero se cancela al normalizar probabilidades; las unidades finales las generan las llegadas, cestas y cantidades. Elasticidad simulada de −0.3 a −1.2; no se interpreta como causalidad estimada. Trend_i acotado 0.85..1.15 al cabo de un año. Calendario y precio pueden cambiar pesos, nunca stock ni ventas por fuera de los eventos.

Todos los siguientes son **supuestos de simulación**, no estadísticas locales:

## 10. Tickets, cestas y registros económicos

Misión probabilística por ticket: desayuno20%, comida/abarrotes30%, refrigerio30%, hogar/cuidado15%, regional5%; estos porcentajes son hipótesis, ajustables por franja. SKU distintos por ticket: 1..8, distribución truncada con media objetivo3.2; cantidades por línea enteras1..4, 1 predominante. La llegada crea cesta deseada; no existe transacción de venta por una cesta completamente no atendida.

Co-compra aumenta probabilidades, no impone productos: gaseosa→papas/snack +0.15, leche→avena +0.12, café→galletas +0.12, pasta→salsa +0.20, shampoo→acondicionador +0.10. Se aplica en una sola pasada tras el SKU inicial, con probabilidad final≤0.65 y sin encadenamiento recursivo. Marcas sustitutas de la misma subcategoría compiten; no se compra siempre toda la familia. Existe co-compra de fondo aun sin vínculo. Parámetros permanecen ocultos para el entrenamiento de Market Basket, disponibles solo en truth de simulación.

Ticket conceptual: saleId/sourceEventId estable, timestamp UTC, fechaLocal, customerKey|null, paymentMethod, grossBeforeDiscount, itemDiscount, subtotalAfterDiscount, ticketDiscount=0 en primera versión, total, status, scenarioId y businessId. Línea: productKey, quantity, baseUnitPrice, discountPct, effectiveUnitPrice, costAtSale, lineDiscount y lineTotal. Calcular en céntimos y redondear una vez por línea; `total = sum(lineTotal)`. Factores numéricos usan precisión suficiente y se materializan sin ruido flotante monetario.

Pagos sintéticos: cash55%, wallet30%, card10%, bank_transfer5%; sin crédito comercial en primera versión. wallet es categoría del sistema, no se simulan transferencias reales de Yape/Plin. Venta completed equivale a cobro completo y stock descontado; pending no es venta efectiva ni decrementa stock. Objetivo1% cancelaciones y≤0.5% pending como casos controlados, adicionales al volumen de completadas. En el generador inicial las cancelaciones se resuelven el mismo día, antes del cierre; así los labels diarios no se reescriben con información posterior al origen. Una cancelación tras completed revierte cantidades/dinero con evento referenciado; nunca borrar el movimiento original. Cancelaciones posteriores al día requerirían versionado as-of y quedan fuera del generador inicial. Consumidor final no recibe documento ficticio de identidad.

## 11. Reposición, costo de stock, mermas y stockouts

Política generadora usa datos disponibles al emitir el pedido, nunca el forecast ganador del benchmark ni demanda latente futura. Apertura determinística: hasta `ceil(μ*(L+7))+SS` unidades para no perecibles; perecibles capados por vida útil. Cada apertura registra costo C y movimiento opening. No se importa una compra simulada anterior al rango para justificarla.

Al cierre: `inventoryPosition = onHandUsable + outstandingQty - reservedQty`, reservedQty=0 inicialmente. Si posición≤ROP: `orderQty = ceilToPack(max(0, targetStock-inventoryPosition))`, con targetStock `ceil(μhat*(L+R))+SS`. μhat inicial=μ de maestro y, tras28 días, media de ventas últimas 28 con nota de censura; R=7 días para no perecibles y R=1..3 para perecibles. MOQ/bulto según proveedor. Agrupar líneas por proveedor/día; no repetir un pedido abierto de la misma necesidad.

Perecibles: FEFO para stock físico, lote con receivedAt/expiryAt, cap de pedido por ventas esperadas durante vida útil; pan fresco reposición matinal diaria según media previa, descarte de sobrante al cierre. Lácteos con vida útil corta se limitan a cobertura máxima7 días. No vender producto vencido. Si la granularidad de bulto impide un cap seguro se permite no pedir y se registra la razón; no forzar sobrantes gigantes.

Primera versión: recepción completa por pedido, sin recepciones parciales. Pedido puede permanecer pendiente al corte; recepciones después del corte quedan en planificación, no movimientos realizados. Compras completed se crean al recibir, costo fijado al ordenar. Cada pago referencia la compra recibida. Proveedor analytics conserva promised/ordered/received timestamps. Diferencia demanda-vs-stock no genera compra instantánea ni aumento ficticio de stock.

Costo contable demo: promedio ponderado móvil de stock por SKU (`stockValueBefore + receivedQty*unitCost`) / (`stockBefore + receivedQty`). Guardar ese costo como costAtSale. Stock físico por lotes FEFO no se confunde con política de valoración. Ajustes/mermas disminuyen valoración con el costo vigente y se reportan aparte de COGS de venta. Cancelación recupera valor original de la línea; mantener libro de valor explícito para no revalorizar el pasado.

Stockout: requestedQty>available ⇒ soldQty=min(requestedQty,available), `lostDemandSynthetic=requestedQty-soldQty`. No stock negativo, no transaction por unidades no vendidas; sustitución probabilística por SKU del mismo grupo con stock, registrando original y sustituto sin doble conteo. Truth original no es feature de producción. Presentación: «demanda potencial no atendida simulada»; no «pérdida real» ni shortage×precio como pérdida monetaria.

Casos controlados: 4–8 SKU con episodios de retraso/agotamiento de1–3 días en el año, configurados con seed, más incidencias emergentes. Objetivo≤5% producto-día con censura y variedad de casos al corte: varios bajo mínimo, uno de baja rotación y uno sin movimiento reciente. Validar que existen; si faltan, ajustar política/config antes de congelar la versión, no insertar movimientos ad hoc tras la generación ni favorecer el test ML.

## 12. Dataset ML y objetivo

Panel diario por tenant+scenario+productKey+localDate, 29,200 filas, contiene ventas completadas netas de cancelaciones atribuibles, unidades solicitadas sintéticas separadas, stock de apertura/cierre, recepciones, mermas, costo, precio, promoción, disponibilidad y calendar keys. Cero ventas es observación válida, distinto de día ausente. Para forecasting contar unidades netas efectivamente vendidas; cancelación referencia y revierte la venta original, no crea demanda negativa en el día del reverso. En análisis de caja se respeta la fecha real del reverso.

**Target principal fijado:** unidades vendidas efectivas acumuladas en h días futuros, `y_h(t)=sum(soldUnits[t+1..t+h])`, h∈{1,7,14,28}. Ventas pueden estar censuradas por stockout: se expone esta limitación. No se promete un estimador de demanda irrestricta. Target latente simulado solo sirve a una evaluación secundaria de censura, no entra como label principal ni feature. Datos sin stockouts pueden evaluarse aparte, sin sustituir el test completo.

No se reutilizan los 31 features/M5 joblib con nuevos nombres de productos. Nueva versión contractual `pasco-demand-v1` y artefacto independiente a definir en M6.5; V2 sigue demand-v1. La cantidad de features transformados dependerá de la codificación aprobada y será metadata real, nunca una cifra copiada de V2. Artefactos solo propiedad de la aplicación, con hash/contrato/entrenamiento/corte identificados.

## 13. Features y disponibilidad al origen

Origen t es **cierre del día t**; primer objetivo es D=t+1. Convención: lag1=soldUnits[D−1], lag7=soldUnits[D−7], etc. Rolling usa exclusivamente observaciones≤t; no includes target futuro. El nombre/índice del lag se fija en contrato para eliminar ambigüedad.

| Feature o grupo | Cálculo/disponibilidad | Regla contra leakage |
| --- | --- | --- |
| productKey, categoría, subcategoría, marca | Maestros activos al origen | Codificación entrenada solo en train; categorías desconocidas con fallback |
| activeAgeDays / historyDays | Edad efectiva al origen | No usar historial futuro del producto nuevo |
| lag1, lag7, lag14, lag28 | Unidades netas de fechas anteriores a D | Missing explícito; no rellenar con ventas futuras |
| rollingMean/Sum7,14,28 / std28 | Ventana termina en t | Transformar por producto y orden temporal; test nunca actualiza hacia atrás |
| nonzeroDays28, zeroShare28, daysSinceLastSale | Ventas hasta t | Diferenciar inexistencia histórica de ventas cero |
| priceAtOrigin, priceChange28, relativePrice28 | Precio conocido en t y sus histories | No usar precio efectivo futuro realizado como dato conocido |
| promotionKnownNextH / announcedDiscount | Solo campañas anunciadas antes o en t | Promoción desconocida futura=escenario sin promoción; flag de disponibilidad |
| calendar(D), weekday/month/week, weekend | Calendario conocido | Para h>1: conteos de días/feriados/pagos en horizonte, no solamente D |
| paydayDaysNextH, monthEndDaysNextH, holidayDaysNextH | Calendario cerrado y públicamente conocido | Eventos sintéticos solo si fueron anunciados; no incorporar shock futuro |
| stockoutDays28 / availableHours28 | Señal observada de stock agotado hasta t | Truth lostDemandSynthetic prohibida en X |
| onHandUsableAtOrigin / knownInbound | Stock y pedidos efectivamente conocidos | Experimental para forecast de ventas; ablation sin stock y sin recepciones; nunca stock final futuro |
| categorySalesMean28 | Ventas pasadas agregadas del mismo tenant | Sin target encoding global ni agregados futuros; no mezclar tenants |

Opcionales posteriores: lags56/rolling56 si cobertura suficiente, no obligatorios para primera comparación. No incluir como features seed, misión secreta, popularidad secreta, uplift verdadero, ruido futuro ni ventas sintéticas latentes. Preprocesadores y selección de features se ajustan dentro de cada fold.

## 14. Forecasting: benchmark y serving

Horizontes obligatorios de benchmark: 1,7,14. 28 es experimental; 30 se pospone hasta evidencia de calidad, no se publican ambos redundantes. Cada horizonte tiene label y evaluación propios; nunca `forecast7/7` como forecast de mañana.

Baselines por SKU/origen:

1. Naive último valor: predicción diaria=soldUnits[t]; acumulado=h×ese valor.
2. Seasonal naive7: repetir la última semana conocida en orden para cada fecha del horizonte; acumular.
3. Moving average: media últimos7 y28 días; elegir ventana en validation, acumular h×media.

Candidato inicial: modelo tabular global HistGradientBoostingRegressor por horizonte directo, con loss Poisson como opción para targets no negativos y squared_error como comparación. Scikit-learn ya existe; no seleccionar ganador por nombre. Codificación categórica compatible con versión fijada del repositorio; validar límites de bins y evitar asumir comportamiento de otra versión. XGBoost/LightGBM solo experimento posterior si mejora demostrada y costo operativo justifican dependencia. No deep learning. [Documentación oficial HGB](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html).

Serving: elegir campeón por horizonte frente al mejor baseline, clip únicamente negativos a0, mantener flotante para forecast, redondear hacia arriba solo suggestedQty de inventario. Si no mejora baseline, servir baseline y explicar modelType. Categoría/subcategoría se obtiene sumando predicciones de los SKU del mismo horizonte/corte; evaluación también en esa granularidad. Unidades agregadas son paquetes heterogéneos, no kg equivalentes; dashboard monetario no se deriva de esa suma sin precios/moneda/costos explícitos.

Respuesta futura incluye asOf, trainedThrough, forecastStart/end, horizonDays, sourceScenario, modelVersion, targetDefinition, productCount y qualityStatus. Fuera del corte fijo: «proyección de la demo al 12/10/2026»; no afirmar datos live. Guardas V2 no se deshabilitan globalmente para habilitar V3.

## 15. Validación temporal definitiva

No random train_test_split. Diseño común para todos los SKU:

| Tramo | Días de observaciones objetivo | Uso |
| --- | --- | --- |
| Train | 2025-10-13..2026-06-30 | Entrenamiento; primeras28 fechas son calentamiento de lags |
| Validation | 2026-07-01..2026-08-15 | Comparación de baselines, features y pocos hiperparámetros |
| Test intocable | 2026-08-16..2026-10-12 | Informe final una vez, antes de refit de serving |

Para cada h, solo usar origen t si **todo** su label t+1..t+h cae dentro del tramo objetivo asignado. Ejemplo h7: último origen train=2026-06-23; validation=2026-06-30..2026-08-08; test=2026-08-15..2026-10-05. Los orígenes con etiquetas que atraviesan una frontera quedan fuera, no se reparten sus días entre train y test. Los lags sí pueden usar pasado del tramo anterior. h28 tiene menos ventanas de validación/test; informar cantidad efectiva, no fingir 58 orígenes completos en el test para ese horizonte.

Backtesting adicional solo en train: bloques objetivo 2026-04,2026-05,2026-06, con ventana expansiva y misma exclusión de labels cruzados. Después se selecciona configuración en validation. Para test se permite refit con train+validation **cuyas etiquetas terminan a 2026-08-15**; modelo fijo durante test. Las features de cada origen pueden usar ventas de test ya observadas en ese momento, nunca futuras: rolling-origin operativo. No reentrenar con test durante el reporte. Intervalos solapados producen errores correlacionados: reportar además orígenes semanales no solapados cuando h lo permita.

Tras congelar resultados, modelo de serving puede refitearse con toda la historia etiquetada hasta el12/10, excluyendo los últimos h orígenes sin label completo. Ese refit no recibe una nueva métrica test independiente. Forecast posterior al corte no tiene ground truth todavía; no generar futuro oculto para seleccionarlo ni inventar accuracy del futuro.

## 16. Métricas, aceptación y cold start

Métricas obligatorias sobre misma población de labels/orígenes:

- WAPE=`sum(abs(y−ŷ))/sum(y)`; si denominador 0, null y contador, no 0 ni infinity inventados.
- MAE=`mean(abs(y−ŷ))` y RMSE=`sqrt(mean((y−ŷ)²))`, unidades por horizonte.
- Bias firmado=`mean(ŷ−y)` y normalizedBias=`sum(ŷ−y)/sum(y)` cuando denominador > 0; positivo=sobrepredicción.
- Opcional sMAPE, con convención y casos 0 documentados; no elegirlo por ocultar errores.

Informar global, categoría, SKU, productos de baja demanda, censura/no censura y horizontes. WAPE global privilegia alto volumen; incluir MAE macro por SKU y cobertura para no esconder los lentos. **No accuracy=100−WAPE**, ni WAPE como confianza individual. Umbral propuesto para liberar ML h7: mejora WAPE relativa ≥ 5% respecto del mejor baseline en validation y test, |normalizedBias|≤10%, sin degradación grande y repetida en categorías críticas. Si no cumple, baseline sigue siendo resultado válido. Umbrales son gates de ingeniería sintéticos, no garantía comercial. h14/28 se publican solo con gate propio; un éxito h7 no valida h28.

Cold start:

| Historia observada por producto | Comportamiento |
| --- | --- |
| Tenant vacío | insufficient_history; no forecast numérico fingido ni prior de otro tenant |
| 0–13 días | Prior de categoría del mismo tenant si existe, ajustado por envase/precio y declarado; si no, reglas/insufficient_history |
| 14–27 días | Media móvil7/14, qualityStatus=limited_history; horizonte 7 prioritario |
| ≥28 días | Modelo global con missing flags/codificación desconocida según contrato; comparar contra baseline |
| ≥56 días y suficientes días con venta | Elegible para horizonte 14 y features 56; no implica confianza alta |
| ≥90 días | Elegible experimental 28 con evaluación propia |

Probar cold start ocultando prefijos de historia dentro de train/backtest, no añadiendo nuevos SKU al catálogo para este propósito. Productos nuevos se evalúan en holdout por producto dentro de validation si se investiga transferencia; no mezclarlo con validación temporal principal. Perfiles de categorías/marcas reales no reemplazan evidencia de demanda del negocio.

## 17. Proyección de stock e Inventory Intelligence

Stock proyectado es cálculo derivado, no un modelo ML de stock: `projectedStock[d]=onHand(t)+sum(knownExpectedReceipts≤d)−sum(forecastDaily≤d)−knownExpiryQty≤d`. Para h7 directo acumulado no se distribuye uniformemente entre días: daysOfCover/fecha estimada requiere curva diaria (modelo h1 con estrategia futura evaluada o perfil weekday histórico declarado). Si solo existe acumulado 7, mostrar cobertura aproximada `onHand/(forecast7/7)` como tasa media, sin prometer fecha exacta.

Recepciones previstas son planificación, no stock disponible ni entrega garantizada. Mostrar escenario con/sin pedidos conocidos. Fecha estimada de stockout=primer día cuya proyección no truncada≤0; almacenar déficit teórico aparte, stock físico proyectado mostrado=max(0,proyección). Si no hay curva o entradas fiables: fecha null. Con demanda diaria media 0, cobertura null/«sin demanda prevista», no número infinito. Al mismo origen, la expectativa de recepciones solo usa lo que se conocía entonces.

Inteligencia propuesta por SKU:

- μ_d y σ_d de ventas diarias últimas 28 completas; note stockout/censura. σ_L de lead time observado o prior demo si insuficiente.
- Seguridad `SS=ceil(z*sqrt(L*σ_d² + μ_d²*σ_L²))`, z=1.28 como objetivo de servicio heurístico inicial 90% **sin garantía de distribución/servicio real**; mínimo 1. En demanda intermitente usar reglas de cobertura y bandera, no fingir normalidad.
- Reorder point `ROP=ceil(μ_d*L)+SS`. Con curva forecast validada, sustituir μ_d*L por demanda prevista durante L, indicando método.
- Posición=stock útil+recepciones firmes conocidas−reservas; suggestedQty=`ceilToPack(max(0,forecast(L+R)+SS−posición))`, cap por shelf life/capacidad; separar predicción decimal y recomendación entera.
- Riesgo stockout: determinístico HIGH si cobertura<L, WATCH si cobertura<L+R, OK en otro caso; no probabilidad ML sin calibración.
- Overstock: cobertura>max(30,2*(L+R)) en no perecibles; perecibles si stock supera demanda durante vida útil. Umbral configurado y visible.
- Slow moving: edad≥60d, días con venta≤4 en últimas 30 y aún hubo alguna venta; dead stock: stock>0, edad≥60d y ninguna venta en últimos 60. Sin historial no equivale a dead stock.
- Bajo mínimo configurado es métrica operativa distinta de riesgo/ROP; no sustituir uno por otro en assistant.

La política generadora usa su regla de §11 y se congela antes del benchmark. La recomendación ML puede compararse con ella; no rehacer el histórico para que la recomendación parezca perfecta.

## 18. ABC/XYZ, margen y rotación

ABC por **consumption value**: sum(quantitySold*costAtSale) del periodo completo de 365 días al corte; moneda PEN. Orden descendente estable (empate SKU). A incluye el SKU que alcanza/supera 80% acumulado; B siguiente hasta 95%; C resto. No imponer 80% de productos en A. Total valor 0→UNCLASSIFIED. Alternativa ABC por revenue solo comparación explícita, no mezclar métodos. Para backtest ABC se recalcula con pasado, no clasificación anual futura como feature.

XYZ por coeficiente de variación de ventas semanales en las últimas 13 semanas **completas**; en corte lunes 12/10, últimas semanas terminan domingo 11/10. CV=σ/μ con población; X≤0.5, Y>0.5..1, Z>1. Media 0→NO_MOVEMENT, no dividir por0; menos 8 semanas→INSUFFICIENT_HISTORY. Mostrar además semanas cero e intervalos entre ventas porque CV es limitado para intermitencia. AX combina valor alto/estable, AZ alto/variable, CZ bajo/variable; orienta revisión/cobertura, no determina automáticamente compras.

`grossRevenue` = ventas brutas antes de descuento; `netRevenue` = grossRevenue − discounts − reversos; `COGS` = sum(quantity × costAtSale) neto de reversos; `grossMargin` = netRevenue − COGS; `grossMarginPct` = grossMargin/netRevenue si netRevenue > 0, en otro caso null. Calcular por SKU/categoría/periodo usando datos efectivamente registrados. No son utilidad neta: no se incluyen alquiler, salarios, energía ni impuesto a la renta. Precios demo de caja con IGV incorporado sin desglose fiscal: margen comercial aproximado en la misma base, no cálculo contable tributario oficial. Una vista de tickets netos de cancelación no vuelve a restar un reverso ya excluido; el libro de flujos permite medir reversos en su fecha efectiva sin doble descuento.

Pregunta «mayor margen» debe distinguir monto total vs porcentaje/unitario y periodo. Si costo ausente, margin unknown con cobertura, no costo 0 fingido. `inventoryTurnover=COGS_period/averageDailyInventoryValue` con misma base monetaria; promedio diario a costo, no stock final por precio actual. Si denominador 0, null. `daysOfInventory=daysInPeriod/turnover` cuando válido; distinta de daysOfCover basada en demanda prevista. `daysSinceLastSale` con fecha/corte y estado no-history diferenciado.

## 19. Market Basket y cross-sell

FP-Growth principal: tickets sale/completed no cancelados; representación binaria presencia por productKey, no quantity como varias ocurrencias. No incluir compras, pending, consumidor como producto ni futuras ventas. Entrenar reglas sobre train+validation; evaluar soporte/confidence/lift en test antes de publicación. Categoría/subcategoría son análisis separados, no mezclar categorías con SKU en la misma transacción porque producen reglas jerárquicas triviales.

Thresholds iniciales configurables: support≥0.01, mínimo 50 tickets de soporte, confidence≥0.20, lift≥1.20, tamaño itemset≤3, antecedente 1..2 y consequent 1. Limitar top 5 por lift y soporte, no por nombre preferido. Si una regla tiene confidence 1, señalar posible artefacto/rareza y verificar conteos; no publicarla como asociación general sin evidencia suficiente. `support=P(X∪Y)`, `confidence=P(Y|X)`, `lift=confidence/P(Y)`. No causalidad, no relación contractual con marcas.

Apriori opcional académico sobre misma matriz/mismos thresholds si tiempo razonable; comparar reglas/tiempo/memoria, no ejecutar por SKU individual. mlxtend no está en requirements actual: su incorporación, si se elige, debe justificarse y fijarse **en M6.7**, no en esta fase. [Implementación y contrato FP-Growth de mlxtend](https://rasbt.github.io/mlxtend/user_guide/frequent_patterns/fpgrowth/).

Cross-sell sencillo: para cesta actual X, recomendar Y mediante una regla validada, siempre que Y esté activo, tenga stock y no esté ya presente; máximo 3 resultados. Explicar cantidad de tickets, periodo, confidence y lift. No llamarlo predicción personalizada de un cliente ni almacenar perfiles sensibles. Hasta que M6.9 conecte skills, estas preguntas son futuras capacidades.

## 26. Customer Intelligence — contrato comercial

Objetivo: analizar ventas ya previstas, sin crear un motor de recomendación personal ni clustering. Unidad de identidad: customerCode estable del Contact registrado, no nombre, email ni ObjectId entre entornos. Solo tickets sale/completed netos de cancelaciones según §10/12. Una compra pending/cancelled no suma gasto, frecuencia ni recency. Todos los cálculos se filtran por tenant, scenario y corte.

### 26.1 Rankings y comportamiento

Periodos soportados: hoy, últimos7/30/90 días e histórico al corte. Últimos90 = 2026-07-15..2026-10-12; otros periodos conservan §6. Ranking descendente y desempate por customerCode, con criterio y ventana visibles. «Mejores clientes» usa netRevenue por defecto y permite cambiar a unidades/frecuencia; no mezcla los criterios en un score arbitrario. Consumidor final se muestra en una tarjeta de participación anónima, sin ranking, RFM ni preferencias individuales.

| Métrica por cliente registrado | Definición y límites |
| --- | --- |
| Total gastado / ranking revenue | Suma de netRevenue efectivo de sus tickets en la ventana; PEN. No utilidad del negocio |
| Unidades compradas / ranking unidades | Suma de cantidades de líneas; paquetes/envases, no equivalencia de kg/ml |
| Frecuencia / ranking frecuencia | Número de saleCode distintos completados; no número de líneas |
| Ticket promedio / ranking ticket medio | netRevenue/tickets; null si cero. Publicar n; para ranking destacado exigir al menos3 tickets en la ventana, el resto queda como muestra limitada |
| Artículos promedio por ticket | SKU distintos por ticket, promediados; separar de unidades por ticket |
| Primera/última compra | Fechas de primera/última venta efectiva observada en todo el histórico hasta el corte; no prometer vida comercial anterior al dataset |
| Días desde última compra | Diferencia de fechas calendario Lima; nunca usar createdAt técnico de carga. Sin compras: null y «sin compras registradas» |
| Categoría/subcategoría favorita | Mayor netRevenue de sus líneas en la ventana; criterio explícito. Alternativa por unidades si se solicita; empate por clave estable |
| Productos más comprados | Top5 por unidades, con SKU, nombre, gasto y periodo; no productos inferidos de otros clientes |
| Intervalo medio entre compras | Media de diferencias de timestamps de tickets ordenados dentro de la ventana, expresada en días; n<2 ⇒ null. Varias compras el mismo día pueden producir intervalo inferior a1 |
| Tendencia de gasto | Últimos30 contra30 anteriores, monto y porcentaje. Base0 ⇒ porcentaje null y «actividad nueva/sin base»; señalar si registro reciente reduce exposición |
| Promociones utilizadas | Tickets y líneas con descuento promocional registrado, descuento total y proporción de tickets; no campañas que el cliente solo pudo ver |

Primera compra y recency usan todo el pasado disponible; sumas/rankings respetan la ventana elegida. Clientes sin ventas permanecen visibles con ceros de conteo e importes y ratios/fechas null. No convertir null a cero ni afirmar que falta actividad por abandono. La condición analítica «inactivo» no cambia Contact.isActive=true ni bloquea a un cliente.

### 26.2 RFM explicable

Ventana de F y M:90 días inclusivos hasta el corte. R: días desde última compra efectiva usando todo el pasado disponible. F: tickets distintos en90 días. M: netRevenue en PEN de esos tickets. No RFM de consumidores anónimos ni mezcla de monedas. Se eligen umbrales absolutos de demo en lugar de quintiles entre solo40 clientes para que los empates no cambien segmentos artificialmente; no son benchmarks del comercio peruano.

| Score | R (menor recency es mejor) | F: tickets/90d | M: PEN/90d |
| ---: | --- | --- | --- |
| 5 | 0–7 días | ≥20 | ≥500 |
| 4 | 8–14 días | 10–19 | 250..menos500 |
| 3 | 15–30 días | 5–9 | 100..menos250 |
| 2 | 31–60 días | 2–4 | 30..menos100 |
| 1 | ≥61 días | 0–1 | 0..menos30 |

Guardar componentes crudos y rScore/fScore/mScore; mostrar razones, no solo un código. No combinar R+F+M en una probabilidad o valor de vida futuro. Sin compra histórica: R y rScore=null, estado «Sin compras»; F=0/M=0 son hechos válidos. Importes se comparan en céntimos y fronteras inclusivas definidas por la tabla.

Segmentos mutuamente excluyentes, evaluados en este orden:

1. **Sin compras:** ninguna compra efectiva hasta el corte.
2. **Inactivos:** última compra hace más de90 días.
3. **En riesgo de perder actividad:** última compra hace31–90 días; etiqueta de recencia, no predicción de churn ni causa.
4. **Nuevos:** primera compra observada hace≤30 días, última hace≤30 y hasta4 tickets en90 días.
5. **Clientes más valiosos:** rScore≥4, fScore≥4 y mScore≥4.
6. **Frecuentes:** R≤30 y fScore≥4, sin cumplir el segmento anterior.
7. **Potencialmente leales:** R≤30 y fScore2–3; etiqueta de regla demo, no propensión ML.
8. **Ocasionales activos:** R≤30 y los restantes casos.

Los nuevos con alta frecuencia pueden pasar a frecuente/valioso; un cliente de gran gasto antiguo puede quedar en riesgo. Counts de segmentos suman40, incluido «Sin compras». Detallar en cada respuesta ventana90d, recency y umbrales relevantes. No comunicar ofertas automáticamente ni crear campañas a partir del segmento.

Si no hay cliente elegible, consumidor final; no añadir ventas para cumplir un perfil. Cada cliente tiene dos categorías preferentes y pesos suaves reproducibles; el resto conserva probabilidad positiva. Auditoría: variedad de tickets/intervalos/ticket medio, primeras/últimas compras, personas nuevas y personas sin actividad reciente; no40 copias con nombres diferentes.

### 26.4 Preferencias frente a Market Basket

FP-Growth sigue usando tickets globales, incluidos los anónimos. Preferencia de cliente es agregación de **sus** tickets por categoría/producto, con n y ventana. No correr FP-Growth independiente para cada persona con escasa muestra ni aplicar una regla global como una preferencia demostrada de Ana. «Qué suele comprar X» usa top productos/categorías observados y resuelve el nombre por0/1/N candidatos.

Queries futuras: «¿Quiénes son mis mejores clientes?», «¿Quién gastó más este mes?», «¿Qué cliente compra más gaseosas/bebidas?», «¿Cuáles son mis clientes frecuentes?», «¿Cuándo compró por última vez X?», «¿Qué suele comprar X?», «¿Qué clientes no compran hace30 días?» y «¿Cuál es mi cliente más frecuente?». El ejemplo «Ana Torres» no crea un cliente: si no coincide con una ficha real del tenant, aclarar/no encontrado. Consultas estructuradas ⇒0 LLM; síntesis opcional solo a partir de estas métricas.

## 27. Supplier Intelligence — compras, ofertas y dependencia

Dos perspectivas separadas: **oferta configurada** (qué puede abastecer) y **recepción observada** (qué compró/recibió el negocio). Identidad supplierCode, filtrada por tenant/scenario; proveedor nunca elegido por coincidencia de nombre de otro entorno. Consumer/customer no se considera proveedor. No score único de proveedor.

| Métrica por proveedor y periodo | Definición |
| --- | --- |
| Monto comprado / ranking gasto | Suma de costos efectivos de recepciones completed netas de cancelaciones; PEN. Mostrar valor pedido pendiente aparte |
| Unidades compradas / ranking volumen | Sumatoria de paquetes/envases recibidos; no comparar como peso equivalente entre SKU |
| Órdenes / ranking órdenes | purchaseCode de pedido distintos emitidos en ventana, incluidos estados desglosados; número de recepciones aparte, sin doble conteo |
| Frecuencia / última orden | Intervalo medio de orderedAt; n<2 ⇒ null. Último pedido y última recepción con fechas propias |
| Categorías y productos | Con oferta activa y con recepción en periodo, conjuntos etiquetados por separado |
| Costo medio por producto | sum(receivedQty*effectiveUnitCost)/sum(receivedQty), para mismo productKey y moneda; sin recepciones ⇒ null, no costo de catálogo fingido |
| Evolución de costo | Precio histórico de oferta anunciado y costo de órdenes realizadas, con fechas, bases y porcentaje; sin base previa, unknown |
| Lead time | receivedAt−orderedAt en días, promedio/mediana/σ sobre recepciones completas; pendientes excluidos; indicar n |
| Puntualidad | receivedAt≤promisedAt; numerador puntuales/denominador recibidos con ambas fechas; fechas faltantes reducen cobertura |
| Retraso | max(0,receivedAt−promisedAt), promedio entre retrasados y tasa de retraso; mostrar ambos, no inferir causalidad |
| Fill rate | ΣreceivedQty/ΣorderedQty de órdenes cerradas, por SKU o envases con advertencia; n y estado visibles |
| Dependencia | Participación del proveedor en gasto/órdenes, SKU sin alternativa activa y productos críticos afectados |

Periodos por defecto30 días y alternativas7/90/histórico. Rankings de puntualidad/lead time requieren≥5 recepciones con timestamps completos para destacarse; con menor n mostrar muestra limitada sin declarar ganador fiable. «Mayor retraso» distingue promedio de días y número de órdenes; «menor costo» se calcula para un producto específico, nunca promediando productos diferentes. Ranking por categoría filtra líneas/órdenes vinculadas a esa categoría, no todas las compras del proveedor.

Fill rate de primera versión: §11 solo tiene recepciones completas; órdenes cerradas cumplidas dan100%. Es una consecuencia del diseño, **no prueba de excelencia logística**, y no aporta ranking si todos empatan. Pedido pendiente: mostrar cantidad ordenada y pendiente; «vencido» si promisedAt pasó y no se recibió. No incorporarlo como fill rate terminal ni recepción con quantity0. Recepción parcial permanece fuera del generador inicial; si se habilita luego, exige quantityReceived/cancelled/remaining por línea y nuevas invariantes.

### 27.1 ProductSupplierOffer lógico y compatibilidad

V3 **sí permite múltiples ofertas por producto**, conservando el diseño de80 principales y aproximadamente24 segundas de §4. ProductSupplierOffer es un contrato lógico, no decisión de crear otra colección ahora:

| Campo | Regla |
| --- | --- |
| offerKey | scenarioId + productKey + supplierCode + effectiveFrom; versión temporal estable |
| supplier / product | Códigos estables canónicos; referencias locales resueltas dentro del tenant |
| purchasePrice / currency | Coste por unidad vendible, céntimos PEN; no cotización confirmada |
| leadTimeDays / variabilityDays | Plazo informado por oferta o fallback declarado a ficha de proveedor |

Preservar descripción humana, 0/1/N y consulta contextual del producto.

### 27.2 Dependencia de abastecimiento

- `singleSourceProductPct` = SKU activos con exactamente1 oferta activa / SKU activos con al menos1 oferta activa. Mostrar ambos conteos; productos con0 ofertas son brecha separada, no desaparecen del reporte.
- `singleSourceBySupplier` = número/lista de SKU activos cuya única oferta pertenece a ese proveedor. Para ofertas alternativas inactivas o vencidas no contar cobertura.
- Productos críticos: A de ABC **o** riesgo stockout HIGH del snapshot; ambos métodos/cortes documentados. `criticalWithoutAlternative` es intersección con single-source, no predicción causal.
- Participación de gasto = compras recibidas del proveedor / compras recibidas de todos en la misma ventana y moneda. Total0 ⇒ porcentaje null. Participación de órdenes usa denominador de órdenes distinto y explicitado.
- Productos suministrados alguna vez no equivalen a disponibilidad actual; dependencia se calcula con ofertas vigentes.

«12 productos dependen de X» solo es válido si el conteo observado es12; no será un valor fijo de la demo. Queries futuras: «¿A qué proveedor le compro más?», «¿Con cuál gasto más?», «¿Qué proveedor entrega más rápido/se retrasa más?», «¿Qué productos dependen de un solo proveedor?» y rankings por categoría. Sin datos de entregas no inventar puntualidad.

## 28. Snapshot integral del negocio y comparaciones

Snapshot conceptual **business-health-v3**, asOf=2026-10-12 al cierre Lima, datasetVersion y modelVersion visibles. Agrega seis dominios existentes/propuestos sin duplicar fuentes de verdad. Cada bloque indica ventana, coverage, status y evidenceRefs; faltantes son UNKNOWN/INSUFFICIENT_HISTORY, no ceros ficticios. «¿Cómo está mi negocio?» usa el snapshot completo disponible, con prioridades explicables; no se afirma haber analizado dominios no consultados.

| Dominio | Contenido mínimo |
| --- | --- |
| Ventas | netRevenue hoy/7d/30d, variación, unidades, tickets, ticket medio; grossRevenue/descuento/reversos como detalle |
| Rentabilidad | COGS, grossMargin/Pct y cobertura de costo; top productos/categorías por monto y porcentaje diferenciados |
| Inventario | Valor útil a costo al corte, bajo mínimo, riesgo stockout/overstock, slow/dead stock, daysOfCover y métodos |
| Forecast | Horizonte/corte válido, proyección próxima, crecimiento frente a periodo comparable observado, productos/categorías destacados y recommendedQty separado |
| Clientes | Registrados activos30d (≥1 ticket), nuevos30d (primera compra), recurrentes30d (≥2 tickets), top, RFM90d/en riesgo/inactivos; participación anónima aparte |
| Proveedores | Compras recibidas recientes, gasto por proveedor, órdenes pendientes/vencidas, retraso, lead time/n y dependencia |

Clientes activos/nuevos/recurrentes pueden solaparse: no sumar esas tarjetas como personas distintas. Los segmentos RFM sí son exclusivos. «No compran hace30 días» filtra última compra>30d y separa sin compras; no cambia el umbral RFM de inactivo>90d.

Crecimiento esperado de forecast7: `(forecastUnits13..19Oct - observedUnits6..12Oct)/observedUnits6..12Oct`; fecha y diferencia **predicción vs observado** explícitas. Base0 ⇒ diferencia absoluta y porcentaje null. No mostrarlo como crecimiento realizado ni comparar un forecast7 con un mes completo; h1 se compara con día comparable. La cifra puede ser baseline, se muestra el método real. Reposición incluye costo/ofertas cuando disponibles, nunca pérdida financiera estimada por shortage×precio.

Comparaciones al corte fijadas:

| Ventana | Base comparable |
| --- | --- |
| Hoy12/10 | Día anterior11/10 como cambio diario, y lunes05/10 como weekday comparable; indicar cuál |
| Últimos7:06..12/10 | 29/09..05/10, siete días completos |
| Últimos30:13/09..12/10 | 14/08..12/09, treinta días completos |
| Mes a fecha01..12/10 | 01..12/09, doce días completos, no septiembre completo |
| Semana a fecha lunes12/10 | Lunes05/10 hasta hora de corte equivalente; en snapshot de cierre es un día completo |

Todos los timestamps usan UTC en persistencia, calendario Lima en analytics. Si una futura vista es intradía, ambos extremos se limitan a la misma hora local o se declara la falta de comparación; no normalizar silenciosamente un día parcial contra uno completo. Variación=`(actual-base)/base` si base>0; con base0, porcentaje null. Fechas siempre acompañan «actual», «anterior» y «próximo».

Queries añadidas: «¿Cómo va mi negocio?», «¿Cómo fueron mis ventas esta semana?», «¿Qué categoría me genera más margen?» y «¿Qué productos tengo que reponer primero?», además de §26/27. Primera versión sin health score ni supplier score. Síntesis LLM opcional interpreta solo hechos/evidencia; métricas, rankings y RFM no requieren LLM.

## 29. Requisito obligatorio de paridad LOCAL ↔ MongoDB Atlas

**Un dataset lógico, dos cargas.** El generador produce un paquete canónico versionado una vez y ambos entornos consumen ese mismo paquete aprobado. Reejecutar el generador con inputs idénticos sirve para comprobar reproducibilidad, no para regenerar una variante cloud. No ajustar stock, precio, fecha, perfiles o promociones al importar en Atlas.

Flujo lógico: `Generator V3 → Canonical Scenario → Local Mongo / MongoDB Atlas`. Artefactos ML se entrenan a partir de ese Canonical Scenario; no a partir de una extracción cloud diferente. Comparación obligatoria: **canónico↔local**, **canónico↔Atlas** y **local↔Atlas**; que los dos imports repitan el mismo defecto no produce PASS.

| Producto | productKey=`v3.`+SKU; SKU único por tenant |
