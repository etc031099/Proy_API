## Defectos locales reproducidos y corrección

### Rechazo de una respuesta LIVE parcial legítima

El adapter ML LIVE existente (v3_live_inventory_supplier.py) puede devolver:

```json
{
  "availabilityStatus":"PARTIAL",
  "items":[{
    "stock":{"onHand":21},
    "risk":{"level":null,"reasonCodes":["LIVE_FORECAST_REQUIRED"]},
    "recommendation":{"recommendedQty":null,"shouldReorder":null,"status":"LIVE_FORECAST_REQUIRED"}
  }]
}
```

Con envelope PARTIAL y metadata válida, el backend previo exigía siempre un entero
en recommendedQty. Lanzaba ML_SERVICE_UNAVAILABLE al validar la fila, antes de
añadir hechos al contexto. La reproducción previa confirmó Inventory FAILED.

Ahora solo admite el null explícito si es LIVE, el envelope y availabilityStatus
son PARTIAL y la recomendación lleva LIVE_FORECAST_REQUIRED con shouldReorder=null.
Conserva null y stock, sin inventar cantidad cero ni recomendar reposición.
Null sin esta procedencia se sigue rechazando; expone código sanitizado
INVENTORY_RESPONSE_INVALID e internalCause=AGENT_SKILL_VALIDATION_ERROR.

Esta incompatibilidad está demostrada localmente, pero **su presencia en la
respuesta cloud incidente sigue NO CONFIRMADA**. No se debe presentar como causa
cloud probada.

### Fail-fast descartaba hechos independientes

El handler hacía break ante excepción o estado no admitido. Se reprodujo que un
fallo de Inventory impedía ejecutar Supplier. Ahora continúa las tareas
independientes; omite Forecast en un plan inventory-first si no hay candidatos de
Inventory, para no sustituirlos por otro ranking global. Conserva hechos parciales
verificados. Si hubo un fallo, PARTIAL, NO_DATA o dependencia ausente, no sintetiza.

Política mínima de evidencia: todas las tareas requeridas completas y alguna
evidencia READY con facts. No se habilitan recomendaciones basadas en una
combinación incompleta. Una respuesta parcial no se interpreta como éxito completo.
