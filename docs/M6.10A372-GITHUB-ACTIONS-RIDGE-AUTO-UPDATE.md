# A.3.7.3 — Automatización del worker Ridge

## Alcance

El workflow `Forecast Ridge automatic update` reutiliza exclusivamente
`backend/scripts/run-v3-ridge-worker-cloud.js`: preflight `--check` y, si pasa,
`--run`. No inicia Render, frontend, Docker ni servicios web. No usa bootstrap,
seed, promoción forzada ni modifica la política de 107 origins o el horizonte 1d.
No implementa el futuro botón de la aplicación.

Node 22 y Python 3.12 en Ubuntu. El archivo
`ml/requirements-forecast-worker.txt` contiene solo los seis paquetes directos
del grafo de imports del trainer/preflight, con los pins de `ml/requirements.txt`.
Las dependencias transitivas las resuelve pip. Python se obtiene mediante
`sys.executable`; no depende de una ruta Windows.

## Configuración manual en GitHub

1. Publicar posteriormente estos archivos en la rama por defecto `main`.
2. Repositorio → Settings → Secrets and variables → Actions → New repository secret.
3. Crear, con los valores cloud aprobados, estos cuatro repository secrets:
   - `FORECAST_CLOUD_MONGO_URI`
   - `FORECAST_CLOUD_EXPECTED_DATABASE`
   - `FORECAST_CLOUD_EXPECTED_BUSINESS_ID`
   - `FORECAST_CLOUD_EXPECTED_SCENARIO_ID`
4. No crear un secret `FORECAST_TRAINING_PYTHON`: el workflow establece el
   ejecutable Linux del runner. No copiar secretos en YAML, issues o logs.
5. Actions → Forecast Ridge automatic update → Run workflow → rama main →
   mode `check`. Comprobar preflight PASS y el resumen.
6. Para un ciclo manual completo, Run workflow → mode `run`. Cada schedule
   ejecuta automáticamente el ciclo completo después de pasar el preflight.

Los secretos solo se entregan por env a los dos pasos CLI, no a la instalación
de dependencias. Permisos GitHub: `contents: read`. No se suben artifacts con
reportes; el Step Summary proyecta únicamente enums, fechas y números permitidos.

## Programación y exclusión mutua

Cron UTC: `17 */6 * * *` (00:17, 06:17, 12:17, 18:17 UTC).
En Perú: aproximadamente 19:17 del día anterior, 01:17, 07:17, 13:17.
GitHub puede retrasar u omitir ejecuciones programadas bajo carga: no es una
garantía de puntualidad ni un servicio 24/7. Se usa el minuto 17 para evitar la
concentración de cron al inicio de hora. Schedule utiliza la rama por defecto;
este job permite solo main. En repositorios públicos GitHub puede deshabilitar
schedules tras 60 días sin actividad. Revisar también permisos, políticas y
cuota de Actions del repositorio.

Concurrency estática para el único tenant/scenario productivo del repositorio,
`cancel-in-progress: false`: serializa ciclos sin interrumpir el que entrena.
GitHub puede reemplazar un run pendiente por uno más reciente; la durabilidad
del trabajo está en el outbox, no en una cola de runs de GitHub.
Lease/fencing del worker siguen siendo la segunda capa contra otro invocador.

Job: 30 minutos; cada CLI: máximo 10 minutos del paso, watchdog interno de
8 minutos/ciclo; entrenamiento: 120 segundos/trabajo. Máximo un trabajo por
horizonte, dos por ciclo. No hay retries añadidos ni reducción de madurez.

## Resultados y evidencia

La CLI conserva su exit code: espera, falta de historial, rechazo metodológico
y promoción son SUCCESS; fallo técnico es FAILURE. Si preflight falla,
`--run` no se ejecuta. El resumen sanitizado se intenta incluso ante fallo.
No reemplaza los códigos funcionales del worker ni cambia elegibilidad.

Con el estado validado (dataVersion 83, pending=false, 0/107 origins), se espera
SUCCESS: ambos horizontes `NO_PENDING_WORK`, ACTIVE v1 sin cambios. No se espera
entrenamiento ni promoción. La fecha `closedThrough` depende del día del run.
Si después hay pendientes elegibles pero no madurez suficiente para promoción,
se conserva ACTIVE y se reporta `NO_PROMOTION_INSUFFICIENT_HISTORY`.

Guardar URL del run, commit usado, evento schedule/workflow_dispatch, fecha UTC,
conclusión y Step Summary por 7d/14d (pending, decisión, dataVersion,
closedThrough, versión ACTIVE y origins). No guardar secretos ni bytes de modelo.
Para comprobar programación, verificar YAML en main y un run cuyo evento sea
`schedule` después de la siguiente ventana. Un run manual exitoso no demuestra
por sí solo que ya ocurrió una ejecución automática.

Esta fase prepara automatización; no la activa desde Codex, no configura secretos
y no ejecuta cloud. La demostración de promoción requiere datos elegibles y que
el candidato pase la política vigente; no se promete una nueva versión por run.

La conectividad Atlas debe permitir el runner conforme a la política de red
aprobada: los secretos correctos no evitan un bloqueo de red/IP. No se cambia
la allowlist en esta fase ni se recomienda abrirla globalmente. Un fallo de
conexión debe fallar el preflight, sin iniciar el worker.
