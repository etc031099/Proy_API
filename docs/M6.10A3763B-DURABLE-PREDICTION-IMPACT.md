# A.3.7.6.3b — Durable model-attributed prediction impact

## Snapshot decision and causal boundary

The existing V3 snapshot builder reads operational revision, projections, ledger
stock and journal sections inside a Mongo snapshot transaction. Its canonical
snapshotHash excludes capturedAtUtc/payloadBytes. Operational documents remain
mutable and the journal does not promise complete arbitrary historical snapshot
reconstruction. A revision ID alone is therefore not evidence of identical inputs.

The RUN orchestrator pins a snapshot before the first eligible runEligible call,
before fitting or promoting either horizon. The snapshot transaction completes,
then a separate Execution writeVersion CAS stores the pin before work continues.
There is no transaction spanning snapshot capture, training and promotion. New
operations between those points are excluded from the frozen in-memory copy.
If capture or its durable write fails, promotion can proceed but a subsequent
report without a pin is NOT_CAPTURED. No snapshot may first be pinned after a
confirmed promotion. Capture is attempted once for that execution attempt.

The comparison is conditional on the pinned start-of-cycle evidence, not a
measurement of realized sales or business improvement. Training can observe a
later operational revision; that does not replace the scoring snapshot. Both
exact model versions still receive identical scoring inputs. The pin identifies
the actual comparison revision separately from trainedDataVersion.

## Durable evidence and storage

`ForecastMlUpdateExecution.impact.prediction` embeds:

- kind=MODEL_ATTRIBUTED_IMPACT; no operational-change attribution is implemented;
- snapshot business/scenario, dataVersion, asOf, capturedAtUtc,
  observationsClosedThrough, canonical snapshotHash and historical source hash;
- sorted unique product universe with sku/productName and its SHA256;
- exact before/after 7/14 version set, deterministic idempotencyKey;
- compact per-SKU p7/p14 old/new/delta/deltaPct/direction and summary;
- finalizedAt and optional safe capture failure reason.

No snapshot body, operational transactions, stock ledger, feature matrix,
historical series, artifact bytes, customer data or raw exceptions are persisted.
The full snapshot exists only in worker memory and internal subprocess stdin.

Bounds: maximum 200 products, maximum 256 KiB JSON per prediction impact.
Oversized universes fail explicitly with IMPACT_SIZE_LIMIT; no slice/truncation.
There are at most 20 existing attempt records. Keeping bounded impact copies in
attempts plus the current report remains comfortably below Mongo's 16 MiB limit.
No new collection/index is required. New fields are optional for old documents.
Future inventory summary/detail can be added as optional impact siblings without
a destructive migration; no inventory values are computed in this subphase.

## Comparison and summaries

The internal 3a loader reads exact captured versions, verifies provenance and
bytes, and keeps public serving ACTIVE-only. Its optional internal partial mode
isolates a missing/invalid artifact to its own horizon and retains other valid
comparisons. No max-version lookup or substitution is used.

The internal Python CLI validates one V3OperationalSnapshot and creates one
canonical LiveV3Context for both horizons. The 3a scorer builds features once per
SKU and uses canonical Ridge scoring for old/new. Canonical local sources retain
their existing integrity checks. No trainer, Inventory evaluator or public
endpoint is called. Artifact transport is base64 only in internal stdin.

delta=new-old; deltaPct=(100*delta)/old when old!=0, else null. Values are raw
canonical prediction units; display rounding and minimal-change thresholds are
not applied. Null is never zero. Directions are exactly UNCHANGED/INCREASED/
DECREASED/NOT_COMPARABLE. Nonfinite/negative scoring outputs are rejected.

The detail always preserves the pinned SKU universe. comparableProductsCount
counts products comparable in BOTH horizons. predictionChangedCount and
predictionUnchangedCount partition that set; notComparableCount accounts for the
remainder. Per-horizon increased/decreased/unchanged/notComparable counts each
sum to totalProductsEvaluated, so partially available changes remain visible.

For mixed results, an unchanged companion model is used only when the history
explicitly captured equal positive versions with activeChangeSource=NONE and a
non-promotion decision. The execution can be PARTIAL while prediction impact is
COMPLETE if both horizons are fully comparable. Missing companion evidence
produces PARTIAL when at least one comparison is available.

## Idempotency, completion and failure

The key is SHA256(canonical({executionId, snapshot:pin, versions:[7,14]})). It is
based on the fixed fingerprint/universe/revision and exact versions, not a
timestamp alone. Domain finalization derives all deltas/summaries itself from
validated scoring rows and updates the existing document through writeVersion
CAS. Two calculators can score concurrently, but only one commits the final
report. Retries return the stored result without appending/replacing SKU rows.
Finalized prediction data cannot be reset via the generic impact status setter
or erased to start a new GitHub attempt of that promoted execution.

The existing promotion transaction still atomically records confirmed promotion
and impact=PENDING. Post-cycle calculation occurs only after terminal execution
audit. Promotion stays PROMOTED/PARTIAL regardless of report outcome:

- no promotion: NOT_APPLICABLE;
- both horizons comparable for all SKUs: COMPLETE;
- some comparable evidence: PARTIAL;
- no reconstructible/comparable evidence: NOT_CAPTURED.

Codes include SNAPSHOT_NOT_AVAILABLE, SNAPSHOT_MISMATCH,
BEFORE_MODEL_NOT_AVAILABLE, AFTER_MODEL_NOT_AVAILABLE, ARTIFACT_INTEGRITY_FAILED,
PARTIAL_HORIZON_COMPARISON, IMPACT_SIZE_LIMIT, IMPACT_SCORING_FAILED and
IMPACT_SCORING_INVALID. Database unavailability can leave PENDING; the worker
does not falsely report that a final audit write succeeded.

## Recovery

On a duplicate RUN, the original promoted execution/version set is retained and
its report is recovered. This includes legacy promoted executions without a pin,
which become NOT_CAPTURED rather than being repinned to today's evidence.
Each normal RUN also checks at most one older scoped terminal PENDING execution
using existing history indexes, a five-second query bound and no new lock/queue.
This is never invoked by CHECK, STATUS, GET active/status/diagnostics or history.

If the original in-memory snapshot survives, it is reused even if new operations
arrive. After restart, read the current revision first. If it differs from the
pin, stop without building/scoring today's snapshot. If equal, rebuild with the
original asOf/capturedAtUtc and require identical complete metadata fingerprint,
closure and product universe. Any mismatch is NOT_CAPTURED. No reconstruction
capability beyond that is claimed; no new operational evidence is substituted.

Recovery here handles terminal PROMOTED/PARTIAL executions. A hard-killed RUNNING
execution still requires the existing lease/attempt recovery to establish a
terminal result; impact must not finalize while another horizon may still
promote. A higher GitHub attempt can close the interrupted lifecycle and recover
impact without erasing confirmed horizon results.

## Runtime limits and release

Audit subprocess: configured FORECAST_TRAINING_PYTHON, module
ml.service.v3_ridge_prediction_impact, repository root cwd, 45-second timeout,
32-MiB stdin and 512-KiB stdout bounds; raw stderr is discarded. These bounds do
not change existing training/job/cycle timeouts, eligibility or promotion policy.
Normal reads get no additional scoring latency. All fit/promotion mechanisms,
1d non-approval, public ACTIVE-only serving and Inventory formulas are unchanged.

Publication/deploy are not performed. Eventually align backend and the code
checked out by GitHub Actions. No cadence/workflow/secret change is required.
The audit CLI executes on the runner; no ML HTTP endpoint or frontend change
requires a service deploy in 3b itself.
