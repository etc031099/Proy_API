# M6.9F.4E — LIVE Forecast and Business Health

## Scope and status

This phase enables LIVE forecast, forecast-backed inventory policy metrics, and
LIVE Business Health for the existing V3 serving contract. It does not change
the frozen historical forecast path, forecast bundle, training, benchmark,
Mongo/Atlas, frontend, or cloud deployment.

## MA28 LIVE contract

- Source: the approved `MOVING_AVERAGE_28` strategy and frozen history through
  `2026-10-12`, overlaid with `LiveV3Context.closed_sales_by_product_day`.
- For operational date D, the forecast window is exactly 28 consecutive
  calendar dates ending D-1. The end date is capped by the snapshot's certified
  `observationsClosedThrough`; a missing day makes the window incomplete.
- A certified CLOSED day with zero units contributes a real zero. Missing
  certification is not converted to zero. Current D's partial transactions are
  excluded from MA28.
- `expectedUnitsNext1d` means total expected demand for D, not the remaining
  demand for the rest of today. Existing cumulative 1/7/14-day semantics and
  coherence are retained. Horizon 28 remains `UNSUPPORTED_HORIZON` (422).
- Detail/compare requires a resolved SKU and a complete window; otherwise the
  stable functional errors are `AMBIGUOUS_ENTITY` (409) or
  `INSUFFICIENT_HISTORY` (422). New post-cutoff products report `COLD_START`;
  no prior is invented. Batch/rank/summary can retain ready rows and identify
  unavailable rows as `PARTIAL`.
- Category/subcategory filters are not part of the current `ForecastRequest`
  schema; no new hierarchy or request fields were introduced.

Historical transaction cancellations after cutoff are projected once onto the
original frozen sale date and line SKU. They do not mutate the canonical bundle.
The cache key contains business, scenario, `dataVersion`, snapshot hash,
operational date, request scope/horizon, and engine version. Cache entries are
bounded and guarded by a lock; cached row data is not mutated by response
filtering.

## Inventory completion

The LIVE inventory adapter obtains forecast rows from the same immutable live
context, then delegates replenishment calculations to the existing M6.6
`evaluate_sku` implementation. Expected demand, cover, safety stock, ROP,
recommendation, overstock estimate, and risk therefore use existing formulas,
thresholds, lead-time rules, pack sizes, and MOQ. The adapter's cache is keyed
by the full context/revision and forecast availability, not request filters, so
summary/detail/rank views reuse the same full 80-SKU projection.

At least 14 observable availability days are required for demand variability.
Lead time uses eligible observed receipts first, then approved existing product
and supplier configuration. If required lead variability is absent, dependent
policy/risk fields remain unavailable; absence is no longer coerced to zero
variability. Stock and configured minimum remain available independently.
Historical purchase/sale/cancellation state remains read-only and ledger stock
remains authoritative.

## LIVE Business Health

Health composes LIVE Business, Customer, Inventory, Supplier, and MA28 Forecast
from the same snapshot/revision, and reads the existing M6.7 Market Basket
artifact frozen at `2026-10-12`. It does not recalculate basket mining, include
LIVE tickets in MBA, or invent a composite score. Existing rule-based insights
are reused; unsupported overstock-value alerts are omitted when value evidence
is unavailable. Health reports `AVAILABLE` versus `PARTIAL` using missing
forecast and inventory-policy evidence as well as other domain availability.

Each section exposes domain freshness/source and engine version where
available. Forecast freshness includes `observationsThrough`, approved source,
strategy, and horizons. The Market Basket section explicitly retains its
historical cutoff. Historical requests continue through the existing historical
runtime methods.

## Serving and readiness

`POST /v3/intelligence/forecast` and `POST /v3/intelligence/health` now dispatch
LIVE requests to their adapters. Existing auth, tenant/snapshot validation,
payload limits, and V1/V2 routes are unchanged. Readiness reports Forecast and
Health LIVE only when their composed adapters are available; Health also
requires Business/Customer and the existing health engine. Errors remain
functional (for example unsupported horizon and insufficient history), not
fabricated numeric results.

## Local fixture performance and memory

Measured after loading the existing canonical runtime (80 SKUs) and using a
synthetic, certified one-day LIVE snapshot. First call is separated from five
warm calls; these are local engineering observations, not an SLA:

| Domain | First call | Warm median | Warm p90 | Warm max |
|---|---:|---:|---:|---:|
| Forecast summary | 7.01 ms | 0.03 ms | 0.05 ms | 0.06 ms |
| Inventory summary | 170.70 ms | 0.03 ms | 0.05 ms | 0.06 ms |
| Business Health | 1,386.11 ms | 390.47 ms | 404.98 ms | 408.54 ms |

The process measured 148.59 MiB baseline RSS, 372.48 MiB after loading the
runtime, 378.79 MiB after Health, and 374.34 MiB after Inventory. The Health
first-request sampled peak was about 379 MiB in this run, below the previously
reported approximate 512 MiB cloud limit. Measurements vary by host and do not
include cloud cold start or process-family overhead.
