## Why J.2J was insufficient

J.2J only removed markers `1.`–`3.` / `1)`–`3)` at line starts, optionally after a
Markdown bullet. Other occurrences still reached the digit extractor, including
parentheses, brackets, hashes, numeric ordinals, prose entity indices, array indices
and E1/E2 embedded in prose. Thus identical rejected numbers can have different
origins; `[1,2]` alone cannot prove a list-marker root cause.

Before production changes, 28 audit tests ran: 22 PASS and 6 reproduced false
positives for leading `(1)`, `(2)`, `[1]`, `[2]`, `#1`, `#2` with product prose.
Audited ambiguous/metric examples remained rejected: “producto 1/2”, “opción 1/2”,
“los puntos 1 y 2”, “1 y 2”, “1º/2º”, “n.º 1/2”, “primera opción (1)”, numeric
evidence citations, array indices and actual quantities. E1/E2 prose was subsequently
added explicitly: those digits also reach the extractor, but are not presumed to be
the actual historical cloud cause.

## Minimal acceptance change

J.2J's existing line markers remain supported. Additional parenthesized, bracketed
or hash labels are omitted only at the start of a line (optional Markdown bullet
and <=3 spaces), use indices 1–3, and are followed by spaced prose. A following
bare quantity or unit/entity count (unidad/es, proveedor/es, producto/s, days,
weeks, tickets and package units) prevents omission; e.g. `(1) unidad` or `[2]
proveedores` remain grounded claims. Digits elsewhere in the body are always scanned.

Inline “Según el punto 1”, “productos 1 y 2”, `(1)` citations, `items[1]` and E1/E2
in prose are not automatically accepted. Classification is diagnostic, not permission.
They still need numeric facts; the prompt instead forbids these forms in prose.
Quantities 1/2/40, unsupported percentages 80/25, unknown stock and invented numbers
remain rejected when absent from cited facts. Product names/presentations, decimal
locale, existing rounding and evidence scoping remain unchanged.

## Shared prompt hardening

The provider-neutral grounded system instruction now explicitly requires short
prose in interpretation/advisoryRecommendation, with no numbered lists, numeric
indices or numbered evidence references inside strings. Products must be identified
by names or SKU; evidence references remain in the structured evidenceRefs field.
This applies to every provider using the grounded path, not a DeepSeek-only adapter.

The schema and json_object mode are unchanged, as is max output 300. The instruction
adds prompt text; the next call's input usage must be observed, not assumed to remain
1705. Pricing, provider usage/cost handling, context builder and routing are unchanged.

## Sanitized diagnostics

UNSUPPORTED_NUMBER still carries validationField and unsupportedNumbers. It now
also carries up to three `{value, pattern}` entries in unsupportedNumberDetails,
aligned with the first occurrence of each distinct rejected value. Classification
looks only at bounded nearby syntax internally; nearby text never leaves the validator.

Allowlisted patterns: LINE_LIST_MARKER, PAREN_INDEX, BRACKET_INDEX, HASH_INDEX,
ORDINAL_INDEX, ENTITY_PRESENTATION, QUANTITY_WITH_UNIT, PERCENTAGE, DECIMAL_METRIC,
STANDALONE_NUMBER, UNKNOWN_CONTEXT, EVIDENCE_REFERENCE. ENTITY_PRESENTATION is
reserved; a valid recognized package occurrence is removed before rejection and
does not produce a rejected-value detail. Context labels are syntax hints, not
claims that an entity or fact was verified.

Public/history projection and logs allow only finite numeric values with magnitude
<=1e9 and allowlisted pattern names; extra fields, text, secrets and unknown patterns
are discarded. Details require UNSUPPORTED_NUMBER and a matching unsupportedNumbers
entry. The UI shows these in the existing expandable diagnostic, never as raw prose.
