# M6.9I.1 — Telegram V3 integration audit

## Scope and outcome

This phase audits the existing Telegram integration and improves the low-stock
message only. V3 assistant conversations and READ queries do not send Telegram
messages. No real Telegram request, business write, Mongo/Atlas operation, or
cloud deployment was performed for this work.

There are two separate notification mechanisms; they must not be conflated:

1. The legacy minimum-stock notifier sends a direct Telegram message when a
   committed stock change crosses the product's configured minimum.
2. Custom `StockAlertRule` events use the durable InventoryAlert outbox,
   Node-RED receipt, and separately deduplicated Telegram channel delivery.

Node-RED's existing inbound command bridge is legacy functionality. It is not
a V3 assistant integration and was neither added nor changed here.

## Minimum-stock notification

### Trigger and exact threshold

`notifyLowStock(businessId, product, previousStock)` is called after a
successful sale transaction, a successful manual stock update, or a purchase
cancellation that reduces stock across the minimum. The condition is a
crossing from `previousStock > product.minStockLevel` to
`product.stock <= product.minStockLevel`. Equality is included. The threshold
is `minStockLevel`, not `reorderPoint`; no formula or threshold is recalculated.
Historical sales/imports/cancellations suppress the direct live notification.

For a sale, stock/product/movement writes are committed by
`transactionWriteService.writeTransaction` before the controller schedules the
Telegram send. For manual stock updates and purchase cancellation, the Mongo
transaction commits before the send is scheduled. A failed transaction
therefore cannot emit this direct message. A Telegram failure does not roll
back an already committed business operation. Normal purchase receipts add
stock and do not create this generic alert; custom rules can resolve during
recovery.

The direct query is tenant-scoped and requires a linked `TelegramConnection`,
`enabled: true`, `lowStockAlertsEnabled: true`, and a chat ID. The legacy schema
defaults the connection and low-stock preference to enabled; linking is the
existing connection action, and users can disable it through Telegram
preferences. Custom rule OPEN/RESOLVED Telegram preferences are separate and
default to false.

### Message

The direct message is now compact and Spanish-only. It contains the product's
human name, SKU when present, on-hand stock, and configured minimum. At exactly
zero stock it says “Producto agotado”; other crossings say “Stock bajo”. It
does not include tenant IDs, database IDs, customer information, tokens, or an
automatic purchase action. Singular/plural unit wording is handled in the
message. Link previews are disabled.

### Re-alerting and duplicate behavior

The direct notifier uses the persisted stock transition rather than a timer or
READ-time scan: further changes while already at/below minimum do not trigger
another message. Recovery to above minimum re-arms the next downward crossing.
No periodic scan or READ route sends low-stock messages. `lastAlertAt` is saved
after a successful send for observability, but it is not a durable dedupe key.
The direct path does not have an event-level outbox; it relies on the
post-commit crossing call and can lose a notification if Telegram is temporarily
unavailable. It does not automatically retry. This limitation is explicit and
is not masked with an unbounded retry loop.

The `product.low_stock` webhook is a separate legacy Node-RED dashboard refresh
path. The backend currently emits it on a stock update whose resulting stock
is at/below minimum; Node-RED refreshes/displays the low-stock list. That event
does not itself send a Telegram alert and is not the direct notifier's retry
or dedupe mechanism.

## Custom stock-rule delivery

`applyStockChange` evaluates enabled custom rules in the same Mongo transaction
as the stock movement. The evaluator opens an alert only on an inactive-to-
active transition; continued matching stock does not duplicate it. Recovery
resolves only the same tenant/product/rule. A later crossing can create a new
event cycle. Historical reconstruction does not evaluate live alerts.

The alert and `InventoryAlertOutboxEvent` are recorded transactionally with a
stable event identity. The backend dispatches events to Node-RED over HTTPS in
production, with a 5-second timeout and a batch limit of 10. The outbox retries
transient failures after 30 seconds, 2 minutes, 5 minutes, and 15 minutes;
GitHub Actions invokes the protected dispatch endpoint every five minutes and
also supports manual recovery. Node-RED validates the event and confirms its
exact `eventId` to the backend before acknowledging receipt. Telegram channel
delivery is separate from that receipt, uses a unique
event/channel/destination key and lease, and cannot happen before the backend
event is DELIVERED. Channel retries are bounded to five attempts with the same
backoff schedule; auth/configuration/destination failures are terminal until
operator intervention. Telegram delivery failure does not undo the business
write or durable outbox receipt. No retry scheduler was added in I.1.

## READ, inbound polling, and V3 boundary

The audit found direct `notifyLowStock` callers only in the transaction-write
controller and manual product-stock controller. Inventory/product READ routes
and V3 assistant READ skills do not call it. The V3 assistant has no Telegram
conversation channel in this phase.

The repository does contain legacy inbound Telegram behavior: after Mongo
connects, `app.js` calls `startPolling`; if `TELEGRAM_BOT_TOKEN` exists, the
backend uses `getUpdates` (25-second long poll, 35-second request timeout) for
`/start`, account connection, and forwarding legacy commands to Node-RED.
Node-RED does not run a second `getUpdates` poller; it replies to forwarded
commands and delivers custom-rule notifications. Removing backend polling
would break existing account linking/legacy commands, so it was preserved and
not expanded into a V3 assistant. A `polling error` log records only a safe
error category and retries after one second. The exact cause of any particular
cloud log cannot be established from local code; duplicate polling by another
deployment instance, credentials/API rejection, or network failure remain
possibilities, not confirmed causes. No cloud logs or live Telegram API were
consulted in this phase.

## Configuration and secrets

- Backend: `TELEGRAM_BOT_TOKEN` (optional for startup; required to send or poll).
- Mongo: tenant-scoped `TelegramConnection` with linked `chatId`, `enabled`,
  and `lowStockAlertsEnabled`.
- Custom-rule outbox: backend `NODE_RED_WEBHOOK_URL` and
  `NODE_RED_WEBHOOK_SECRET`; dispatch endpoint additionally uses
  `INVENTORY_ALERT_DISPATCH_SECRET`.
- Node-RED: matching `NODE_RED_WEBHOOK_SECRET`, `API_BASE`, and
  `TELEGRAM_BOT_TOKEN` for its existing reply flow.

No secret values are stored in code or this document. Missing outbound token
fails with a sanitized non-retryable `CONFIGURATION` category. Direct Telegram
requests time out after 8 seconds and sanitize transport/provider details.

## Remaining limitation / follow-up

The direct minimum-stock path has post-commit delivery but no durable outbox or
retry. If durable recovery for that legacy alert is required, a separate scoped
change should record a stable event in the existing transactional outbox and
reuse the existing channel worker rather than add another scheduler. The exact
cause of historical Render polling logs remains unconfirmed pending safe log
evidence. No second alert type is recommended now: the configurable stock-rule
alert already covers an additional user-selected threshold without inventing
another rule. Neither item was silently presented as solved here.
