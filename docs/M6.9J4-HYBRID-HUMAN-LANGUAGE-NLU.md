# M6.9J.4 — NLU híbrido para lenguaje humano

Estado: implementación y validación offline completas; pendiente publicación y smoke controlado. Sin push, deploy, Atlas, proveedores reales ni operaciones comerciales reales.

## Problema y causa reproducida

Sobre el código publicado J.3 (`39951df`), se leyó el router original mediante `git show` y se reprodujeron las dos consultas con los routers reales:

| Mensaje | Router V3 anterior | Ruta determinística heredada |
| --- | --- | --- |
| `q mas se vende?` | Sin plan | Sin plan; termina en aclaración genérica |
| `q productos se vende mas?` | Sin plan | `intent=search_product`, `query="se vende mas"` |

V3 reconocía `más vendido`, pero no componía el verbo de venta y el superlativo de estas frases. La búsqueda genérica heredada interpretaba el residuo lingüístico como nombre de producto. El query local exacto fue `se vende mas`; no se comprobó el payload histórico cloud. La intención analítica debía preceder al resolver de entidades.

## Arquitectura

Antes: normalización acotada → grounded explícito / router V3 → router heredado → aclaración local de desconocidos V3. DeepSeek solo sintetizaba hechos verificados.

Ahora: normalización ligera → gate OOD/seguridad y WRITE existentes → grounded explícito / reglas V3 de alta precisión → comprobación de rutas determinísticas heredadas válidas → una clasificación DeepSeek NLU cuando falta una interpretación fiable → validación estricta → plan cerrado → resolver J.2S / skills existentes / aclaración / OOD.

`languageNlu.js` concentra contrato, decisión de fallback y conversión a capacidades existentes. No registra nuevas skills. El provider neutral y el adapter DeepSeek existentes aceptan la ruta interna `SEMANTIC_NLU`; conservan JSON mode, no razonamiento, sin herramientas, un intento y ningún fallback Gemini. V1/V2 conservan su clasificación heredada; no se añade una nueva llamada Gemini.

### Decisión determinística frente a NLU

No se usa una confianza numérica del modelo. Se consideran señales estructurales del router:

- Plan válido con intención explícita y argumentos compatibles: determinístico.
- Stock extraído por las reglas de existencias, búsqueda explícita, SKU y selección vigente: determinístico.
- Gate OOD, seguridad, aclaración contextual, ordinales y decisiones WRITE: se resuelven antes del NLU.
- Sin plan, frase interrogativa no resuelta, texto analítico convertido en lookup, discrepancia entre sujeto y dominio, o término genérico convertido en producto: candidato a fallback.
- Una ruta heredada conocida de lectura, por ejemplo alertas, conserva precedencia. `search_product`, aclaración genérica y `unsupported` no se aceptan como prueba de comprensión semántica de una consulta analítica.

Reglas composicionales acotadas resuelven venta + superlativo y algunas formas cortas de stock/reposición. No hay una regla por cada una de las 435 frases. Las dos consultas cloud ahora generan `get_business_analytics`, `mode=rank`, `entityType=product`, `metric=units`, 0 IA. El período explícito se conserva al canonicalizar el ranking. `como van mis ventas` usa resumen determinístico; las preguntas explícitas de evolución/interpretación conservan la síntesis grounded existente.

## Contrato NLU

El prompt y la validación comparten `SCHEMA`. Todos los campos son obligatorios, no se admiten extras:

```json
{
  "intent": "TOP_SELLING_PRODUCTS",
  "productQuery": null,
  "metric": "units",
  "period": null,
  "quantity": null,
  "horizonDays": null,
  "needsClarification": false,
  "clarificationReason": null
}
```

Enum cerrado de 19 intents: PRODUCT_SEARCH, INVENTORY_LOOKUP, LOW_STOCK, REPLENISHMENT, SALES_SUMMARY, SALES_EVOLUTION, TOP_SELLING_PRODUCTS, FORECAST, CUSTOMERS_AT_RISK, CUSTOMER_VALUE, CUSTOMER_ACTIVITY, SUPPLIER_PERFORMANCE, CROSS_SELL, BUSINESS_HEALTH, CREATE_SALE, CONFIRM_WRITE, CANCEL_WRITE, OUT_OF_DOMAIN, AMBIGUOUS.

`productQuery`: texto literal contiguo del mensaje, máximo 100 caracteres, sin secretos ni controles; nunca un ID/SKU inferido. JSON máximo 2200 bytes. `metric`: null/units/revenue/tickets. `period`: null/TODAY/LAST_7_DAYS/LAST_30_DAYS/THIS_MONTH; debe estar explícitamente respaldado. El servidor calcula las fechas mediante el resolver operacional existente. `quantity`: entero 1–10000, solo CREATE_SALE, extraído de una expresión explícita de venta. Números de SKU o presentación no autorizan cantidades. `horizonDays`: null/1/7/14 y debe corresponder a una duración expresada; un horizonte no aprobado se rechaza aunque el modelo omita el campo. `clarificationReason`: null/MISSING_PRODUCT/MISSING_INTENT/MISSING_CONTEXT/AMBIGUOUS_ACTION, consistente con el flag.

El modelo devuelve clasificación, no una respuesta visible. Los textos visibles provienen de renderers aprobados, aclaraciones del servidor o, cuando corresponde, una síntesis grounded posterior con sus propias validaciones.

## Entidades, estado y WRITE

- J.2S resuelve el candidato dentro del tenant autenticado y conserva 0/1/N coincidencias, nombres humanos, SKU, ordinales y TTL. El NLU no determina correspondencias de catálogo.
- Contexto NLU: mensaje actual redactado, tipo de entidad activa y existencia de lista. No recibe nombres/IDs de entidades activas, resultados de skills, datasets, analítica, Mongo, precios ni historial completo. El servidor conserva la entidad real.
- Seguridad/OOD se evalúan antes del proveedor. Se redactan credenciales reconocibles también en el mensaje actual. Las entidades que contienen esos secretos se rechazan.
- Una intención nueva interpretada por NLU reemplaza las opciones antiguas; no revive una lista expirada ni cambia el tenant/conversación. Un producto activo inequívoco se conserva según el TTL existente.
- `pan` sin intención/contexto pide aclaración. `saca/retira` siguen ambiguos y no se convierten en venta.
- CREATE_SALE semántico requiere verbo de venta, cantidad explícita y candidato literal. Solo entonces el wrapper entrega una propuesta interna al mismo parser/resolver/draft de venta. Elimina la propuesta del transporte público y conserva el consumo NLU. No hay segunda extracción por proveedor en ese handoff.
- Selección → preview → confirmación explícita → ejecución siguen siendo responsabilidades del backend. CONFIRM_WRITE/CANCEL_WRITE de NLU solo aclaran: no se traducen a una decisión autorizante. `ya dale` no ejecuta. Las decisiones exactas ya aprobadas, como `si hazlo` y `mejor no`, siguen su máquina de estados existente.
- La confirmación valida preview/conversación/estado/idempotencia mediante la implementación previa. Pruebas de confirmación usan servicios falsos; no ejecutan transacciones comerciales reales.
- Secuencias A/B/C verificadas: pan → segundo → forecast → cross-sell; clientes → segundo → gasto del mismo cliente; ranking de ventas → entidad compatible resuelta → stock. No se toma un ordinal de un objeto arbitrario.

## Latencia, costo y fallos

Prompt NLU base: 1662 bytes UTF-8. Se agrega un mensaje y dos indicadores mínimos; se verifica el límite total de 8000 bytes del provider. Cap de clasificación: 300 tokens, limitado también por el cap DeepSeek existente. Síntesis: se mantiene el default configurado de 500 y máximo 600; esta fase no cambia esos límites.

`DEEPSEEK_NLU_TIMEOUT_MS`: default 8000 ms, configurable entre 1 y 20000 ms. Ocho segundos es un presupuesto separado para una salida corta sin razonamiento; no es una predicción de latencia ni una garantía de red. Un valor muy bajo aumentará aclaraciones por timeout. `DEEPSEEK_TIMEOUT_MS` sigue controlando la síntesis. No se modificó ninguna variable de entorno real.

| Flujo | Llamadas |
| --- | --- |
| Consulta determinística común / OOD reconocido / selección / preview normal | 0 |
| NLU → skill/render determinístico, aclaración u OOD | 1 NLU |
| Grounded reconocido directamente | 1 síntesis, sin NLU |
| NLU → SALES_EVOLUTION con evidencia comparable → grounded | 1 NLU + 1 síntesis |
| NLU falla | 1 intento máximo; aclaración segura, sin retry |

El único caso que necesita el segundo provider conserva separados clasificación y síntesis; no fusiona autorización o grounding con interpretación lingüística. Si falta evidencia comparable, no se llama a síntesis. No hay reintento, reparación de JSON parcial ni fallback automático a otro provider.

`routingMode=deterministic|semantic_fallback` indica cómo se enrutó, no si hubo síntesis posterior. `semanticClassification` y `groundedAnswer` exponen proveedor/modelo, llamadas, input/output/total tokens, latencia, finish reason, aceptación y motivo de fallback, costo/rango existente. El agregado `usage` cuenta todas las llamadas y es compatible con las tarjetas actuales. Datos de usage ausentes se mantienen null; tarifa desconocida no se convierte en cero.

Timeout, 429, 500, red, envelope inválido, truncamiento, JSON/schema inválido e intent desconocido terminan en aclaración controlada sin ejecutar la clasificación rechazada. La pregunta de fallback distingue stock bajo, reposición y ventas, en lugar del error genérico. No se guardan prompts completos, raw response, reasoning ni secretos.
