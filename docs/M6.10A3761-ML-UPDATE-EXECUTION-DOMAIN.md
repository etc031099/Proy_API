# A.3.7.6.1 — Durable ML update execution domain

## Scope and separation of responsibilities

`ForecastMlUpdateExecution` is an additive audit entity, not a new training
pipeline. `ForecastMlUpdateEvent` remains the operational signal/outbox;
`ForecastMlUpdateState` remains the current state/lease/fencing authority;
`ForecastTrainingJob` remains the training/evaluation/candidate lifecycle.

This phase only registers the model in `models/index.js`, supplies a persistence
adapter and a domain service, and adds offline tests. It does not connect the
manual API, cloud worker, workflow, public history API, impact scorer or UI.
No model training, promotion, migration, backfill or cloud operation is executed.

## Data contract

- Public identity: generated UUID v4 `executionId`; internal business/scenario
  scope is mandatory for every domain read/write.
- Sources: `MANUAL`, `SCHEDULED`, `CLI`. Scheduled covers the automatic workflow;
  this phase does not infer source from mutable environment variables.
- Optional correlated identity: `manualRequestKey`, GitHub repository/run ID,
  `cliInvocationKey`. Each source must supply its corresponding identity.
- Timing: requested/started/finished timestamps; null means not captured/not
  reached. A terminal execution cannot finish before its recorded start.
- Data: before/evaluated revisions, close boundary, pending before/after,
  canonical signal types, eligibility, available/required origins.
- Revisions remain decimal strings in the existing signed int64 range;
  numeric input is rejected, including unsafe JavaScript numbers. No Number
  conversion is performed. GitHub run IDs are also strings.
- Global status, stage, canonical reason and generated safe message.
- Exactly two horizon entries, 7 and 14: active versions before/after,
  candidate version/status, training job reference, trained revision,
  promotion decision/reason, policy version, result and origins/eligibility.
- `requiredOrigins=107` at global and horizon level; 1d is rejected.
- `impact` contains only status/reason. No SKU diffs or inferred impact exist.
- `writeVersion` is the optimistic concurrency token, distinct from model,
  operational revision, worker lease and training fencing tokens.

## Unique indexes / durability

1. Global unique public execution ID.
2. Unique `(businessId, scenarioId, manualRequestKey)`, partial for string keys.
3. Unique `(businessId, scenarioId, github.repository, github.runId)`, partial
   for string repository/run IDs. Repository is normalized to lowercase.
4. Unique `(businessId, scenarioId, cliInvocationKey)`, partial for string keys.
5. History index `(businessId, scenarioId, requestedAt DESC, executionId DESC)`.

No TTL or deletion is configured. Index creation is not run by the domain
service, and GET/domain reads never initialize indexes or create documents.
The subsequent integration/deployment must provision and verify these indexes
before enabling execution writes. Unique indexes, not an in-memory map, are the
production duplicate-create guard. A duplicate key reloads the scoped winner;
conflicting correlated identities are rejected rather than silently merged.

## State transitions

| From | Allowed next statuses |
| --- | --- |
| REQUESTED | PENDING, RUNNING, DEFERRED, FAILED, INTERRUPTED |
| PENDING | RUNNING, DEFERRED, FAILED, INTERRUPTED |
| DEFERRED | PENDING, RUNNING, FAILED, INTERRUPTED |
| RUNNING | NOT_ELIGIBLE, EVALUATED_NO_PROMOTION, PROMOTED, PARTIAL, FAILED, INTERRUPTED, NO_PENDING_WORK |

Terminal outcomes are immutable within an attempt. A global PROMOTED requires
both horizons promoted with consistent candidate/new-active versions. Global
EVALUATED_NO_PROMOTION requires that outcome for both horizons. Mixed outcomes
are represented as PARTIAL. A confirmed horizon promotion cannot be relabeled
as a global FAILED, NOT_ELIGIBLE, NO_PENDING_WORK or INTERRUPTED result.

Horizon outcomes may be recorded directly from REQUESTED to a terminal outcome
when the worker reports its complete result; otherwise their transitions follow
the same ordered state graph. A final horizon result cannot be replaced by a
different result within the same attempt. Unknown versions stay null; absence
does not prove that an ACTIVE changed or remained unchanged.

Available operations: `createExecution`, scoped `getExecution`, manual/GitHub
identity lookup, `transitionExecution`, convenience start/pending/deferred/
not-eligible/no-pending/promoted/no-promotion/partial/failed/interrupted methods,
`recordHorizonResult`, `registerGithubAttempt`, `setImpactStatus`.

## Attempts and concurrency

Creation is idempotent for the same identity. Repeating an older GitHub attempt
returns the latest principal execution without rolling it back. A higher
`runAttempt` registers on the same execution only after the previous attempt
has a terminal outcome. An unfinished attempt must first be resolved explicitly
(for example, INTERRUPTED by future recovery logic); this domain does not guess
that a worker is dead and does not bypass its existing lease/fencing.

Attempts preserve number, dates, status, safe reason, final horizon results,
evaluated revision, close boundary and impact metadata. Top-level fields then
describe the latest attempt, while earlier attempts remain recorded. No second
principal execution is created for a GitHub retry. Manual/CLI duplicate calls
return their execution and do not automatically restart terminal work.

Maximum 20 GitHub attempts per principal execution, a defensive bound for a
small retry history, not an ML threshold. Exceeding it returns
`EXECUTION_ATTEMPT_LIMIT`; nothing is truncated/deleted. Future high-volume
operation may move attempts into a separately paginated store.

Every mutation requires `expectedVersion`. Production uses a scoped atomic
`findOneAndUpdate` filtered by `writeVersion` and increments that version.
Two competing starts cannot both succeed. Concurrent horizon reporters receive
`EXECUTION_CONFLICT`; the caller must reload the scoped execution and reapply
its own result. The domain never blindly overwrites the other horizon and does
not add backend training retries. Duplicate creation of the same new GitHub
attempt safely reloads an already-registered winner after a version conflict.

## Impact and security

Impact status is independent of ML outcome. PENDING/COMPLETE/PARTIAL impact
metadata requires a recorded horizon promotion. Changing impact metadata never
changes the promotion outcome or ACTIVE versions. This is only future metadata,
not a claim that a SKU comparison has been implemented.

Only catalogued reason codes persist; unknown codes become UNKNOWN_REASON.
Messages are generated from the static catalog, never copied from caller/error
text. Unknown document/result fields are rejected. The schema has no slots for
URIs, credentials, headers, session objects, artifact bytes, datasets, matrices
or arbitrary evaluation payloads. Caller-provided opaque identity/reference
fields must contain actual identifiers, never secret material. Internal job
references are not intended to be exposed verbatim by a future public API.

Reads use scope even when the public ID is known; wrong scope returns null,
and wrong-scope mutation returns EXECUTION_NOT_FOUND. This is domain isolation,
not a substitute for the authentication middleware required by the future API.

## Validation and compatibility

`node --test backend/test/forecastMlUpdateExecution.test.js` validates the real
Mongoose schema offline and uses an injected repository emulating unique indexes
and CAS. Production adapter query construction is tested separately. These tests
do not certify index provisioning/query behavior against a live Mongo server;
that remains an explicit local integration prerequisite before worker wiring.

The collection may begin empty. No old execution, actor, impact or timing is
fabricated. Existing manual status/worker behavior is unchanged because the new
domain is not wired to them. Future phases add integration, actual attributed
impact, scoped paginated API, UI and the demonstration, in that order.
