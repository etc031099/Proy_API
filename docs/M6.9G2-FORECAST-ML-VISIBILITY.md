## Contrato y flujo autenticado

```text
Frontend apiClient
  → GET /api/intelligence/forecast/evaluation
  → authenticate + business access + analytics rate limit
  → HistoricalScenario validado server-side para tenant V3
  → POST /v3/intelligence/forecast (mode=evaluation, dataMode=HISTORICAL)
  → evidencia JSON persistida, validada con Pydantic
```

Se añade un selector al endpoint interno de forecast existente; no otra ruta ML ni otra aplicación. El backend construye business/scenario/dataset/timezone y fija asOfDate=2026-10-12. No recibe businessId del browser ni consulta snapshot/stock LIVE. El secret interno existente se mantiene en el cliente backend. ML valida auth/contexto; el modo evaluation rechaza LIVE y cualquier otro cutoff en vez de hacer fallback.

La respuesta pública `{success,data}` contiene contrato `forecast-model-evaluation-v1`:

- `modelEvaluation[]`: modelId, algorithm, modelType, learningType, task, target, horizonDays, features/featureGroups, dataset, trainPeriod/validationPeriod/testPeriod, metrics, baseline, mejora relativa ya documentada cuando existe, modelStatus, version, trainingCutoff, artifactHash y evaluationEvidenceHash, limitations.
- `selectedOperationalMethod`: MOVING_AVERAGE_28, label, STATISTICAL_BASELINE, NOT_APPLICABLE, OPERATIONAL, horizontes, versión y razón de selección.
- `operationalEvaluation[]`: métricas TEST MA28 por horizonte con estado BASELINE como técnica de referencia, sin llamarla ML.
- `analysisCutoff`: 2026-10-12.
- `historicalSeries`: available=false, reasonCode=TEST_PREDICTIONS_NOT_PERSISTED, points=[].

Schemas Pydantic explícitos, campos extra prohibidos y floats finitos. El backend verifica envelope/lineage/requestId, versión de contrato y estados. Metadata y artefactos faltantes/inconsistentes producen error seguro; no se sustituyen con números. No se publican rutas internas, PII o secretos.

El loader lee evidencia una vez por raíz/proceso, con cache acotado de cuatro entradas. Cada respuesta serializa una estructura nueva, evitando mutación de la evidencia compartida. La renovación de reportes se hace por despliegue/worker nuevo; esta fase no soporta reemplazo mutable de evidencia en caliente. El readiness forecast existente sigue siendo necesario; no se añade un readiness académico independiente.

## Real vs. predicho

La inspección de reportes y scripts de evaluación no encontró una serie TEST persistida por fecha/producto. `evaluate_r4_test.py` conserva métricas y reportes por grupo; sus predicciones TEST se calculaban en memoria. Los reportes V3 también conservan agregados, no observaciones individuales actual/predicted.

No se ejecutó inferencia para recrear esa evidencia: usar el artefacto final reajustado como si fuera el fit original podría producir otra curva. La UI presenta las comparaciones reales de métricas y una explicación de la ausencia de la curva. No aparece un gráfico ficticio ni se mezcla el historial observado LIVE con predicciones TEST HGB. Esta limitación está cubierta por el contrato y no impide mostrar la evidencia académica existente.
