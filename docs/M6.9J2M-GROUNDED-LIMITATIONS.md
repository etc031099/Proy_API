## Previous contract and reproduced cause

`limitations` was a required `string[]` with 0–2 elements, nonempty strings up to
240 characters. After schema validation, the grounding validator required literal
membership in `HALLUCINATION_CONTRACT`: seven general instructions about facts,
entities, safety and approved ML semantics. It used neither keywords nor semantic
matching, and did not require any partial/missing/unavailable factual state.

Before modification, all six example warnings in the request reproduced
`LIMITATION_NOT_ALLOWED`: future demand, changing data, external factors, reviewing
suppliers, forecast variability and insufficient information. An exact general
policy sentence was accepted even without a partial flag. These local fixtures
show a mismatch between generic prompt wording, literal policy comparison and
actual data limitations; they do not reconstruct the unknown cloud response.

## Final contract: codes backed by evidence

Option A was selected. The JSON remains `observations` plus `limitations`, with
unchanged cardinalities, text length limits and observation fields. `limitations`
is still a string array, but its values must now be authorized codes, never prose.
The private compact context is versioned `grounded-v3-context-v2` and includes
`allowedLimitations: [{code, message, evidenceRefs}]`.

| Code | Explicit condition in sent evidence | Backend-rendered message |
| --- | --- | --- |
| RECOMMENDED_QUANTITY_UNAVAILABLE | Inventory is PARTIAL (result or availabilityStatus), recommendedQty is null and recommendation.status is LIVE_FORECAST_REQUIRED | La cantidad sugerida no está disponible para parte del inventario consultado. |
| FORECAST_UNAVAILABLE | Forecast result NO_DATA/UNAVAILABLE, or item status COLD_START/INSUFFICIENT_HISTORY/UNAVAILABLE | No hay pronóstico disponible para parte de los productos consultados. |
| SUPPLIER_RELATION_UNAVAILABLE | Projection explicitly omitted supplier facts with NO_CANDIDATE_SUPPLIER_EVIDENCE | La evidencia consultada no permite vincular proveedores con los productos candidatos. |
| ANALYTICS_PARTIAL | Explicit PARTIAL result/availabilityStatus without a more specific condition for that evidence | Parte de la información analítica consultada está marcada como parcial. |
| ANALYTICS_UNAVAILABLE | Explicit NO_DATA/UNAVAILABLE result outside the forecast-specific case | Un resultado analítico consultado está marcado como no disponible. |
| CONTEXT_EVIDENCE_OMITTED | Evidence explicitly omitted with CONTEXT_BUDGET | Parte de la evidencia fue omitida para respetar el límite del contexto. |

The collection is derived from the projected evidence and recomputed after budget
trimming, remaining inside the 6400-byte context limit. Rank truncation, the normal
three-product limit, supplier-wide metrics, null without provenance and ordinary
forecast uncertainty do not independently authorize a limitation. The validator
intersects the sent allowlist with codes derivable from the current facts, so a
stale or forged allowlist cannot authorize an unsupported state. Messages always
come from backend constants after validation; the provider cannot supply them.

The previous incomplete-execution gate is preserved: a PARTIAL/NO_DATA/failed
skill still prevents a provider call and keeps verified facts. Authorization tests
for those contexts do not enable synthesis on incomplete plans.

## Prompt, validation and diagnostics

The shared prompt states that limitations are not general observations, generic
warnings or ordinary LLM uncertainty. It requires only codes present in
allowedLimitations, explicitly says `"limitations": []` when the collection is
empty, and forbids precautionary additions or copying constraints as limitations.
The shared schema adds this description without changing array/string types,
cardinalities, 900-character text limits or the combined 2160-character bound.

Unknown or unauthorized codes still fail closed with `LIMITATION_NOT_ALLOWED`.
Sanitized diagnostics add `limitationReason` from a fixed set:
NO_ALLOWED_LIMITATION_CONTEXT, UNKNOWN_LIMITATION_CODE, LIMITATION_NOT_AUTHORIZED.
`limitationCode` is exposed only for a known backend code; arbitrary generated text
or unknown codes are never echoed. Projection, logs and expandable UI preserve
only these safe fields, alongside the existing field/layer diagnostics.

J.2L remains default 500/configurable through 600, JSON mode unchanged, length
rejected as OUTPUT_TRUNCATED, no partial-JSON repair or retry. Numeric grounding,
J.2I product presentations and J.2J/J.2K structural handling are unchanged. Routing,
skills, ML, pricing, token telemetry and WRITE state handling were not modified.
