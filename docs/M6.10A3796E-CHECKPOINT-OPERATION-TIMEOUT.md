# A.3.7.9.6E — Presupuesto temporal de checkpoint cloud

## Contexto

El límite anterior de captura operativa era 120 s de tiempo total. La lectura de sizing previa en cloud tardó aproximadamente 66.3 s para 56,676 documentos y 101,053,736 bytes (unos 40 chunks estimados). Ese preflight fue una solicitud independiente y no consumía el presupuesto del POST posterior de checkpoint; sirve como referencia de latencia, no como parte del mismo reloj.

El checkpoint se mantiene fail-closed: si se agota el presupuesto, la captura queda `FAILED`, el control permanece en mantenimiento y la recuperación sigue usando exclusivamente el flujo administrativo existente. No se marca `READY` ni se libera el fence por timeout.

## Presupuesto

- Captura local/certificación: 120,000 ms.
- Captura operativa cloud por defecto: 240,000 ms.
- Máximo cloud configurable: 300,000 ms.
- Variable de servidor opcional: `ML_TEST_CHECKPOINT_CLOUD_TIMEOUT_MS`; solo acepta enteros entre 120,000 y 300,000. La configuración inválida falla antes de iniciar la captura.
- El timeout no puede enviarse por HTTP. La ruta mantiene su contrato cerrado y rechaza campos extra como `timeoutMs`.
- Se conservan los límites volumétricos: 128 MiB, 200,000 documentos, chunks objetivo de 4 MiB, 128 chunks y RSS máximo de 512 MiB.

El valor de 240 s da margen respecto a la lectura observada para persistir y verificar chunks y finalizar, sin convertirse en una espera ilimitada. El máximo de cinco minutos limita el período potencial en mantenimiento. No garantiza que Atlas complete siempre la operación dentro del presupuesto.

## Alcance del reloj y fases

Un deadline monotónico único empieza al iniciar la captura y cubre la adquisición/quiescence, drain de writers, lectura de snapshot, escritura de chunks, verificación y finalización. La verificación no obtiene un segundo presupuesto de captura. Los fallos por deadline conservan la fase y el checkpoint identificables.

Los logs de progreso allowlisted informan `checkpointId`, `phase`, `budgetMs`, `elapsedMs` y `remainingBudgetMs`; los fallos agregan el tiempo de fase. No incluyen URI, payload, hashes de artifacts ni errores crudos. Las operaciones Mongo reciben el tiempo restante cuando el driver lo admite; la lectura de cursor conserva su `maxTimeMS` de 45 s por operación y la transacción final limita el commit a 5 s. Estos límites por operación están subordinados al presupuesto total.

El sizing/preflight read-only tiene su presupuesto independiente y no se suma al tiempo de captura. El límite de lectura del cursor de 45 s tampoco es el timeout global de la captura.

## Diagnóstico del checkpoint cloud existente

El estado informado para el checkpoint `98abbcb6-baee-4368-a283-0249cb40f877` solo confirma `FAILED` y `CHECKPOINT_OPERATION_TIMEOUT`. No se proporcionó el campo diagnóstico de fase ni se consultó el status cloud durante esta fase, por lo que no se puede afirmar honestamente cuál fase agotó el reloj anterior. El volumen y duración del preflight no prueban por sí solos que la captura se agotara en lectura.

Tras publicar esta corrección, consultar el endpoint administrativo de status ya existente para revisar `failureDiagnostics.phase`, si está persistido. La elegibilidad de recuperación de ese checkpoint no se presume por su código de fallo: el mecanismo administrativo existente debe volver a validar protocolo, `readyAt`, control, writers y fencing antes de permitir recuperar. Esta fase no hace esa recuperación.

## Validación local

Las pruebas focales verifican los valores local/cloud, configuración inválida y máxima; un reloj simulado fuerza timeout durante lectura, escritura de chunks y verificación, confirmando estado `FAILED`, mantenimiento/fencing intacto y recuperación únicamente por el executor administrativo local ya certificado. No se accedió a Atlas ni se ejecutó checkpoint cloud.

Resultado de volumen en replica set local desechable: el fixture cloud-equivalente completó captura, persistencia, verificación y restore exacto con 56,675 documentos y 101,050,857 bytes; captura ~5.4 s, restore con verificación ~13.8 s. Un fixture adicional de 56,676 documentos y 101,053,736 bytes completó la captura con verificación en ~6.1 s. Estos números certifican límites/flujo local, no predicen latencia de Atlas.
