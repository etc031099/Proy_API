## 4. Gates exactos conservados

Fuente ejecutada sin modificar: `ml/scripts/benchmark_minimarket_v3.py::check_acceptance` y `attach_top10_gate`.

1. Mejora relativa de WAPE global `(base-model)/base >= 0.05`.
2. Sesgo global normalizado definido y `abs(sum(pred-y)/sum(y)) <= 0.10`.
3. MAE macro por SKU `<= 1.10 * baselineMacroMae`; si baseline macro es cero, `<= 0.1*h`.
4. **Todas** las categorías y los segmentos originales A.1: si hay demanda y WAPE base positivo, mejora relativa `>= -0.10`. Si no hay denominador válido/positivo, `MAE_model <= MAE_base + 0.1*h`.
5. **Cada** SKU top 10 por ingresos calculados solo hasta el cutoff TRAIN: deterioro MAE relativo `<= 0.20`; con MAE base cero, no puede empeorar. Además sesgo normalizado individual absoluto `<= 0.20`, o no calculable (comportamiento del gate existente).

Todos deben pasar en cada horizonte y en los tres tramos. La subcategoría se informa como diagnóstico, no se inventó un gate nuevo. Los segmentos originales (`very_low/intermittent/high_stable/medium`) se mantienen en los gates aunque se pruebe un router de dos expertos: no se reemplazaron por segmentos más fáciles. ## 7. Stockout y censura

VALIDATION: 3680 producto-días, 1519 con cero ventas, 252 con `availableHours < 15`, 153 simultáneamente cero y disponibilidad reducida. La referencia 15 h es la exposición diaria del escenario canónico, no una tolerancia de stock nueva. Una disponibilidad inferior a 15 h es indicador de posible censura, no prueba de demanda perdida.

No se ajustaron ventas ni se eliminaron etiquetas para mejorar scores. A.2 mantiene el target de **ventas observadas** y excluye availability como feature de los modelos LIVE-causales: el snapshot operativo local documentado no certifica exposición horaria histórica LIVE equivalente. Utilizar disponibilidad futura de la ventana sería leakage. Tampoco se ponderaron ventanas usando disponibilidad futura. El efecto sobre error de los grupos censurados se conserva en el análisis adicional de predicciones; la causa latente de cada cero sigue NO CONFIRMADA. Un modelo futuro de demanda no restringida necesita exposición fiable: no puede deducirse de ventas cero.

## 8. Features y auditoría de leakage

Se revisaron las 38 features A.1; se reutilizan 27 compatibles con información causal disponible, más cinco señales derivadas de los últimos 28 días cerrados hasta T inclusive. `zeroSalesStreak`, `daysSinceLastSale`, lags y rolling means/std ya existían y no se duplicaron.

`saleDays28/28` equivale a nonzero rate; no se añade otra columna redundante. Los 27 campos base y los parámetros íntegros están en el protocolo JSON. ## 9. Familias, configuración y todos los intentos

- **POISSON27**: control Poisson con las 27 features A.1.
- **POISSON32**: Poisson con 27+5 features de intermitencia.
- **HURDLE32**: HGBClassifier aprende `P(Y_h>0)` en todas las filas TRAIN; HGB Poisson aprende `E[Y_h|Y_h>0]` solo en positivos. Predicción = producto de ambas salidas, no un umbral binario ni redondeo. Si una clase no existe, probabilidad constante conocida en TRAIN. Se contrasta empíricamente, no se presupone superioridad.
- **WEIGHTED32**: mismo Poisson32, peso `N/(K*n_categoria)` por fila TRAIN. Cada categoría recibe el mismo peso agregado, peso medio 1. No se usan errores de validación, top10 ni pesos ajustados para aprobar gates. Igualar solo SKU no modificaría este dataset balanceado por número de filas; se prueba igualar representación por categoría. El objetivo Poisson todavía puede ser sensible al volumen, no se afirma eliminarlo por completo.
- **MIXED32**: dos expertos **globales**, Poisson32 para regulares y hurdle32 para SKU con zero-rate TRAIN >=0.5. No se entrenó un modelo por SKU. Los dos expertos se ajustan con sus respectivos objetivos sobre el TRAIN global, no exclusivamente sobre cada segmento; se evalúa un router de expertos ya ajustados, no una familia segmentada completamente independiente. Se reutilizan los dos artefactos; sin ajustes adicionales.

Regresores: `HistGradientBoostingRegressor(loss="poisson")`, `max_iter=150`, `learning_rate=.05`, `max_leaf_nodes=15`, `min_samples_leaf=30`, `l2_regularization=1`, `early_stopping=False`, seed 2026. Classifier: mismas restricciones, log-loss predeterminado, sin class_weight (alteraría calibración de probabilidad). OrdinalEncoder ajustado con TRAIN; desconocido −1 tratado como faltante; seis columnas categóricas. No se hizo grid search. Una configuración por variante/horizonte/corte. Poisson es válido para objetivos no negativos con suma positiva, comprobado por entrenamiento y sklearn; no implica distribución Poisson verdadera de los datos.

Se comparan HGB cuadrados y Ridge A.1 sin reentrenarlos para la tabla principal. Ridge es ML supervisado lineal con regularización, no un promedio estadístico fijo. HGB38 A.1 solo es referencia, no candidato LIVE elegible. No Croston, blending MA28, calibración posterior, recorte de métricas ni cambio de gates.

## 15. Viabilidad y autoactualización futura — solo diseño

| Alternativa | Evaluación |
|---|---|
| Entrenar dentro de FastAPI actual | No recomendado: ya se observó RSS local de runtime 403.21 MiB; los perfiles aislados no prueban capacidad conjunta, concurrencia ni tiempos en CPU Free. Puede comprometer serving y dormir/reiniciar. |
| Worker separado activado por eventos | Recomendado: lease/fencing, debounce, una tarea por tenant, candidato durable y promoción atómica. No se presupone que exista worker cloud gratuito siempre encendido. |
| Job Node/Python controlado | Opción viable de aislamiento: Node coordina, Python ajusta y sale, con límite de RAM/tiempo. Lanzarlo en el mismo host con RAM compartida no elimina el riesgo; requiere slot y recursos certificados. |
| Worker supervisado en PC existente | Alternativa académica sin servicio pagado, con polling automático del outbox y disponibilidad condicionada a PC/red. No depende de intervención manual ni de esta conversación para cada venta; no promete 24/7. |

Se mantienen las restricciones de infraestructura documentadas en A.1; no se consultó ni cambió cloud en A.2. Los tiempos Windows/CPU local no son benchmarks Render. Artefactos pequeños no garantizan que el conjunto runtime+entrenamiento quepa en Free. No hay mecanismo nuevo implementado.

Flujo futuro: venta/corrección comprometida → outbox durable en la misma transacción/revision → refresco automático de dataset/features causales → entrenamiento cuando existan etiquetas maduras → evaluación automática con gates congelados → candidate → persistencia/hash → promoción CAS solo si pasa → invalidación por versión de modelo → forecast nuevo. Entrenamiento automático intentado no garantiza promoción ni que cada pronóstico cambie numéricamente.

La exportación debe separar fecha efectiva de operación y conocimiento/as-of para correcciones retroactivas; el snapshot actual no demuestra entrenamiento point-in-time completo. La estrategia previa sigue activa si un candidato falla, nunca se publica un modelo rechazado. Nada de este flujo se implementó aquí.

## 16. Decisión y única siguiente línea experimental

No hay receta que supere todos los gates en los tres tramos para 1/7/14. La intermitencia existe, pero los fallos también afectan SKU regulares, sesgo y comparación de períodos; hurdle, Poisson y ponderación no bastan para atribuir el problema solo a sparsity. La censura observada puede contribuir, sin causa latente identificada; el target se mantuvo como ventas observadas. No se ha demostrado que los gates sean imposibles ni se propone bajarlos.

**Una siguiente línea:** modelo global de regresión cuantílica/absolute-error regularizado por horizonte, con contracción causal hacia efectos de categoría y evaluación explícita del compromiso MAE–sesgo. Motivación: MAE/WAPE evalúan error absoluto, mientras Poisson optimiza deviance y la combinación hurdle estima media condicional; la asimetría/dispersión puede sostener errores y sobrepredicción individuales. Congelar una receta pequeña y los mismos gates antes de ajustarla; usar solo desarrollo. No añadir simultáneamente más familias ni mirar TEST. No hay garantía de aprobación. M6.10A.3 queda bloqueada hasta champion y controles operativos/cold-start satisfactorios.
