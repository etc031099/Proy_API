# M6.10A.3.1 — Forecast Model Registry and Artifact Persistence

**State:** implemented locally; no model artifact, bootstrap, serving path, worker, or cloud activation was created. This phase supports only 7- and 14-day model versions. A 1-day model is intentionally unsupported.

## Collections and metadata

`ForecastModelArtifact` stores one immutable model-version record and its bounded serialized bytes in MongoDB. It records tenant (`businessId`), scenario, horizon, family, recipe, monotonically issued `modelVersion`, status, training/data cutoffs and window, feature version/hash, frozen promotion-policy version/hash, global WAPE/MAE/bias, serializable checks, trigger reason, artifact SHA-256/location/byte count, source dataset hash, lineage, optional idempotency key/fingerprint, sanitized failure code, and timestamps. Artifact bytes are excluded from ordinary queries and are returned only by the explicit active-artifact read. The implementation caps each artifact at 5 MiB. A zero-byte placeholder may be recorded as a CANDIDATE for metadata workflows but cannot be promoted. It does not deserialize joblib or accept a real Ridge artifact in this phase.

`ForecastModelRegistry` is the mutable pointer, unique per `(businessId, scenarioId, horizonDays)`. It stores `activeArtifactId`, `activeModelVersion`, `generation`, and the last issued version counter. The active ID/version are both null for an empty pointer and otherwise must be present together. The monotonic sequence is independent for 7d and 14d.

## Indexes

- Artifact unique `(businessId, scenarioId, horizonDays, modelVersion)`.
- Artifact partial unique `(businessId, scenarioId, horizonDays)` where `status=ACTIVE`.
- Artifact partial unique `(businessId, scenarioId, horizonDays, idempotencyKey)` when the key is a string.
- Artifact history lookup `(businessId, scenarioId, horizonDays, status, modelVersion desc)`.
- Registry unique `(businessId, scenarioId, horizonDays)`.

The artifact collection-level ACTIVE constraint is a final guard; the registry pointer remains the authoritative serving selection. No model registry or ACTIVE entry is created for horizon 1.

## State machine

```text
CANDIDATE ──promote (generation CAS)──> ACTIVE ──next successful promotion──> SUPERSEDED
    ├──reject─────────────────────────> REJECTED
    └──mark failed────────────────────> FAILED
```

Only `status` and sanitized `failureCode` are mutable metadata. Training facts, metrics, hashes, recipe, lineage, and bytes are immutable through Mongoose. A rejected, failed, or stale candidate cannot be promoted. Rejection/failure leaves any existing ACTIVE pointer untouched.

## Candidate creation and integrity

Candidate creation validates the tenant/scenario/horizon, nonempty family and recipe, dates, decimal-string Mongo int64 data version, hashes, finite/nonnegative metrics as applicable, plain JSON checks/lineage without secret-bearing keys, and a byte buffer from 0–5 MiB. It computes SHA-256 from the bytes and rejects any supplied mismatch. Promotion and active reads re-check byte length/hash and the exact frozen policy identifier/hash (`M6.10A22-PROMOTION-v1`, `522a2af4ec30f83b016d7c9bc8886e775f1871a4bb9469963648e5539e25cdc3`); promotion also requires nonempty bytes. Candidate creation never marks a model ACTIVE.

An optional idempotency key is unique within tenant/scenario/horizon. A repeated key with identical candidate metadata returns the original version; a different payload returns `IDEMPOTENCY_KEY_CONFLICT`.

## Promotion, CAS, and transactions

Promotion runs in a bounded Mongo replica-set transaction with snapshot reads and majority writes. It checks the requested generation, exact candidate tenant/scenario/horizon/version, candidate state, frozen policy/metadata, and artifact hash. It changes the previous ACTIVE to SUPERSEDED, candidate to ACTIVE, then updates the pointer with compare-and-swap on the expected generation and previous pointer and increments generation once. A CAS loser receives a controlled conflict; the transaction rolls back all status/pointer writes. A repeated promotion of the already pointed ACTIVE version is idempotent and does not increment generation. Transient/write-conflict and duplicate-key transaction failures receive at most one whole-transaction retry; unknown commit outcome is retried only at commit and then returned as an explicit unknown outcome, never replayed as a new promotion.

An empty pointer can promote its first candidate at generation 0; this only defines the operation. No bootstrap was run. `getActiveModelMetadata` and `getActiveModelArtifact` follow the pointer's exact artifact ID and version; neither selects `max(modelVersion)`. All database operations include tenant, scenario, and horizon scope. `listModelVersions` is similarly scoped and bounded.

## Focal integration coverage

Run only against a local MongoDB replica set (`rs0`) configured via `MONGODB_TEST_URI`. The wrapper rejects non-local URIs, creates a fresh random `_test` database, and the test drops only that disposable database in teardown. It covers 7d/14d creation and independent versions, invalid 1d/metrics/hash, first and subsequent promotion, supersession, exact-pointer reads and bytes, hash tampering, immutable metadata, rejection/failure, stale-generation conflict, duplicate create/promotion idempotency, tenant/scenario/horizon isolation, concurrent creation/promotion, CAS single-winner behavior, and transaction rollback consistency. This focal integration completed **1/1 PASS** on the local `rs0`; no Atlas connection, online dataset, commercial mutation, training, TEST, or cloud write was used.

## Known limitations / next phases

- No production Ridge bytes or bootstrap exist; this is persistence infrastructure only.
- No scoring/serving, worker, scheduler, public endpoint, frontend, or inventory integration is included.
- The service stores bounded bytes in one Mongo document; a future artifact format exceeding the validated limit needs a separately reviewed storage change.
- Replica-set transactions are required; standalone MongoDB is unsupported.
- The deployment/worker availability and inventory's 1-day forecast dependency remain later-phase blockers documented by A.2.3.
