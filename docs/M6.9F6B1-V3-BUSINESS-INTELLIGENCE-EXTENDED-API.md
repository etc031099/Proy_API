# M6.9F.6B.1 — API estructurada de Inteligencia del Negocio V3

## Alcance y seguridad

Extensión autenticada de `GET /api/intelligence`, para el frontend futuro de F.6B.2. El navegador solo llama al backend Express; no conoce el servicio ML ni su secreto. Todas las rutas usan `authenticate` y `checkBusinessAccess`. `businessId`, scenario, lineage y snapshot se resuelven server-side desde el usuario autenticado. No se acepta un tenant en query/path. Las lecturas de un endpoint comparten el request/snapshot V3 existente; una petición nueva obtiene la revisión operativa nueva. No hay cache nuevo ni decisión de autenticación cacheada.

Las fechas usan el reloj operacional `America/Lima` ya definido por F.5A. `asOf=YYYY-MM-DD` conserva sus límites y reglas: histórico hasta el cutoff y LIVE posterior requiere snapshot válido, sin fallback. No se escriben datos ni se recalculan fórmulas/modelos.

Respuesta exitosa: `{ success: true, data }`. Error: `{ success: false, code, message }`; ambigüedad puede incluir `candidates` con `key`, `label`, `type` únicamente (sin Mongo ID). Errores de negocio distinguen `PRODUCT_NOT_FOUND`, `CUSTOMER_NOT_FOUND`, `SUPPLIER_NOT_FOUND`, `AMBIGUOUS_ENTITY`, `INVALID_PERIOD`, `INSUFFICIENT_HISTORY`, `LIVE_SNAPSHOT_INVALID` y `ANALYTICS_UNAVAILABLE`.

## Rutas

| Método y ruta | Contrato |
|---|---|
| `GET /sales` | `period=TODAY\|LAST_7_DAYS\|LAST_30_DAYS` o `startDate`+`endDate`; `compare=true` opcional; `limit=1..20`. Devuelve revenue/units/tickets/averageTicket/grossMargin y `grossMarginAvailability`, rango previo/variación del motor y top productos/categorías. `includeSeries=true` solicita puntos diarios del mismo motor, limitado a rangos de hasta 30 días; cada punto conserva status. Si no se solicita, `series=null`, `seriesStatus=NOT_REQUESTED`. No se divide un total ni se sintetiza una tendencia diaria. |
| `GET /customers` | Ranking RFM con `sortBy=spend\|frequency\|recency\|gross_margin`, `segment`, `limit=1..20`, `offset`. `summary.segments` conserva la distribución M6.8; incluye total, active (registrados menos el segmento INACTIVE), new, inactive, atRisk, highValue, potential y la exclusión de Consumer Final. `recency`, `frequency` y `monetary` son las entradas RFM de 90 días cuando el motor las incluye; `spend` y `lifetimeTicketCount` permanecen métricas separadas de vida completa. |
| `GET /customers/:customerRef` | Detalle autenticado resuelto por el motor: stable customer code/display name, segmento, recencia, frecuencia, gasto, ticket promedio, última compra, razones, preferencias, tendencias/ventanas y freshness/status disponibles. Los campos RFM faltantes quedan `null`; `spend`/`lifetimeTicketCount` se distinguen de monetary/frequency de 90 días. Sin correo, teléfono o Mongo ID. |
| `GET /suppliers` | Ranking por gasto recibido, periodo acotado, summary de spend/pedidos pendientes y recibidos y dependencia del motor; `limit` y `offset` acotados. El summary no define un promedio agregado de lead time y lo marca `NOT_EXPOSED_BY_ENGINE`; cada fila expone promedio/muestra del motor y su availability. Si falta muestra/lead time, se entrega `null` con `INSUFFICIENT_HISTORY`. Puntualidad no disponible queda `null`, no se estima. |
| `GET /suppliers/:supplierRef` | Detalle del motor: órdenes, spend observado, pendientes/recibidas, lead time, puntualidad, dependencia, productos y cost trends disponibles. Cost history vacío se marca `INSUFFICIENT_HISTORY`; no se inventa puntualidad. |
| `GET /associations` | Resumen del artifact M6.7 y reglas `antecedent`, `consequent`, soporte, confianza, lift, tickets, estabilidad/clasificación. Siempre `mode=FROZEN`, `cutoff=2026-10-12`; las cifras de conteo proceden de summary del artifact cargado, no de nueva minería. |
| `GET /products/:sku/related` | Cross-sell por SKU desde recomendacionesBySku del artifact aprobado: producto relacionado, support, confidence, lift, ticketCount, stability y classification. No usa tickets LIVE ni lenguaje causal. |
| `GET /health` | Estado general y dominios sales, margin, customers, inventory, suppliers, forecast y marketBasket: status, freshness, métricas e insights aprobados. No contiene score compuesto. |
| `GET /inventory?limit=1..20` | Mantiene ranking anterior y añade ABC/XYZ/ABC×XYZ desde el summary del motor. `flag=low_stock\|overstock\|slow_moving\|dead_stock\|single_source\|should_reorder` solicita hasta 20 filas filtradas por los flags existentes del motor. Conteos/listas no se recomputan en el backend. |

Forecast y product inventory existentes siguen disponibles y sin cambios de contrato. Montaje, autenticación, rate limit y orden de middlewares existentes se mantienen.

## Frescura y nulabilidad

- Ventas, clientes, proveedores, inventario y Health heredan `mode`, `asOf`, `updatedAt`, `dataThrough`, `dataVersion`/`snapshotHash` y freshness del motor cuando existen.
- Market Basket siempre se declara congelado al 2026-10-12, incluso cuando otras secciones de Health son LIVE.
- Gross margin/COGS, lead time, puntualidad, preferencias, cost history y métricas no sustentadas por el motor pueden ser `null`, con availability/history status donde corresponda. `0` solo se conserva cuando el motor lo devuelve como valor observado.
- Consumer Final no aparece como cliente RFM individual.
- No hay fallback a histórico para solicitudes LIVE inválidas.

## Contrato de consumo propuesto para M6.9F.6B.2

La UI debe consumir los endpoints de arriba directamente como JSON, usando `asOf`, `mode`, `freshness`, `status`, `availability` y `historyAvailability` para etiquetas/estados. Debe representar `null` como “No disponible”/“Historial insuficiente”, no como cero. En Market Basket debe mostrar siempre “Histórico al 12/10/2026”. La serie de ventas se pide explícitamente con `includeSeries=true` y solo hasta 30 puntos. Rankings/listas deben respetar `limit`/`offset`; no inferir valores fuera de la página. Errores y candidatos se presentan con sus códigos/labels seguros, nunca con IDs técnicos ni datos de otro negocio.

## Límites conocidos

- La serie diaria usa llamadas diarias acotadas al engine (hasta 30) solo cuando se solicita; no se agrega una lectura de colecciones ni una agregación alternativa en Express.
- No se crea un promedio global de lead time: se conservan los datos por proveedor publicados por el motor.
- La API no introduce cache; coherencia de LIVE sigue dependiendo del snapshot/dataVersion existente.
- No se modificó frontend ni se desplegó. La aceptación visual pertenece a F.6B.2.
