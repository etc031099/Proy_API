## 2. Flujo y clases

`classifyGrounded` distingue `DETERMINISTIC`, `GROUNDED_LLM`, `OUT_OF_DOMAIN` y `AMBIGUOUS_WRITE`. Las órdenes explícitas, selecciones y confirmaciones siguen sus rutas existentes; las acciones ambiguas no reciben permiso de escritura por clasificación.

Flujo efectivo: wrapper WRITE y guard tenant → gate externo de alta precisión → clasificación de preguntas analíticas abiertas V3 → plan READ/autorización → skills → contexto compacto → síntesis neutral opcional → validación → respuesta. Las consultas simples conservan rutas deterministas, sin síntesis LLM. El gate se adelanta al fallback de búsqueda por frase que causaba los bugs de cuento/Bitcoin; esto no significa que todo texto desconocido se rechace.

`domainGate.js` usa formas completas de preguntas externas, normalizadas por acentos/puntuación. Incluye deportes de ayer, capital de Francia, cuento, recomendación externa de laptop, cotización de Bitcoin, presidente y currículum. No usa una blacklist extensa de monedas o nombres. Referencias explícitas al catálogo o consultas mixtas con lenguaje del negocio se dejan al routing normal para evitar falsos positivos. No es un clasificador universal de temas externos; otras formulaciones pueden seguir llegando al fallback legacy. El proveedor/clasificador real continúa sin validación en esta fase.

Ejemplos permitidos: precio de Sprite/pan/Coca-Cola, cuánto cuesta este producto, mejorar ventas, priorizar inventario, retener clientes, explicar WAPE/K-Means/forecast y analizar el negocio. Las explicaciones aprobadas de WAPE, selección de k y MA28 vs HGB siguen siendo deterministas. La interpretación abierta de esas métricas puede producir un plan grounded.

El orquestador comprueba el tenant antes de usar V3. `service.resolveContext(context)` sigue validando escenario y lineage server-side. El builder no acepta URIs ni credenciales del usuario. Para tenants sin capacidad V3 se conserva el routing previo; no se reutilizan resultados V3 de otro negocio.

## 4. Context builder

`groundedContext.js` recibe pregunta, plan, resultados ya autorizados y binding del escenario. Devuelve un objeto inmutable `grounded-v3-context-v1` con pregunta redactada, intención, escenario/dataset, fecha operativa, corte histórico, `noHistoricalSkuData`, constraints y evidencia seleccionada.

Cada evidencia tiene ref local E1…E4, skill, estado, scope (periodo, modo, fecha, revisión/hash disponibles, fuente, días cerrados), indicador de truncamiento y facts permitidos. Se excluyen resultados de skills ajenas al plan. Allowlists por familia, profundidad acotada y hasta tres filas; no documentos completos, IDs Mongo, correos/teléfonos, URLs, tokens, contraseñas, snapshots o historial conversacional. Se conservan `null`, estados de disponibilidad, riesgo, mínimo configurado, stock, cobertura, incoming, RFM y metadatos analíticos relevantes.

Para retención se envía solo Customer, no todo el catálogo/proveedores/asociaciones. Se conserva `rfm90d.raw`, última compra, frecuencia, gasto y segmento disponibles. No se presume que un ranking AT_RISK tenga asignación K-Means ni una probabilidad de churn. Para priorizar inventario se envían riesgos/stock/mínimo/cobertura, forecast pertinente y pedidos/proveedores disponibles. Para interpretar ML se envía evaluación y metadatos, sin ventas individuales de clientes.

El límite de contexto es **6400 bytes UTF-8**. El recorte elimina filas completas y, si no basta, facts completos marcados `omission=CONTEXT_BUDGET`; conserva la fuente y el corte. No corta JSON serializado ni presenta el contexto omitido como completo. En los **14 fixtures H.7** medidos: **1517–3418 bytes** (aprox. 506–1140 tokens usando bytes/3). Es un estimador explícito, no tokenizer ni usage del proveedor; los datos reales pueden producir tamaños distintos. El sobre del proveedor tiene un límite adicional de 8000 bytes para messages.

## 5. Síntesis y guard de alucinaciones

El contrato exige usar solo evidencia entregada, declarar insuficiencia, separar hechos de recomendaciones, no ejecutar acciones, no inventar cifras/entidades y respetar cortes. Incluye: MA28 estadístico; HGB V3 28d rechazado para operar; FP-Growth sin causalidad; Isolation Forest sin fraude/probabilidad; WAPE no equivale a accuracy; K-Means exploratorio, no churn prediction.

Para SKU nuevos se marca `noHistoricalSkuData=true` y se muestra que no hay historial directo ni forecast validado: solo exploración sustentada por categorías/patrones existentes.

La respuesta neutral usa JSON con 1–3 observaciones (`evidenceRefs`, `interpretation`, `advisoryRecommendation`) y hasta dos limitaciones del contrato. El validador compara refs, números e identificadores V3 con **facts efectivamente enviados**, no contra el resultado completo retenido. Se rechazan datos ajenos, texto sensible, claims metodológicos incorrectos reconocidos y afirmaciones de ejecución. Estos controles estructurales/lexicales no prueban la verdad de toda frase libre: la calidad semántica con el proveedor real se evaluará en J.2B.

Sin proveedor neutral explícitamente inyectado, el runtime reúne y muestra los hechos aprobados e indica que la interpretación adicional no está habilitada. No usa Gemini como fallback para esta síntesis nueva. El resto del camino Gemini legacy mantiene su configuración y comportamiento.

## 6. Provider-neutral y compatibilidad

`providers/neutralProvider.js::createNeutralProvider` recibe identidad/modelo server-side, un transporte `generate` inyectado, timeout y precios opcionales. J.2A no incluye transporte HTTP nuevo, selector DeepSeek, modelo, URL o key. La interfaz pública es `generate({messages,maxTokens,temperature}) → {text,provider,model,usage,latencyMs,estimatedCostUsd,pricingVersion}`.

El nuevo camino de `execution.generateGrounded` comparte el presupuesto y observabilidad de ejecución: máximo una generación grounded por request, sin tools y sin retries/failover. La fábrica acota timeout (máximo 20 s; default 15 s), prompt/respuesta y normaliza usage desconocido a null. Se solicita cap de **300 output tokens**, temperatura 0; la interfaz permite 600 para una futura política explícita de detalle. No se configura hoy un proveedor de pago para esta ruta.

El adapter Gemini, su SDK, secretos, defaults, output ceilings y failover legacy permanecen compatibles. La clasificación/contexto grounded no importa su adapter ni sus códigos. J.2B puede inyectar un transporte nuevo sin reescribir router, skills, motores o state machine WRITE. El camino legacy todavía importa Gemini; esta fase añade el desacoplamiento necesario para grounding V3, no sustituye de forma global el proveedor.

## 7. Telemetría y costo

Se agregan campos neutrales al usage del runtime e historial público, manteniendo aliases existentes:

`provider`, `model`, `llmCalls`, `inputTokens`, `outputTokens`, `totalTokens`, `estimatedCostUsd`, `providerLatencyMs`, `pricingVersions`.

Determinista y preview/cancel sin generación: provider `none`, model null, llamadas/tokens/costo 0. Con generación neutral: identidad/modelo declarados por wiring, usage real del transporte, latencia medida. Sin usage/tarifa: null, nunca cifra inventada. `metricsComplete` neutral requiere input/output/total; thought/tool tokens no aplicables no se fabrican como uso real. Gemini conserva su validación de campos específicos. No se registran prompts, facts ni secretos en los eventos existentes; el historial proyecta metadatos grounded, no el contexto completo.

`estimateCostUsd` acepta configuración server-side con provider/model, moneda USD, versión, `effectiveFrom`, `inputPricePerToken`, `outputPricePerToken` y cached input opcional. Selecciona la versión efectiva más reciente y suma categorías disjuntas: `(input-cached)*inputRate + cached*cachedRate + output*outputRate`. Sin tarifa cached configurada se aplica inputRate al input completo. Con tarifa cached pero sin usage cached verificable, costo null. Los tests usan precios ficticios claramente etiquetados; no se cargaron tarifas Gemini/DeepSeek reales.

Los aliases legacy siguen representando generaciones lógicas; intentos Gemini conservan su telemetría histórica. No se afirma costo exacto de retries con usage ausente. El camino nuevo no reintenta: una generación/una invocación de transporte, o ninguna.

## 8. Fallos, WRITE y privacidad

Se simularon 401, 429, timeout, 5xx y respuesta malformada. La síntesis falla de forma controlada y preserva el texto factual obtenido; no devuelve errores crudos del proveedor. Si falta una skill posterior, se conserva la primera evidencia y no se solicita síntesis con la lectura incompleta. PARTIAL también impide esa generación. NO_DATA por sí solo no justifica una llamada.

Grounding solo READ. Una recomendación no genera `PendingAction`, ni se guarda como confirmación. `hazlo` sin preview válido pide el flujo normal; una READ grounded durante un preview suspende su confirmación y exige revisar de nuevo la tarjeta. Confirmar explícitamente invoca solo el servicio WRITE existente; seleccionar una entidad/ordinal no confirma. Cancelación sigue siendo cancelación. La prueba integrada ejecuta una confirmación **solo en un mock** para verificar el contrato, nunca una operación comercial.
